# フロントエンド移行 — Flutter から Electron へ

親 Issue: [#201](https://github.com/HIKARU0627/Auto-Scoring/issues/201)（フロントエンドを Flutter から Electron へ移行する）。

本書は **2026-09-10 のオーナー決定**と、その後の段取り・cut-over 条件を記録する。
実装はまだ始まっていない。現行の Flutter アプリ（`app/`）は**凍結**しており、
新機能は Electron 側（将来の `desktop/`）へ入れる。

## 1. 決定の要約

| 項目             | 決定                                                                                                                   |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------- |
| シェル           | **Electron**                                                                                                           |
| 言語・UI         | **TypeScript + React + Vite**                                                                                          |
| スタイル         | **CSS 変数（デザイントークン）+ Tailwind** — [`design-tokens.md`](./design-tokens.md) の配色・余白・タイポを移植する器 |
| サーバ状態       | **TanStack Query** — 画面はほぼサイドカー API の投影。独自キャッシュを書かない                                         |
| API クライアント | **OpenAPI から生成**（`openapi-typescript` + `openapi-fetch`）。手書きしない                                           |
| テスト           | **Vitest + React Testing Library**、フロー系は **Playwright (Electron)**                                               |
| PDF 表示         | **PoC で決める**（[Issue #202](https://github.com/HIKARU0627/Auto-Scoring/issues/202) PoC 6）                          |
| バックエンド     | **変更しない** — Python サイドカーはそのまま。API 変更が要ると判断したら司令塔へ相談                                   |

**新規依存は上記に限る。** 増やす場合は Issue を立てて司令塔に確認する。

### 1.1 理由

- 開発効率の悪さと UI のブラッシュアップ。目指す完成形は落ち着いたダークテーマのフラットデザイン（モチーフ画像はオーナー提供。リポジトリには入れない）。
- この移行は、既に起票されている UI 系 Issue（#185 / #187 / #192 / #196 など）より**優先**する（オーナー指示）。

### 1.2 規模（実測、2026-09-10、`origin/main`）

| ----------------------------------------- | ------ | -------- |
| `app/lib`（実装）                         | 24,780 | 63       |
| `app/test`（テスト、`_test.dart` のみ）   | 23,868 | 52       |

本 PR にて測り直した値であり、旧版に載っていた古い内訳値とは対応しない。

**書き直す量より、失う可能性のあるもののほうが重い。** 守るべき約束の正本は
[`frontend-invariants.md`](./frontend-invariants.md)（テストが根拠の INV 170 件と、

## 2. 最大のリスク — テストが固定している約束

`app/test` のウィジェットテストは、実機検証で痛い目を見て確定した振る舞いを固定している。
コードを書き直すと、これらは**黙って消える**。

移行の完了条件は「画面が動くこと」ではなく、
[`frontend-invariants.md`](./frontend-invariants.md) の一覧が**新スタックのテストで全部固定されていること**。

Issue #201 で司令塔が挙げた 10 項目（網羅ではない。詳細は不変条件文書）:

| 不変条件                                                             | 出どころ     |
| -------------------------------------------------------------------- | ------------ |
| 見ていない判断材料で確定できない                                     | #85 / #145   |
| 確信度から完了を導かない（確信度 1.00 の誤った 0 点が 14 件中 7 件） | §25.2 / #136 |
| 失敗が要約から漏れない・畳んでも残る・下流の「待ち」と区別できる     | #86          |
| 無効な操作には、無効にしている条件そのものから導いた理由が出る       | #88          |
| 画面を足したら「ホームへ戻れる」検査に必ず載る                       | #88 / #197   |
| 失敗の文言は「何が起きたか」と「次に何ができるか」を必ず両方持つ     | #86          |
| 廃止した文言が二度と現れない                                         | #111 / #138  |
| 別のボタンにフォーカスした Enter が確定を実行しない                  | #145         |
| 無効ボタンの明度差は目視でなく計算で満たす                           | #88          |
| 回答欄の未検出／未割当／読み順の食い違いの見せ方                     | #164 / #171  |

### 2.1 完了条件そのものにあった穴 — テストが無い保証（Issue #216）

上の完了条件は `app/test` を基準にしている。**`app/test` に無い保証は、この基準では定義上こぼれる。**

見つかった実例が Windows の Job Object（強制終了時のサイドカー自動回収）で、
これは `app/lib` の実装だけが持っていてテストが1件も無い。PoC 7（#203）がライフサイクルを
直接叩いたから偶然見つかった。そこで `app/lib` を同じ観点で1回掃き、
[`frontend-invariants.md`](./frontend-invariants.md) §14 に **UG-01〜UG-15 の 15 件**として記録した
（掃いたファイル 63 件、候補として検討 31 件、認定 15 件。掃き方は同 §14.1）。

移行の完了条件は、したがって次の 2 つになる。

1. §1〜§13 の **INV 170 件**が新スタックのテストで固定されていること。
2. §14 の **UG 15 件**が引き取られていること。うち 10 件は移行先ではテストで守れる
   （Flutter で書き忘れていた 7 件 + 移行先で初めてテスト可能になる UG-03 / UG-05 / UG-11）。
   残る UG-01 / UG-02 / UG-04 / UG-08 と UG-14 の「場所が一致していること」の側は
   **Windows 実機の確認**に落ちる。だから cut-over 条件に実機確認を必須で入れた（次項）。

### Phase 3 以降 — 画面ごとの移植

取込 → テスト設定（配点・回答欄エディタ）→ 答案キュー → 添削レビュー → 答案確定 → 設定 → 出力。

**1 画面 = 1 Issue = 1 PR。** 各 PR は、その画面が持っていた不変条件のテストを必ず伴う。

#### 不変条件の引き取りを PR で積み上げる

[`frontend-invariants.md`](./frontend-invariants.md) の不変条件は **INV 170 件 + UG 15 件**あり、
「全部移した」を 1 つの PR で一度に証明することはできない。そのため、画面ごとの PR で
**どれを引き取ったかを積み上げる**運用にする。cut-over の判定（次項）は、この積み上げが
185 件を覆っているかで行う。

- 画面移植 PR は、その画面が**引き取った INV 番号・UG 番号を PR 本文に列挙**し、対応する新スタック
  （Vitest / Playwright）のテストを示す。
- **UG は「テストで守る」だけとは限らない。** テストで守れないものは、代わりに何をするか
  （Windows 実機の確認手順、実装上の構造的な担保）を PR 本文に書く。
- その画面に関係する INV / UG のうち**引き取らないものがあれば、引き取らない理由**（例: 別画面へ移管、
  follow-up Issue で対応）を PR 本文に書く。

### Cut-over

次がすべて満たされたときのみ `app/`（Flutter）を削除し、CI・docs・packaging を切り替える。

1. [`frontend-invariants.md`](./frontend-invariants.md) §1〜§13 の **INV 170 件**が全部新スタックで固定されている
2. 同 §14 の **UG 15 件**が引き取られている（テストで守るもの／Windows 実機の手順で守るものの別を明示する）
3. **強制終了しても次回の起動が失敗しないこと。Windows 実機で確認するまで cut-over しない。**
4. Windows での配布物（electron-builder + PyInstaller サイドカー）が動く
5. 司令塔の承認

#### 3 の確認手順と、それが必須条件である理由（最高責任者の決定、2026-09-10）

**理由: いま Flutter が持っている保証を、移行で黙って落とさないため。**

Flutter は `app/lib/core/child_process_group.dart` で `dart:ffi` から `kernel32.dll` を呼び、
`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` を立てた Job Object にサイドカーを入れている。
アプリがタスクマネージャーから強制終了されても、Windows カーネルがサイドカーを道連れで終わらせる。
**この保証には `app/test` にテストが1件も無い**（`ChildProcessGroup` / `JobObject` への参照 0 件、実測）。
Win32 の挙動は `flutter test` では固定できないからで、**テストが無いので上の 1 を満たしても消える。**
素の Electron（Node.js `child_process`）にこの機構は無い
（[`poc-7-sidecar-lifecycle.md`](./poc-7-sidecar-lifecycle.md) §4 表 1 行目）。

孤児が残ると `app-data/.lock` を握り続けるため、次回起動したサイドカーは exit code 3 で即座に終了し、
利用者には「Auto-Scoring はすでに起動しています」だけが出る ―― **起動できない理由が画面から分からない状態**になる。

**確認手順**（Windows 実機。自動テストでは代替しない）:

1. アプリを起動し、ホームまで到達させる。
2. タスクマネージャーの「タスクの終了」（または `taskkill /F`）でアプリを強制終了する。
3. サイドカープロセスが残っていないことを確認する。
4. アプリを起動し直し、**ホームまで到達すること**を確認する。「すでに起動しています」が出たら不合格。

Job Object 相当をどう実装するか（ネイティブアドオンで `AssignProcessToJobObject` を呼ぶか、
サイドカー側に親プロセス監視を入れるか）は PoC 7 §5.4 の決定に従う。**どちらを採っても、
この cut-over 条件が要求するのは実装の有無ではなく上の 4 手順の実測結果である。**
関連する保証の一覧は [`frontend-invariants.md`](./frontend-invariants.md) §14（UG-01〜UG-15）。
