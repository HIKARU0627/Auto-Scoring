# デザイントークン

Issue #67。アプリの見た目を決める値（フォント・配色・余白・角丸・エレベーション・
モーション）を1箇所に集め、その根拠を残す文書。

**この文書の対象は `app/`（Flutter）だけ**である。PDF出力に焼き込む色とフォントは
別の決定で、[pdf-export.md](./pdf-export.md) §3 にある（画面と出力で赤ペンの色を
合わせている点だけ §3.4 で触れる）。

## 0. なぜトークンを先に決めるのか

Issue #67 以前の `app/lib/core/app_theme.dart` は23行で、中身は
`ColorScheme.fromSeed(Color(0xFF1565C0))` と `useMaterial3: true` だけだった。
TextTheme もコンポーネントテーマも余白スケールもモーション定義も無い。この状態で
画面を作り込むと、画面ごとに寸法と色がばらつき、後から揃えるのは全画面の書き換えに
なる。

だから**この Issue の主目的は「良い見た目を決めること」ではなく、「見た目を後から
差し替えられる構造にすること」**である。以下の値はすべて出発点であり、変えたく
なったらトークンを差し替えればよい。**変えたときはこの文書も同じPRで更新する。**

### ファイル構成

| ファイル                             | 中身                                                                              |
| ------------------------------------ | --------------------------------------------------------------------------------- |
| `core/design/design_tokens.dart`     | 余白・角丸・エレベーション・アイコン寸法・レイアウト寸法・モーション              |
| `core/design/app_color_schemes.dart` | ライト/ダークの `ColorScheme` と `AppStatusColors`                                |
| `core/design/app_typography.dart`    | フォント指定・`TextTheme`・`AppTextRoles`                                         |
| `core/design/app_status_tone.dart`   | 状態→強調度（`AppStatusTone`）の対応と、その色                                    |
| `core/design/app_theme_context.dart` | `context.colors` / `context.texts` / `context.statusColors` / `context.textRoles` |
| `core/app_theme.dart`                | 上記を `ThemeData` へ組み立てる（コンポーネントテーマ）                           |
| `core/widgets/`                      | 複数画面で重複していた見た目の要素                                                |

依存方向は `features → core → api`（[technology-stack.md](./technology-stack.md) §5）。
トークンは全部 `core` にある。`features` からの触り方は2通りで、寸法・モーションの
ような定数は `AppSpacing.lg` のように直接、テーマに載る色と文字スタイルは
`context.colors` / `context.textRoles` 経由で読む（後者は `Theme.of(context)` の薄い
別名なので、ライト/ダークの切り替えがそのまま効く）。**画面が自分で値を決めることは
無い。**

#### INV-080 静的検査の対象範囲と運用方針

1. **対象範囲**:
   - 走査対象: `desktop/src/renderer/features/` 配下の全 `.ts` / `.tsx` ファイル。走査ファイル数が 24 件以上であることを assert し、glob 外れによる空振りを防ぐ。
   - 違反とみなすもの:
     1. 色リテラル: `#hex`、`rgb()`、`rgba()`、`hsl()`、Tailwind 既定色（`bg-black`, `bg-white`, `text-black` 等）、任意ブラケット色指定（`bg-[#...]`）。デザイントークン色（`bg-surface`, `text-on-surface`, `text-error`, `text-attention`, `text-success` 等）を使用すること。
     2. 任意ブラケット寸法/スタイル: `className` 内の任意値指定（`max-w-[960px]`, `border-[3px]`, `text-[48px]`, `h-[14px]` 等）。
     3. 数値スペーシング: Tailwind 生数値スペーシング（`p-1`, `py-0.5`, `mt-1.5` 等）。`AppSpacing` に対応するトークンクラス（`p-xs`, `p-sm`, `p-md`, `p-lg`, `p-xl`, `p-xxl` 等）を使用すること。
     4. 単独 `rounded`: トークン角丸（`rounded-sm`, `rounded-md`, `rounded-lg`、円形用の `rounded-full`）ではなくプレーンな `rounded` を直接指定すること。
     5. インラインスタイル直書き: `style={{ color: ..., backgroundColor: ..., padding: ..., margin: ..., borderRadius: ... }}` による静的スタイルの直接指定。
   - 対象外とするものとその理由:
     1. TypeScript/JavaScript ロジック内の配列インデックスアクセス（`entries[0]` 等）や正規表現・演算子に含まれる角括弧: スタイリングではなくデータ処理・ビジネスロジックであるため。
     2. PDF 座標計算・ドラッグ描画における動的絶対配置（`style={{ left, top, width, height }}`）および進捗率のパーセンテージ幅（`style={{ width: \`\${pct}%\` }}`）: 画面の寸法規律ではなく、PDF ページの動的幾何変換（`normalized-coordinates`）やランタイム状態の計算値であるため。
2. **既存残存違反の扱い（厳密な同一性 allowlist 方式）**:
   - 件数ベースの baseline は採らず、`(file, symbol, rule, literal)` の組で 1 件ずつ列挙した allowlist で許可する。`line` は記録時点の参考値であり照合キーには含めない（`features/` は並行編集で行番号が動くため）。これにより既存違反があるファイル内でも、列挙に無い新規違反（新しいリテラル）は即座に赤となる。
   - allowlist は Issue #295 で空になった。上限は `EXPECTED_ALLOWLIST_COUNT = 0` で、以後は新規違反を allowlist に登録できない（増やす方向は赤、減らす方向のみ許可）。
   - 新しく `features/` にスタイルを足すときは allowlist ではなく、`design-tokens.css` / `index.css` のトークン・ユーティリティクラスを使う（§4.6）。

## 2. タイポグラフィ

### 2.1 このアプリが画面に出す文字

設問文・**OCRが読み取った答案の文字**・採点コメント。ほぼ全部日本語である。Latin は
点数（`12 / 20 点`）と一部のラベルだけ。したがって「Latin用フォントに日本語が
フォールバックで付く」構成は取らない。フォールバック構成では、1つの文の途中で
2書体のウェイト・字幅・ベースラインが混ざる。**それが混ざるのは、レビュアーが最も
注意深く読まなければならない文字そのもの**である。

### 2.2 採用: Noto Sans JP（可変フォント、同梱）

`app/assets/fonts/NotoSansJP-VariableFont_wght.ttf`（9.6 MB）。

**コスト（承知のうえで払っている）**: この1ファイルでリポジトリのpackサイズが
約2.4 MB→約12 MBになり、**リポジトリ最大ファイルの約24倍**という事実は変わらない。
cloneは確実に重くなる。一方で配布物は約75 MBのinstallerなので、そちらでの9.6 MBは
相対的に受け入れられる範囲である。

**それでも同梱する**という結論で確定している。決め手は容量ではなく正しさで、
サブセット化して軽くする案を採らない理由は §2.3.1 に分けて書いた。

決め手は次の2点で、どちらも**推測ではなく実測**した（`app/test/app_typography_test.dart`）。

1. **数字が等幅**。10個の数字の送り幅が全て同一（フォント内部で 521/1000 em）。
   点数は `12 / 20 点` の形でその場で書き換わるので、比例数字だと桁が変わるたびに
   行全体が横に揺れる。`tnum` フィーチャは持っていないが、**そもそも必要ない**。
2. **`wght` 軸の可変フォントで、Flutter は `fontWeight` をその軸へそのまま流す**。
   つまり1ファイルで 100〜900 の本物のウェイトが出る（合成ボールドではない）。
   静的インスタンスを3ウェイト同梱すると約15 MBになるところが9.6 MBで済む。

### 2.3 却下した候補と、その理由

| 候補                                         | 却下理由                                                                                                                                                                                                                                   |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **BIZ UDPGothic**（UD書体）                  | 誤読しにくさでは第一候補だった。だが**数字が比例幅**（`1` の送り幅 1290 に対し他は 1556 / 2048 em）で、しかも `tnum` を持たないため直しようがない。点数表示が揺れる。加えて Regular/Bold の2ウェイト（静的2ファイル 9.3 MB）しかない       |
| **BIZ UDGothic（等幅）を認識文字だけに併用** | 誤読耐性は最も高く、マス目付き解答欄とも相性が良い。だが2書体で計14 MB。**トークンを差し替えれば後から採用できる**ので、この Issue では見送る                                                                                              |
| **OS同梱フォント（游ゴシックUI等）を指定**   | 追加バイトはゼロだが、開発機（Linux）・CI・利用者で描画が変わる。これは Issue #60 で解消したばかりの問題と同じ類で、あのときは日本語とLatinを同時に描けるフォントがLinuxに無くテストが13件落ち続けていた。OS依存へ戻すのはその再導入になる |
| **`google_fonts` パッケージ**                | 初回描画時にネットワークを要求する。このアプリはオフライン前提（サイドカーもローカル）                                                                                                                                                     |

**この決定は可逆である。** 書体を変えたくなったら `app_typography.dart` の
`appFontFamily` と `pubspec.yaml` の `fonts:` を差し替え、この節を書き直せばよい。
ただし §2.2 の2点は `app/test/app_typography_test.dart` が検査するので、それを
満たさない書体に変えるならテストの意図ごと見直すこと。

### 2.3.1 なぜサブセット化しないのか（容量削減の誘惑への回答）

9.6 MB は**リポジトリ内の最大ファイルの約24倍**であり、「使う文字だけに絞れば
数百KBになる」という削減案は必ず出る。**採らない。** 理由は容量ではなく正しさである。

この画面が表示するのは**OCRが手書き答案から読み取った任意の日本語**で、どの字が
出るかは事前に分からない。サブセット化して外れた漢字は豆腐（□）になる。それは
見た目の劣化ではなく、**生徒が書いた字と違うものを画面に出している**という誤りで
あり、しかも起きる場所が「レビュアーが1文字ずつ突き合わせている、まさにその欄」
である。誤読を減らすために書体を選んでおきながら、字を消す最適化は矛盾する。

同梱ファイルの実測（`fontTools` で確認）:

| 項目           | 実測値                                                                             |
| -------------- | ---------------------------------------------------------------------------------- |
| ファイルサイズ | 9,589,900 bytes（9.15 MiB）。同梱フォントはこの**1ファイルのみ**                   |
| 可変軸         | `wght` 100〜900（named instance 9個）。静的インスタンスではない                    |
| グリフ数       | 17,936（cmap 収録 16,732 codepoint）                                               |
| 容量の内訳     | `glyf` 5.36 MB（55.9%）+ `gvar` 3.75 MB（39.1%）で全体の95%                        |
| 収録範囲の確認 | JIS第2水準（躑躅・顰蹙・魑魅魍魎 等）・人名異体字（髙﨑德濵瀨邊 等）ともに欠落なし |

**9.15 MB は可変フォント1本として妥当**である。内訳のとおり、実体は輪郭データ
（`glyf` 5.36 MB）と、その輪郭をウェイト方向へ動かす差分（`gvar` 3.75 MB）。
静的インスタンス1ウェイトなら `gvar` が無くなるぶん約5.5 MBだが、タイプスケールは
w400/w500/w700 を使い分けるので**3ウェイトで約16.5 MB**になり、可変1本のほうが
小さい。つまり可変フォントの採用自体が既に容量削減側の選択である。

なお収録範囲は「Unicodeの全CJK」ではなく**日本語の標準的な文字集合**である
（CJK拡張A/Bはごく一部）。これは正しい線引きで、削るなら「日本語として書かれうる
文字集合」を削ることになる、というのが上の論点である。

`app/test/app_typography_test.dart` の
`the bundled file is still the whole variable font` が、フォントの table directory を
直接読んで **(1) `fvar` があること**（静的インスタンスへの差し替え検出）と
**(2) グリフ数が17,000以上あること**（サブセット化の検出）を検査する。容量削減の
コミットは、diff上は無害に見えてもここで落ちる。

### 2.4 ライセンス（自分で確認した内容）

- **SIL Open Font License 1.1**。ライセンス全文は `app/assets/fonts/OFL.txt`
  として**アプリに同梱**している（`pubspec.yaml` の `assets:`）。OFL は
  「フォントの再配布時にライセンスと著作権表示を同梱すること」を求めるので、
  これがその要件への対応。
- 著作権表示: `Copyright 2014-2021 Adobe (http://www.adobe.com/), with Reserved
Font Name 'Source'`（Noto Sans JP は Source Han Sans 由来）。
- **Reserved Font Name** があるため、改変版をその名前で配布することはできない。
  本リポジトリは**無改変のまま同梱**しており、サブセット化もしていない
  （生徒答案にどの漢字が出るか分からないため、字形を削らない）。
- 商用利用・埋め込み・アプリへの同梱は OFL で明示的に許諾されている。フォント
  単体を有償で売ることだけが禁止で、本件は該当しない。

### 2.5 スケール

Material 3 の標準サイズをそのまま使い、**行送りと字間だけを日本語向けに変える**。
サイズを作り直さないのは、Material の各ウィジェットが `titleMedium` などのスロット
から文字スタイルを解決するため。スロットの寸法比を崩すと Chip や ListTile の
プロポーションが壊れる。

- `height`（行送り）: 本文系 **1.75**、UI系 **1.4**。漢字は em ボックスを上下いっぱいに
  使うので、Latin向けの行送り（Material 既定は body で 1.43）だと行同士が視覚的に
  ぶつかる。
- `letterSpacing`: **0**。Material の body/label は Latin 向けに正の字送りを持つが、
  日本語には単語間スペースが無いため、これは「語の内部」を開けてしまう。例外は
  §2.6 の `recognizedText` だけで、そこは「読む」ではなく「1文字ずつ確認する」ための
  意図的な字送りである。
- `leadingDistribution: even`: 増やした行送りをベースラインの下だけに垂らさず上下に
  均等配分する。ListTile や Chip の中で日本語1行が光学的に中央に乗るのはこれによる。

### 2.6 役割別スタイル（`AppTextRoles`）

Material のスロット名（`titleSmall` 等）は「階層のどこか」しか言わない。この
アプリには「その文字が何であるか」で調整したいものがあるので、役割で名前を付ける。

| 役割             | 中身                      | 既定                          | 意図                                                                                                                                                        |
| ---------------- | ------------------------- | ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `questionText`   | 設問文・採点基準の説明    | `bodyLarge`                   | 読んで頭に入れる文章。行送り広め                                                                                                                            |
| `recognizedText` | AI/人が認識した答案の文字 | `bodyLarge` + 17px + 字間 0.5 | **読むためではなく、隣の手書きと1文字ずつ突き合わせるための書体**。1段大きくし、このアプリで唯一の正の字送りを持たせて、1文字ずつを「確認する対象」に見せる |
| `gradingComment` | 採点コメント・根拠        | `bodyMedium`                  | 生徒が返却答案で読む文章。パネル幅に合わせて詰めない                                                                                                        |
| `score`          | 点数                      | `headlineSmall`               | 数字が主役。§2.2 の等幅数字により桁が変わっても揺れない                                                                                                     |
| `uiLabel`        | ラベル・ボタン・チップ    | `labelLarge`                  | 1行前提なので行送りは詰める                                                                                                                                 |

呼び出しは `context.textRoles.recognizedText`。

## 3. 配色

### 3.1 2つのルール

1. **作業面は静かにする。** 採点は同じ画面を何時間も見る作業なので、面積を占める
   ニュートラル（背景・カード・パネル）は手で決める。アクセントの彩度を大きな面に
   乗せない。
2. **彩度の高い色は「人間が見ないと決められない」ためだけに取っておく。**
   `AppStatusColors.attention` がアプリ唯一の暖色・高彩度で、使い道は
   低Confidence・要確認・OCR/AI失敗だけ。**単に処理中のものには色を付けない。**
   進行中は一覧で最も数が多い状態なので、そこに色を割くと本当に人を呼んでいる
   ものが埋もれる。

シードは `#3D6478`（彩度を落としたスレートブルー）。従来の `#1565C0` は Material の
サンプル然とした高彩度の青で、画面の大半を占める作業領域には強すぎた。ただし
**シードが直接画面に出るわけではない**: Material にアクセント系
（primary/secondary/tertiary/error）を生成させ、ニュートラル系はその結果を
上書きして手書きの値に置き換えている（`appColorScheme()`）。アクセント生成を
Material に任せるのは、`on<Role>`/`<Role>` の組み合わせのコントラストを機械的に
保証させるため。

### 3.2 ライトのニュートラル

`surface` は `#FFFFFF` ではなく `#F7F8F9`。最大輝度の面を背景に何時間も黒い文字を
読むのが眩しさの主因であること、そして**採点対象のPDF自体が白い**ことによる。
アプリ側が一段下がることで、答案が手前の物として読める。

### 3.3 ダークのニュートラル（本気で作り直した部分）

従来はシードの `brightness` 違いでしかなかった。Material 既定のダークからの変更は2点。

- **`surface` を `#171B1E` まで持ち上げた**（Material 既定は `#0F1417` 前後の
  ほぼ黒）。純黒の隣に明るいグリフを置くとハレーション（画数の多い漢字がにじんで
  見える現象）が最大化する。また `surface` の下に余白が無いとエレベーションランプが
  組めない。
- **`onSurface` を柔らかいオフホワイト `#CFD7DC` にした。** Material 既定は自分の
  `surface` に対して約 14.4:1 になるが、本アプリは **11.89:1**。WCAG AAA（7:1）は
  大きく上回ったまま、1時間読み続けたときの疲れが違う。

この「上限」は `app_theme_contrast_test.dart` の
`dark text is soft, not maximum-contrast` が 7.0〜13.0 で固定している。白へ戻すのは
してもよいが、**意図せず滑り込むのではなく、決めて、この文書を更新して**行うこと。

### 3.4 状態色（`AppStatusColors` と `AppStatusTone`）

Material の `ColorScheme` に枠が無いものだけを足す。画面は状態を直接色にせず、
まず `AppStatusTone` の4段階に落とす。

| Tone        | 使う状態                                                   | 色                             |
| ----------- | ---------------------------------------------------------- | ------------------------------ |
| `neutral`   | 未処理・AI処理中・未評価・却下（決定済みだが完了ではない） | `colorScheme.onSurfaceVariant` |
| `attention` | 要確認・低Confidence・AIが判断できなかった設問             | `AppStatusColors.attention`    |
| `success`   | 承認済み・確認済み・出力済み・登録完了                     | `AppStatusColors.success`      |
| `danger`    | エラー・取込失敗・読み込み失敗                             | `colorScheme.error`            |

- `attention` と `error` を分けているのが要点。低Confidence の認識は**成功している**。
  信用せずに人が見るべき、というだけで、失敗ではない。
- `success` はくすませてある。済んだ仕事は引っ込むべきで、画面で一番明るいものには
  しない。
- **`annotationMark`（`#C62828`）はライト/ダークで同じ値**。添削記号（○×△・下線・
  囲み・点数）が乗るのは、テーマに関係なく常に白いPDFのページだからである。したがって
  「紙に対して」読めればよい。これは PDF出力が焼き込む赤
  （[pdf-export.md](./pdf-export.md) §3、`_MARK_RGB`）と揃えてあるので、画面で見た
  ものが出力紙面と一致する。**この色は `colorScheme.error` ではない** — 正解に付ける
  ○はエラーではなく、教師の赤ペンである（従来コードは `error` を借りていた）。

**色は状態の唯一の手がかりではない**（Issue #25 の基準）。○×△・Confidence・ジョブ
状態は、すべてアイコン（形）と日本語ラベルを併せ持つ。上の色はその区別を**より
早く見つけられるようにするだけ**で、色が見えなくても情報は落ちない。

### 3.6 無効なボタンの色（`AppDisabledButtonColors`、Issue #88）

Material の既定は無効なボタンを `onSurface` の 12%（下地）と 38%（ラベル）で描く。
あの数字は Material 自身の明るい surface を前提にしたもので、**§3.2 / §3.3 の静かな
ランプの上では数値が出ない**。カード（`surfaceContainerLow`）に載せた既定の無効ボタンを
実測すると:

| 既定の無効ボタン（カードの上）                   | ライト | ダーク | 判定             |
| ------------------------------------------------ | -----: | -----: | ---------------- |
| `onSurface` 12% の枠 / `surfaceContainerLow`     |   1.26 |   1.35 | 3:1 に届かない   |
| `onSurface` 38% のラベル / `surfaceContainerLow` |   2.30 |   2.80 | 4.5:1 に届かない |

Issue #88 が報告した「ダークテーマでは無効ボタンとカード背景の明度差が小さく、ボタンで
あることすら判別しにくい」はこれである。そこで既定を上書きし、役割を3つに分ける。

| トークン                  | 値                        | 何を担うか                                       |
| ------------------------- | ------------------------- | ------------------------------------------------ |
| `disabledButtonOutline`   | `outline`                 | 「ボタンがそこにある」。境界線なので 3:1 を目標  |
| `disabledButtonLabel`     | `onSurfaceVariant`        | 「何のボタンか」。読む文字なので 4.5:1           |
| `disabledButtonContainer` | `surfaceContainerHighest` | 板。ランプの段なので差は小さく、数値は期待しない |

| 組み合わせ                                                  | ライト | ダーク | 判定             |
| ----------------------------------------------------------- | -----: | -----: | ---------------- |
| `disabledButtonOutline` / `surface`                         |   3.94 |   4.66 | AA（非文字 3:1） |
| `disabledButtonOutline` / `surfaceContainerHighest`（最小） |   3.24 |   3.26 | AA（非文字 3:1） |
| `disabledButtonLabel` / `surface`                           |   8.11 |   8.02 | AAA              |
| `disabledButtonLabel` / `surfaceContainerHighest`（最小）   |   6.68 |   5.60 | AA               |

**「押せない」を色で伝えようとはしていない。** 色だけに載せた状態は、色の見え方が違う人
には届かない（Issue #25）。押せないことと、押せない理由は §8 の文が伝える。色に求めるのは
「ボタンがそこにあると分かること」だけである。3種類のボタン（filled / outlined / text）が
同じ見た目になるので、**アプリ全体で「無効」の見た目はひとつ**になる。無効な
`TextButton` にも枠が付くのは有効なときより目立つが、枠も下地も無い無効なテキストボタンは
文章と見分けが付かないので、そちらを取った。

上書きするのは無効のときだけで、有効・ホバー・フォーカス・押下は Material の既定へ落とす
（`core/app_theme.dart` の `_buttonStyle`）。数値と配線は
`app/test/app_theme_contrast_test.dart` が両テーマについて計算して検査する。

`outlineVariant` / `surface` は 1.56（ライト）/ 1.89（ダーク）で 3:1 を満たさない。
これは**区切り線・カード枠の色**であり、WCAG 1.4.11 が対象とする「UIコンポーネントの
識別に必要な視覚情報」ではない（区切り線が見えなくても、行の内容も操作も失われない）。
Material 既定の `outlineVariant` も同程度である。境界を見つける必要がある箇所には
`outline`（3:1 以上）を使う。

## 4. 余白・角丸・エレベーション・レイアウト寸法

### 4.1 余白（`AppSpacing`、4px基準）

| トークン |  値 | 使いどころ                                         |
| -------- | --: | -------------------------------------------------- |
| `xs`     |   4 | 1行の中（アイコンとラベルの間）                    |
| `sm`     |   8 | 密接した要素の間（ラベルとその値）                 |
| `md`     |  12 | 横に並ぶコントロールの間、コンパクトなバナーの内側 |
| `lg`     |  16 | フォームの項目間、カードの内側                     |
| `xl`     |  24 | 画面のセクション間、ページの外周                   |
| `xxl`    |  32 | 中央に置いた単独要素の上下（起動スプラッシュ）     |

段階を6つに絞ってあるのは、採点画面が密度の高い1面であり、6択あれば「関係あるものを
まとめ、無いものを離す」には足りるため。よく使う組み合わせは `AppSpacing.page` /
`.card` / `.banner` / `.actionBar` / `.panel` として `EdgeInsets` で持つ。

### 4.2 角丸（`AppRadius`）

`sm` 4（チップ）・`md` 8（カード・ボタン・入力欄。既定）・`lg` 12（ダイアログ）。
業務ツールとして情報密度を保つため控えめに揃える。角丸が大きいほど、入れ子になった
コンテナのたびに横幅を失う。

### 4.3 エレベーション（`AppElevation`）

`flat` 0 / `raised` 3 / `modal` 6。

**面は影ではなく色で分ける**のが基本方針で、通常の部品はすべて elevation 0 に置き、
ニュートラルランプの段で区別する。影を使うのは本当に内容の上に浮くもの（添削レビューの
アクションバー = `raised`、ダイアログ = `modal`）だけ。採点画面はパネルが何枚も
重なるので、影だらけの画面はライトではうるさく、ダークでは濁る。

### 4.4 アイコン寸法・レイアウト寸法

`AppIconSize`: `inline` 16（本文と同じ行に並ぶ）・`dense` 18（チップ、バッジ）・
`standard` 24（Material既定）・`display` 40（パネル内の空状態）・`hero` 48（全画面エラー）。

`AppLayout`: `narrowBreakpoint` 900（添削レビューが Inspector を PDF の下へ回す幅、
Issue #21 の受入条件）・`inspectorWidth` 440（Issue #85 で 360 から拡げた。
このパネルには承認の判断材料が全部入るので、折り返した行数だけ材料が下へ流れる。
隣のビューアは使っていない幅を手放しただけで、設問1問ぶんの答案領域に800pxは要らない）・
`formMaxWidth` 640（フォームの
読みやすい行長）・`messageMaxWidth` 480（文章なので フォームより狭い）・
`dashboardMaxWidth` 800（ホーム画面の内容幅）・`dialogContentWidth` 360・
`hairline` 1・`sectionDivider` 24。

`dashboardMaxWidth` はフォームより広くウィンドウより狭い（Issue #68 で追加）。
ホームのカードは進捗バーと状態の内訳を横に並べるのでフォーム幅では窮屈になり、
一方で最大化したデスクトップでカード1枚を画面いっぱいに伸ばすと、テスト名から
その行のボタンまで目が長距離を移動することになる。

設問依存DAGパネル（Issue #64）の寸法もここにある: `dagNodeWidth` 116・
`dagNodeHeight` 64（設問番号と最長の状態ラベルが2行で収まる最小）・
`dagPanelHeight` 272（展開時のバンドの高さの上限。図はこの中をスクロールするので、
設問が増えてもPDFビューアから奪う高さは変わらない）・`activityBarHeight` 2。

Issue #85 で、この高さの決め方に2つの上限を足した。

- `dagPanelMaxHeightFraction` 0.3 — バンドは**共有するペインの高さの3割まで**。
  固定値だけだと高さの低いウィンドウで割を食うのは常に判断材料のほうになる
  （1280x720で画面の45%を占め、根拠・コメント・基準ごとの判定を画面外へ押し出して
  いた）。**この画面の縦は判断材料が先に取り、進捗は余りを取る。**
- `dagColumnGapSpreadLimit` 3 — 幅が余ったぶんは層間のギャップに回し、
  元の幅の3倍で止める。ギャップは矢印が描かれる場所で、このパネルが見せたい
  「上流が終わって下流が動き出す」はそこにある。ノード自体は広げない
  （`dagNodeWidth` で既に読める）。ピクセル上限ではなく倍数なのは、
  ギャップの基準値を将来変えても意味が変わらないようにするため。

### 4.5 Electron レンダラーのモーダルダイアログレイアウト（Issue #293）

`desktop/src/renderer/styles/design-tokens.css` の CSS 変数と、
`desktop/src/renderer/styles/index.css` のユーティリティクラスで定義する。
`features/` からはクラス名だけ参照し、任意ブラケット値は使わない（INV-080）。

| トークン / ユーティリティ                | 値                                                           | 使いどころ                                                                           |
| ---------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------ |
| `--layout-dialog-viewport-padding-block` | `spacing-xxl` + `spacing-lg`（48px）                         | ビューポート中央に置くモーダルの外側余白（上下合計）。オーバーレイの `p-lg` と揃える |
| `--layout-dialog-viewport-max-height`    | `calc(100dvh - var(--layout-dialog-viewport-padding-block))` | モーダルパネルの最大高さ。画面高から外側余白を引いた高さ                             |
| `max-h-dialog-viewport`                  | 上記 max-height を適用                                       | 確認ダイアログなど、ビューポート内に収めるパネル                                     |
| `--layout-dialog-body-footer-grid-rows`  | `minmax(0, 1fr) auto`                                        | 本文行はスクロール、最下行（キャンセル/確定）は固定                                  |
| `grid-dialog-body-footer`                | 上記 grid-template-rows を適用                               | 本文＋固定アクション行の 2 行グリッド。同形の確認ダイアログで再利用                  |

## 5. モーション

**長時間見る画面なので、常時動くものを作らない。** モーションは「今まさに状態が
変わった」ことだけを伝えて止まる。アイドルアニメーションも、ループする強調も、
待たされる遷移も置かない。

| トークン                | 値                            | 用途                                                                       |
| ----------------------- | ----------------------------- | -------------------------------------------------------------------------- |
| `AppMotion.stateChange` | 150ms                         | ポインタ/キーボードでコントロールの状態が変わる                            |
| `AppMotion.emphasis`    | 250ms                         | 頼んでいないのに現れて気付く必要があるもの（上限。これより遅いものは無い） |
| `AppMotion.standard`    | `Easing.standard`             | 状態変化の既定カーブ                                                       |
| `AppMotion.enter`       | `Easing.emphasizedDecelerate` | 画面に入ってくるもの（減速して着地する＝「到着した」と読める）             |

**Issue #67 での適用は `AppErrorBanner` の入場1箇所だけ**（フェード+わずかな上方向
移動、`emphasis`/`enter`）。エラーバナーは「頼んでいないものが現れて、気付いてほしい」の
代表例なので、モーションの意味を1つ確定させるのにちょうどよい。
`app/test/app_error_banner_test.dart` が「1回で終わって二度と動かない」ことを検査する。

**各画面への本格適用は別Issue**とする。語彙を先に固定するのが目的である。

### 5.1 唯一の例外: 実行中を示すハイライト（Issue #64）

上の原則の例外は**1つだけ**で、設問依存DAGの進捗パネル
（[dependency-dag-progress-view.md](./dependency-dag-progress-view.md) §4）にある。
`RUNNING` のジョブを持つノードの下辺に、`AppLayout.activityBarHeight`（2px）の
低コントラストのバーが**動き続ける**。

「今まさに処理中」は、1回告知して止められる種類の情報ではない。止まった表示では
「処理中のまま固まっている」と区別が付かず、それこそがレビュアーが最も知りたい
違いである。

例外はここで閉じている: **実行中のノードにしか出ず、2px以上にはならず、
`RUNNING` を離れた瞬間に消え、OSの「視差効果を減らす」設定では止まった同じバーに
なる**。パネルのそれ以外の動きは全て1回で終わる（依存が解けた瞬間の
`emphasis` 250ms の告知と、`stateChange` 150ms の色の落ち着き）。

## 6. 共有ウィジェット層

**1箇所でしか使わないものは先回りして共通化しない。** 実際に重複していたものだけを
`core/widgets/` に出した。

| ウィジェット           | 元の重複                                                                                                         |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `AppErrorBanner`       | 答案取込・テスト登録・テスト設定・添削レビュー Inspector の4箇所。padding と、再試行ボタンが横か下かがずれていた |
| `AppFilePickerRow`     | テスト登録（模範解答/採点マニュアル）と答案取込の2箇所                                                           |
| `DisabledActionReason` | 無効な操作の理由。資料取込・テスト設定・設定がそれぞれ自分の言い回しで書いていた（Issue #88、§7）                |
| `BackOrHomeButton`     | 画面からの出口。どの画面も `AppBar` の既定動作に任せていて、置いていなかった（Issue #88、§7.4）                  |

`AppErrorBanner` の `retryable: false` はテスト設定画面用。この画面の失敗は常に
どれかの明示的な操作（自動解析・保存・確定・登録完了）に属するので、汎用の「再試行」は
どれを再実行すべきか判断できない。

答案の状態ラベル（`未処理` / `処理中` …）は**共通化していない**。添削レビューは
`AI処理中` / `AI処理済み` と表記して人間自身のレビューと区別しており、これは画面ごとの
文言の違いであってデザインの重複ではない。共通化しているのは強調度
（`AppStatusTone`）の方である。

## 7. 無効な操作と、画面からの出口（Issue #88）

見た目のトークンと同じ理由でここに書く。**画面ごとに言い回しを発明しないための1箇所**
である（Issue #88 受入条件5）。

### 7.1 文言はコードの1箇所にしかない

無効なボタンの理由は `app/lib/core/action_requirements.dart` が持つ。`ActionRequirement`
のコンストラクタは private なので、`features/` から新しい理由を作ることはできない。

呼び手の形はこれに固定する:

```dart
final unmet = <なにかの>Requirements(...);           // core が条件から導く
FilledButton(onPressed: unmet.isEmpty ? _action : null, ...)
DisabledActionReason(requirements: unmet)            // その場に文を出す
```

**押せないことと押せない理由が同じ1つの計算から出る。** だから「理由の無い無効ボタン」も
「無効でないのに出ている理由」も書けない。逆向き（画面が文言を書き下ろす）をやっていたのが
Issue #111 と #138 で、どちらも条件が変わって文言だけが古くなった再発である。

### 7.2 書き方

- **満たすべき条件を1文で、画面上の操作の名前で言う。** 「できません」で終えず、何をすれば
  有効になるかまで書く（「上の『取込の型』で、どの型で振り分けるかを選んでください。」）。
- 診断文・例外文・HTTPステータス・内部の理由語は載せない（`AGENTS.md`「Security」、
  `core/dag_failure_guidance.dart` と同じ規律）。
- 件数は条件の文に入れる。ただし**同じ数字を画面の2か所に置かない** —— 片方だけが古くなる。
- 「確定済みです」のような _もう済んでいる_ 理由も理由として数える。無効なのに理由が1つも
  無い状態を作らないほうが大事である。
- 進行中だけで無効になる操作も `ActionRequirement.busy` を出す。進捗表示があるかどうかは
  画面ごとに違い、無い画面では灰色のボタンが黙ることになる。

### 7.3 出し方

`core/widgets/disabled_action_reason.dart`。**ツールチップは使わない** —— ポインタを当てた
人にしか出ないので、キーボードだけで操作する人に届かない（受入条件1）。常にツリーに居る
`Text` として、ボタンの直後に置く。アイコン（`info_outline`）を添えるが、意味は文が持つ。
条件が揃えば縦の余白も残さずに消える。

理由が複数のときだけ「この操作を有効にするには、次が必要です:」の見出しと「・」が付く。
1件のときに見出しを付けるのは、同じことを2回言うだけである。

各行の `Key` は `disabled-reason-<id>`。テストは `id` で探すので、**言い回しを直すために
テストを書き換える必要は無い**。

### 7.4 画面からの出口

`core/widgets/back_or_home_button.dart` を `AppBar.leading` に置く。ホーム以外の全画面。

`AppBar` の既定は「ひとつ前の画面がスタックに残っていれば戻る矢印を出す」で、残って
いなければ何も出さない。ルート表（`lib/app_router.dart`）は7本フラットなので go_router 側に
親ルートという逃げ道も無く、**スタックが空の状態で開かれた画面には出口が1つも無い**。
今の起動経路ではそうならないが、それは「その経路がまだ無いから」であって直っているからでは
ない（Issue #88 の論点2）。

- 戻れるなら、ひとつ前へ（`pop`、既定と同じ振る舞い）。アイコンは矢印。
- 戻れないなら、ホームへ（`replace`）。アイコンは家。行き止まりの画面をスタックに残さない
  ために `push` ではない。
- `go` は使わない。あれはスタックを丸ごと捨てるので、今度は着いた先が行き止まりになる
  （Issue #160、`app/test/navigation_stack_lint_test.dart`）。

検査は `app/test/home_escape_test.dart` が**ルート表を列挙して**行う。画面を1つ足して置き
忘れたら落ちる（ルートが対象一覧にも除外一覧にも入っていない、という失敗になる）。

除外しているのは `/starting`（画面ではなく、`SidecarStartupOverlay` がアプリ全体を覆って
いる間の置き場）と、添削レビュー・答案キューの2画面である。後者は Issue #145 が同じ波で
同じファイルを触っていたためで、技術的な障害は無い —— Issue #192 で入れる。
