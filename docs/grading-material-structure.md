# 採点資料の構造（実資料の観測記録）

## 0. このドキュメントの位置づけ

オーナーから提供された**実際の採点資料**（リポジトリ外・非公開）を調べ、
**構造だけ**を記録する。Issue #95 の受入条件「実資料の構造が docs に記録される
（内容は載せない）」に対応する。

### 0.1 これは仕様ではない

**ここに書かれた形は「1 つの塾の 1 期分」というサンプル 1 件でしかない。**
次に来る資料が同じ形である保証はどこにもない。したがって本書の各項目は

- ❌ 「採点資料とはこういう形式である」という**仕様**
- ⭕ 「**少なくともこの形は実在する**ので、設計がこれに耐えるか確認する材料」

として読むこと。**本書の記述を根拠に、特定の形式を前提とした実装をしてはならない。**
形式に依存しない取り込み方針は
[`simplified-design-specification.md`](./simplified-design-specification.md) §4.3 に定める。

### 0.2 内容は載せない

実資料は塾の著作物であり、塾名・講師名・講座名・課題名・日付・QR コード・答案の中身・
採点基準の本文が含まれる。このリポジトリは公開されているため、**本書にはそれらを一切写さない。**
配点の具体的な数値も、採点基準の内容にあたるため記載しない（何階層で書かれているか、という
構造だけを書く）。

実資料そのもの、およびそこから作った画像・抜粋・テキストを commit / PR / Issue / docs /
CI ログ / スクリーンショット / テスト fixture に出すことは、引き続き禁止する
（[`business-rules-and-evaluation-data.md`](./business-rules-and-evaluation-data.md) §6.7）。
採点 provider へ送ってよいこととは別の話である（同 §2 (2)）。

### 0.3 調査方法（再現手順）

リポジトリ外の資料に対し、次を実行して機械的に集計し、加えて代表ファイルを**目視**した。

```bash
# テキスト層の抽出（pdfium と pypdf の 2 系統で比較）
python -c "import pypdfium2 as p; d=p.PdfDocument('<file>'); print(d[0].get_textpage().get_text_range())"
# ページ画像化して目視
pdftoppm -png -r 110 '<file>' <outdir>/page
```

対象: 教科別フォルダ 11 個・PDF 50 本・Word/Excel 12 本。
**「機械で確認したこと」と「ページ画像を目視したこと」は別物なので、分けて記録する。**

| 資料種別               | 異なる文書数 | 機械確認 | **ページ画像を目視**                                                         |
| ---------------------- | ------------ | -------- | ---------------------------------------------------------------------------- |
| 採点基準 PDF           | 10           | 全数     | **3**（数学・英語・物理）                                                    |
| 生徒答案 PDF           | 10           | 全数     | **3**（世界史・数学・現代文）                                                |
| 添削サンプル PDF       | 24 本        | 全数     | **3 本**（世界史・数学・現代文 各 1 本）                                     |
| 添削資料（Excel/Word） | 12           | 全数     | **0**（表とテキストを機械で読んだだけ）                                      |
| 付属手順書             | 8            | —        | **2 枚**（定型オブジェクト集 1 枚、デジタル添削マニュアル簡易版の 1 ページ） |

- **機械確認**の内容: 全 PDF のページ数・ページサイズ・抽出文字数（pdfium / pypdf 双方）、
  全 Word/Excel のシート構成・見出し行・セル値
- **採点基準 4 件（古漢・世界史・地理・現代文）は、抽出したテキストを読んだ**。
  これは**目視ではない**（版面は見ていない）。本書では「抽出テキストで確認」と書き分ける
- 「異なる文書数」は §1.1 の重複を除いた数。添削サンプルは重複の有無を確認していないため本数で記す

**目視していないファイルについては、機械集計と抽出テキストで分かる範囲しか本書に書いていない。**
**版面の見た目に関する記述は、すべて目視した分にのみ基づく。**

## 1. 配布物の構成

1 教科ぶんのフォルダに、次の 4 種類が入っている。

| 資料         | 形式                  | 役割                                   | 本数 |
| ------------ | --------------------- | -------------------------------------- | ---- |
| 生徒答案     | PDF                   | 採点対象                               | 1    |
| 採点基準     | PDF                   | 問題・模範解答・解説・配点             | 1    |
| 添削資料     | Excel **または** Word | 誤答パターンと赤入れ（コメント）の文例 | 0〜2 |
| 添削サンプル | PDF                   | 添削済み答案の見本                     | 1〜4 |

一部のフォルダには、資料の使い方を書いた短いテキストファイルが同梱される
（11 フォルダ中 8。全て同一内容）。そこには添削資料について
「テキストをコピーして使っても、必要な部分を画像として切り取って貼っても構わない」旨が
書かれており、**添削資料は機械処理される前提で作られていない**ことが分かる。

配布物全体の直下には、別途**デジタル添削の手順書**一式（後述 §7）が付く。

### 1.1 同一ファイルの重複

11 教科ぶんのフォルダがあるが、**2 つの教科は生徒答案・採点基準ともバイト単位で同一**
だった（片方のフォルダに「課題は別教科と同じものを使う」旨のテキストが同梱されている）。

したがって「11 教科」を母数にした比率は実態を過大に見せる。**異なる文書としては 10 種類**
である。本書では以下、母数を明示する。

## 2. ファイル名の規則 — 接頭辞は当たるが、揺れも多い

ファイル名には連番と役割名（生徒答案 / 採点基準 / 添削資料 / 添削サンプル）が入っている。

**先頭 2 桁の接頭辞は、この 1 塾 1 期分では完全に一貫していた。**
機械的に数えた結果、`.txt` を除く **63 ファイルすべてに 2 桁の接頭辞があり、
63 件すべてで接頭辞とファイル名中の役割名が一致**していた（`01`→生徒答案、`02`→採点基準、
`03`→添削資料、`04`→添削サンプル。不一致 0 件）。

**一方、接頭辞以外の部分は揃っていない。**

- 区切りが `04_1_` と `04-1_` で混在する（接頭辞直後の区切りは `_` と `-` の 2 種）
- 連番が `1` と `①` で混在する
- 拡張子が二重になっているものがある（`....pdf.pdf`）
- 末尾に空白が入っているものがある
- ページ数や用紙サイズがファイル名に紛れ込んでいるものがある
- 添削資料が 2 本に分かれる教科があり、番号が `03_1_` / `03_2_` に枝分かれする

**設計上の含意**: 接頭辞は**役割の提案を作る手がかりとして使える**。
ただし**確定の根拠にはしない**。理由は 2 つある。

1. **これは 1 つの塾の 1 期分の命名規則でしかない。** 別の塾が同じ規則を使う保証はない
   （§0.1）。したがって規則は**固定せず、編集できるものとして持つ**
2. 接頭辞以外は上記のとおり揺れており、**名前から取れるのはせいぜい役割の当たりだけ**

**確定は人の確認による**（[簡易設計書](./simplified-design-specification.md) §6.3.2）。
接頭辞で当たらなかったものは中身から判定する（同 §4.3.2）。

## 3. 採点基準 PDF

### 3.1 機械可読性は二値ではない

**「テキスト層があるか」だけでは OCR の要否を判断できない。** 抽出可否と、抽出結果が
使えるかは別の問題であり、実資料には少なくとも 3 通りが混在していた。

| 区分                            | 異なる文書 10 件中 | 何が起きるか                                                 |
| ------------------------------- | ------------------ | ------------------------------------------------------------ |
| A. 抽出でき、読み順も正しい     | 2                  | そのまま使える                                               |
| B. 文字は取れるが読み順が壊れる | 2                  | 文字数は多いのに文章にならない。**抽出成功と誤判定されうる** |
| C. 抽出 0 文字                  | 6                  | OCR / 画像理解が必須                                         |

区分 B は**縦書きの教科**で起きた。実測した壊れ方は 2 通りある。

- 1 行あたり 1 文字に分解される（ある文書のあるページは 1673 行・平均 1.01 文字/行）。
  文字数だけ見ると数千文字が「取れて」いるが、語も文も復元されていない
- ルビが本文の間に差し込まれ、かつ行の順序が入れ替わる

**設計上の含意**: `抽出文字数 > 0` を「OCR 不要」の判定条件に使ってはならない。
この誤判定は区分 B の 2 件で確実に起きる。

### 3.2 抽出 0 文字＝スキャン画像、ではない

区分 C の 6 件のうち**目視したのは 3 件**（数学・英語・物理）。その範囲で
**少なくとも 2 通りある。**

- **紙のスキャン**: 傾き・粒状ノイズ・綴じ跡がある
- **デジタル生成だがテキスト層を持たない**: 版面は極めて鮮明で、数式も figure も
  くっきりしている。紙を経由していない

後者は、スキャン答案向けの OCR 前処理（傾き補正・二値化）を当てる対象ではない。
**期待できる読み取り精度も、必要な前処理も、この 2 つでは異なる。**
「抽出 0 文字」を一律に「スキャン」として扱わないこと。

### 3.3 採点基準 PDF が含んでいるもの

目視した範囲では、この 1 本の PDF に次の 4 つが**まとめて**入っていた。

1. 問題（設問文）
2. 模範解答（解答例。字数指定がある教科ではその指定も）
3. 解説
4. 配点・採点基準

**別途「模範解答 PDF」を要求する理由がない。** これが Issue #95 決定 1（模範解答 PDF を
必須入力から外す）の根拠である。

なお、これら 4 つは**論理的な区切りが PDF のページ区切りと一致しない。** 1 つの PDF ページに
「問題」「解答解説」「採点基準」の 3 つの見出しブロックが縦に並んでいる例があった。
**ページ単位で文書種別を切り分けられる前提を置かないこと。**

### 3.4 配点の所在

Issue #95 のコメントには「採点基準 PDF に配点の記載が見当たらなかった」という調査結果が
残っているが、**これは誤りだった。** **確認できた 5 教科すべて**で、採点基準 PDF に配点があった。
内訳は **抽出テキストで確認 2 件**（区分 A の世界史・地理）と
**ページ画像を目視して確認 3 件**（区分 C の数学・英語・物理）である。
**残り 5 件は配点の有無を確認していない**（区分 B の 2 件は抽出テキストの読み順が壊れており、
区分 C の 3 件は目視していない）。

観測された配点は**2 階層**である。

1. **設問ごとの配点**（その設問の満点）
2. **観点ごとの内訳**（どの要素にいくら与えるか。設問の配点を分割したもの）

さらに、内訳の書かれ方が版面上で 2 通りあった。

- 解説の本文中に、箇条書きとして並ぶ
- 版面を左右に分け、**右側の欄外に、対応する解答手順と行を揃えて**並ぶ

後者は、素朴にテキストを 1 列に流し込むと解説と配点が混ざる。
**読み順を保った抽出か、版面ごと理解させる方法が要る。**

### 3.5 採点方式は教科によって違う

観測された範囲で、少なくとも次の 2 方式が混在していた。

- **加点式**: 観点ごとに与点を積み上げる
- **減点式**: 設問の配点から誤りごとに引く。「配点を超えて減点しない」という下限規則や、
  特定の条件を満たさない場合はその区分の点を与えない、といった条件付きの規則を伴う

減点式の教科では、**採点方式そのものが採点基準 PDF に文章で書かれている**（設問ごとではなく
「第 N 回共通の採点の原則」として先頭にまとまっている形も見た）。

**設計上の含意**: 採点方式は設問ごとに異なりうるうえ、その規則自体が自然文である。
[`business-rules-and-evaluation-data.md`](./business-rules-and-evaluation-data.md) §2 (8) の
「加点式・減点式の両方に対応する」は実資料と整合している。

## 4. 生徒答案 PDF

目視した 3 教科はすべて**紙のスキャン**で、テキスト層は無い（機械確認では答案 PDF
10 件すべてが抽出 0 文字）。

### 4.1 版面の構成要素

> **QR コードについて（2026-09-08 に利用者が確認 / 2026-09-09 に 11 教科で計測）**:
> 答案用紙に印刷されている QR コードは**テストの識別子**を符号化したものであり、
> **利用者側からアプリで利用することはできない**。**生徒に紐づくものではない。**
> **個数と位置は一定ではない**（11 教科の計測で **0〜2 個**、**右上に無い答案も実在**）。
> 当初「全教科の右上にある」と共有されたが、計測の結果それは誤りだった。
> **したがって QR を手がかりにする設計は最初から成り立たない。**
>
> 送信の観点では、**回答欄の検出でページ全体を送っても、QR から生徒識別情報は渡らない**
> （決定 7 の範囲内。業務ルール §2 (2)）。
> **採点のペイロードは回答欄の切り出しのみで、そもそも QR を含まない。**
> **QR の値と符号化形式は実資料なので本書には書かない。**
> アプリが読み取らないことは決定 6 のとおり（簡易設計書 §16.4）。

観測された要素は次のとおり。**全部が毎ページ揃うわけではない。**

| 要素             | 位置           | 備考                                                    |
| ---------------- | -------------- | ------------------------------------------------------- |
| メタ情報の表     | 上部           | 講座名（回）・塾名・校舎名・生徒 ID・生徒氏名・提出期限 |
| QR コード        | 右上 / 左下    | **0〜2 個。答案によって個数が違う**                     |
| 回答欄           | 中央の枠内     | 形状は §4.3                                             |
| 設問ごとの得点欄 | 枠の右下など   | **無いページもある**（§4.4）                            |
| 総得点欄・講評欄 | 最終ページ下部 | ラベル付き。**目視できたのは 1 教科のみ**（§4.4・§8）   |
| フッタ           | 最下部         | 講座名・講師名・回・`（k／m）ページ`                    |

メタ情報の表は、**印字されている教科と、手書きで書き込まれている教科がある。**
提出期限の**日付の書式が教科間で異なる**（区切り記号の有無が違う）。

**各欄の記入状況（2026-09-08 に利用者が 3 教科のページ上端を確認）**:

| 欄           | 実際                                       |
| ------------ | ------------------------------------------ |
| 生徒氏名     | 3 教科とも**空欄**                         |
| 生徒 ID      | 3 教科とも**空欄**                         |
| 塾名         | 3 教科中 1 教科で記入あり                  |
| 校舎名       | 3 教科とも空欄                             |
| 講座名（回） | 全教科に印字。**1 教科は講師の実名を含む** |

**「氏名欄が空欄だから生徒識別情報の規則はもう要らない」とは書かない。**
これは**この 1 塾 1 期分でそうだった**というだけで、次の資料で埋まっている可能性がある
（業務ルール §2 (2) の「除去を前提に設計しない」がまさにこれ）。

なお**講座名に講師の実名が含まれる教科がある**ため、答案ページ全体は
**個人情報を含まないわけではない**。これは**回答欄の検出**でページ全体を送るときに効く
（採点のペイロードは回答欄の切り出しのみで、ヘッダを含まない。業務ルール §2 (2) の表）。
いずれにせよ、**provider へ送ってよいこと（決定 7）**と
**公開してよいこと（禁止）**を混同しないこと。

### 4.2 設問とページの対応は多対多

**「1 ページ＝1 設問」は成り立たない。** 目視した 3 教科で、3 通りが同時に存在した。

- 1 ページに 1 設問
- **1 設問が 2 ページにまたがる**（見出しに「その 1」「その 2」と付く）
- **1 ページに複数設問**（うち 1 つはさらに小問 a〜e に分かれる）

Issue #95 本文の「1 ページ = 1 設問の大きな自由記述欄」という記述は、実資料の一部にしか
当てはまらない。**設問とページの対応は多対多として設計すること。**

### 4.3 回答欄の形状

観測された形状。**同一の設計で扱えるものではない。**

- **横書きのマス目**（1 文字 1 マス。行末の右側に 100 単位の文字数目盛りが振ってある。
  マスの総数がそのまま字数制限に対応している）
- **縦書きのマス目**（列が上から下、列の並びが**右から左**。同一ページ上で複数設問が
  右から左に並ぶ）
- **小問ごとの 1 文字枠**（記号 a〜e に対応する小さな枠が縦に並ぶ）
- **罫線の無い自由領域**（数式や図をそのまま書く。実際に手描きのグラフが書かれていた）

**設計上の含意**: 縦書きが実在する以上、回答欄の座標モデルと Annotation の配置は
**書字方向を持たなければならない。** 左横書きだけを想定した実装は、この教科で破綻する。

### 4.4 得点欄の見分け（実装上の注意）

Issue #95 決定 5 のコメントには「**四角で囲まれた `N/M` が合計点**」という実装上の
手がかりが記録されているが、**目視した結果、この判定規則はそのままでは誤る。**

実際に観測されたもの:

- **設問ごとの得点欄**が、斜線入りの四角として、その設問が終わるページに置かれる。
  分母はその**設問の配点**であって、テスト全体の満点ではない
- 1 設問しか含まないページでは、この設問得点欄が**見た目には合計点と区別できない**
- **設問ごとの得点欄とは別に、テスト全体の合計欄が存在する。**
  目視した 1 教科では最終ページ下部にラベル付きで置かれ、同じ枠内に添削者名の欄が隣接していた
  （**この配置とラベルを一般化しないこと**。確認は 1 教科のみ）
- **囲みの無い得点表記も実在する。** 縦書きの教科では、各設問の列の頭に
  `得点/満点` が四角で囲まれずに手書きされていた
- フッタの `（k／m）ページ` は**ページ番号**であり、得点ではない

**したがって「四角で囲まれているか」で合計点を判定してはならない。**
囲みの有無は得点かページ番号かの手がかりにはなるが、**設問得点と総得点は区別できない。**

**ここに書いたラベルや配置は、あくまで観測例である。**「総得点」というラベル表記を
確認できたのは**1 教科だけ**であり（§8）、**この文字列や位置を識別条件として実装しては
ならない**（§0.1「これは仕様ではない」）。

**実際の識別方針は本書では定めない。**
[簡易設計書 §14.2](./simplified-design-specification.md)（文書全体からの候補提示 →
人による確認 → 判別できなければ推測しない）に従うこと。

### 4.5 答案 PDF は課題全体の一部

フッタの `（k／m）ページ` の `m` と、**PDF のページ数が一致しない。**

- 3 ページの PDF のフッタが `1／3`〜`3／3`（一致する例）
- **1 ページの PDF のフッタが `5／7`**（一致しない例。7 ページの課題から 1 枚だけ抜き出したもの）

つまり配布された答案 PDF は、**より大きな課題の一部を抜き出したもの**でありうる。

これは §4.4 とも絡む。抜き出された 1 枚に総得点欄が含まれていなければ、**その PDF だけからは
テストの満点も合計点も分からない。**

さらに、添削サンプルのフッタの `m` は、同じ教科の生徒答案のフッタの `m` より大きかった。
後述する「ページ追加」（§7）が行われたためと考えられる。**`m` は固定値ではない。**

## 5. 添削資料（Excel / Word）

異なる文書としては Excel 7 本・Word 5 本（両方を持つ教科がある）。
**同じ役割の情報が、教科によって表だったり地の文だったりする。**

### 5.1 Excel — 列スキーマが 4 種類

「回数 / 問題番号 / 生徒の誤り方 / 赤入れ案 …」という表だが、**列の構成が統一されていない。**
Excel 7 本に対し、**異なる列スキーマが 4 種類**あった。

| 差異                                                                                             |
| ------------------------------------------------------------------------------------------------ |
| 列数が 6〜11 で異なる                                                                            |
| 「場所」列があるものと無いもの                                                                   |
| 「採点基準」列があるもの、「減点の有無・幅」というものに置き換わるもの、そもそも無いもの         |
| 「重要度」「頻度」列があるものと無いもの                                                         |
| 同じ意味の列の名前が違う（「生徒の誤り方・現状」/「生徒の誤りの例」、「赤入れ案」/「赤入れ例」） |

さらに、表として読むときに次の点が問題になる。

- **見出し行が 1 行目ではない。** 1 行目は講座名などのタイトル行で、見出しはその下にある
- シート名が統一されていない（「赤入れ案」「第 1 回」「Sheet1」）
- 意味を持たない装飾列がある（矢印 `⇒` だけの列で、中身は常に空）
- セル内に凡例が改行付きで埋め込まれている（記号の意味の説明）
- **同一列の値の表記が同一ファイル内で揺れる**（全角と半角の数字が混在、末尾に全角空白が付く）
- データ行は 2〜6 行と少ない

**設計上の含意**: 列名の一致でマッピングする実装は、この 4 スキーマのどれかで必ず外れる。
見出し行の位置すら固定できない。

### 5.2 Word — 構造化されていない地の文

見出しと段落で書かれた解説であり、表を持つものは 1 本だけだった。
段落数は 26〜53。使われている段落スタイルも文書ごとに違う（見出しレベルの使い方が
揃っておらず、囲み枠用の独自スタイルを持つものもある）。

**Excel と違い、抽出すべき項目に対応する枠が存在しない。**

### 5.3 配点との関係

Issue #95 決定 3 は「添削資料は任意だが強く推奨」である。§3.4 のとおり、**目視した範囲では
配点は採点基準 PDF 側にあった**ので、「配点のために添削資料が必須になる」という当初の懸念は
確認できなかった。ただし**目視していない教科があるため、断定はしない。**

添削資料が持っていて採点基準 PDF が持っていない情報は、**誤答パターンと、それに対する
赤入れ（コメント）の文例**である。これは精度に効くが、配点のような必須項目ではない。

### 5.4 Excel から誤答カタログを読み取った結果（Issue #106）

§5.1 の 4 スキーマに対し、**列の位置でも列名の一致でもなく、列名に含まれる語（役割マーカー）で
列を割り当て、見出し行はシート上部を探索する**読み取りを実装した
（`backend/src/auto_scoring/domain/error_catalog.py` と
`backend/src/auto_scoring/adapters/excel_error_catalog.py`）。

#### 実測（2026-09-10、リポジトリ外の実資料に対して実行。内容は載せない）

分母から書く。`01_*` を持つ第 2 階層ディレクトリ = **11 教科**。

| 母数                                       | 数            |
| ------------------------------------------ | ------------- |
| 教科（`01_*` を持つディレクトリ）          | **11**        |
| Excel の添削資料を持つ教科                 | **7**         |
| Word の添削資料を持つ教科                  | **6**         |
| Excel のみ / Word のみ / 両方              | 5 / **4** / 2 |
| `03*` の拡張子: `.xls` / `.xlsx` / `.docx` | 6 / 1 / 6     |

| 読み取り結果                             | 数        |
| ---------------------------------------- | --------- |
| 読めた Excel 教科                        | **7 / 7** |
| 読み取れた行（誤答パターン 1 件 = 1 行） | **27**    |
| 1 ファイルあたりの行数                   | 2〜6      |
| 解釈できなかったシート                   | **0**     |

列ごとの充足（27 行中）:

| 列              | 埋まっていた行 | 埋まっていた教科 |
| --------------- | -------------- | ---------------- |
| 誤答パターン    | 27             | 7 / 7            |
| 赤入れ案        | 27             | 7 / 7            |
| 問題番号 / 回数 | 27             | 7 / 7            |
| **減点量**      | **17**         | **4 / 7**        |

**減点量は 7 教科中 3 教科で得られない。** 内訳は「列そのものが無い」1 教科（§5.1 のスキーマ 4）と
「列はあるが全行が空」2 教科である。Issue #106 の目標は
「誤答パターン → 減点量 → 赤入れ案」だが、**実資料では 3 本目のうち減点量だけが半分強しか無い。**
無い減点量は `None` として持ち、0 にも「減点なし」にも変換しない。

#### 読めなかったことを空の結果にしない

列構成が想定と違うファイルは、**空のカタログではなく
`ErrorCatalogUnreadable` として返る**（理由は「見出し行が見つからない」「見出しはあるがデータ行が
無い」「シートが無い」の 3 種）。「このファイルの列が分からない」と「この資料には誤答の記録が無い」は
登録者にとって全く別の話であり、後者に化けさせない。採点ジョブ側はこれを警告ログに落として採点を
続ける（添削資料は任意入力・業務ルール §2 (18)）。**画面へ出すのは Issue #209。**

#### Word（`.docx`）は Issue #106 の対象外 — その代償

最高責任者の決定（2026-09-10）。§5.2 のとおり非定型の散文で表構造が無く、**抽出の正確さを
検証する手段が無い**ため。黙って落としてはいない。代償は次のとおり。

- **Word のみを持つ 4 教科では、誤答カタログが 1 件も得られない。**
  採点は通る（添削資料は任意）が、コメント生成に効く材料がその 4 教科ではゼロになる。
- 両方を持つ 2 教科は Excel 側だけで足りる可能性があるが、**未検証**である。

扱いをどう決めるかは **Issue #208**（以下 §5.5〜§5.7）。

### 5.5 誤答カタログの生成経路は「元資料に検証可能な構造があるか」で選ぶ（Issue #208）

同じ「誤答カタログ」に **2 系統の生成経路**がある。これは恣意的な不統一ではない。
**元資料に、機械が一意に読み取れて、読み違いを機械自身が検出できる構造があるかどうか**で
一意に決まる。

| 元資料                 | 機械が扱える構造                                                                 | 読み違えの検出                           | 経路                             |
| ---------------------- | -------------------------------------------------------------------------------- | ---------------------------------------- | -------------------------------- |
| Excel の添削資料       | 列と行の格子がある                                                               | 見出し行・必須列の有無で機械が検出できる | **決定的読み取り**（Issue #106） |
| Word の添削資料        | **無い**（非定型の散文。段落 26〜53、表は 1 本だけ、段落スタイルも不統一。§5.2） | **機械には検出できない**                 | **LLM 経路**（簡易設計書 §4.3）  |
| PDF の添削資料（将来） | 形式名では決めない。**その PDF の抽出テキストが格子として一意に読めるか**        | 読み順が壊れる例が実在する（§3.1）       | 読めれば決定的、読めなければ LLM |

**判定に使うのはファイル拡張子ではない。「表に見えるか」でもない。**
**「機械が一意に読み取れ、かつ読み違えを機械自身が検出できるか」**である。
拡張子で経路を決めると、表を持つ Word や表を持つ PDF で説明がつかなくなる。

**人手転記は採らない。** Word のみを持つ 4 教科ぶんを毎回手で写す運用は現実的でない。
LLM 経路にはコストと非再現性の代償がある（簡易設計書 §4.3.3）が、それは
**人の確認を必須の関門にすることで受け止める**（§5.6）。

> **次に新しい形式が出たときの判断手順**: (1) 機械が一意に読めるか、(2) 読み違えを機械が
> 検出できるか、を順に問う。両方満たせば決定的読み取り、どちらか欠ければ LLM 経路。
> **形式ごとの parser を新しく書くのは、この規則に反するときだけである**
> （簡易設計書 §4.3.1）。この規則自体は簡易設計書 §4.3.4 にも書いた。

### 5.6 LLM 経路の正確さは機械で検証しない — 人を関門にし、訂正率を測る（Issue #208）

**正解データが無いので、LLM 抽出の正しさを自動検証することはできない。**
Excel と違い Word には機械が照合できる格子が無い（§5.5）。「自動で検証できる」と書けば
嘘になる。代わりに次の 3 つを採る。

**(1) 人の確認を必須の関門にする。**
LLM が出した誤答カタログは、**人が確認・編集するまで採点のコメント生成に使わない。**
人の確認を経ずに LLM の出力が採点プロンプトに載る経路を作らない。
これを実現するのが Issue #209（誤答カタログを人が確認・編集できるようにする — API と画面・
永続化）である。

> **#209 は Word 対応の付随作業ではなく前提条件である。**
> **#208 の実装は #209 が無いと完成しない。** Word 対応を「Excel と同じく読み取りだけ先に
> 入れておく」ことはできない。読み取り結果を人が見て確定できる画面・API・永続化（#209）が
> 揃うまで、LLM 経路の出力をコメント生成の入力にしてはならない。

**(2) 訂正率を記録する。**
人が何件直したかを数えられるようにする。これが唯一の「正確さ」の指標である。
**AI の提案をスナップショットとして保存し、人が確定した結果と別に持つ**
（簡易設計書 §35-5「AI結果と人間の最終結果を分離して保持する」と同じ）。
LLM 抽出は同じ入力から同じ結果を返さない（簡易設計書 §4.3.3）ので、
**後から遡って数え直すことはできない。最初から数えられる形にしておく。**
記録するのは件数:

| 記録項目       | 定義                       |
| -------------- | -------------------------- |
| AI 提案件数    | LLM が出したカタログ行の数 |
| 無修正採用件数 | そのまま確定した行         |
| 修正件数       | 人が内容を変えた行         |
| 削除件数       | 人が採用しなかった行       |
| 追加件数       | 人が新しく足した行         |

訂正率は上の生カウントから導出する（例: `(修正 + 削除 + 追加) / (AI 提案 + 追加)`）。
**比率だけでなく生カウントを残す**（後から定義を変えても作り直せるように）。
保存先と API は #209。

**(3) 技術検証として扱う。**
`AGENTS.md`「技術検証と製品機能を区別する」に従い、**再現コマンド・期待結果・実際の結果・
決定・撤去または昇格の条件**の 5 点を記録する（次節 §5.7 と同じ形式）。
実資料 4 教科で LLM 抽出を試すときも、**件数と訂正率だけ**を記録し、
設問文・解答文・赤入れの文言は記録しない（§0.2）。
**#209 の画面が無い現時点では訂正率を実測できない**（人が数える道具が無いため）。
#209 の実装後に実資料 4 教科で実測する。

### 5.7 依存を足さない — 標準ライブラリで段落テキストが取れる（技術検証・Issue #208）

`.docx` は XML を集めた zip である。LLM 経路に渡すのは整形済みのプレーンテキストなので、
書式・スタイル・画像の解釈は要らない。**標準ライブラリの `zipfile` と `xml.etree` で
`word/document.xml` の `w:p`（段落）を走査し、`w:t` の文字を連結すれば段落テキストが取れる。**
`AGENTS.md` は「既存コード・標準ライブラリ・既存依存で満たせないときだけ依存を足す」と
定めているので、まずこれを実測した。

#### 検証の 5 点

- **再現コマンド**: `.docx` を zip として開き、`word/document.xml` を
  `xml.etree.ElementTree` で解析し、`w:p` ごとに配下の `w:t` のテキストを連結する。
  実資料と同じく**リポジトリ外**に置いた短いスクリプト（`/home/hikaru/scratchpad/` 配下）で実行した。
  同等の走査は `python3 -c` の一行でも書ける。**実資料はリポジトリに入れない**（§0.2）。
- **期待結果**: Word のみを持つ 4 教科すべてで段落テキストが取れる。`python-docx` は不要。
- **実際の結果**（2026-09-11、リポジトリ外の実資料に対して実行。**件数のみ**）:

| 項目                                                   | 値                                        |
| ------------------------------------------------------ | ----------------------------------------- |
| 対象                                                   | Word のみを持つ 4 教科の `.docx` **4 本** |
| 読めたファイル                                         | **4 / 4**                                 |
| 読めなかったファイル                                   | **0**                                     |
| 段落（すべての `w:p`）                                 | 236                                       |
| うち空でない段落                                       | 170（1 本あたり 36〜53、平均 42.5）       |
| 表（`w:tbl`）                                          | 1                                         |
| テキストボックス内の段落（`w:txbxContent`）            | **0**                                     |
| 埋め込みオブジェクト（`word/embeddings/`・`w:object`） | **0**                                     |
| 画像（`w:drawing` / `word/media/`）                    | 11 要素 / 3 部品                          |
| ヘッダ / フッタ                                        | 0 / 2 部品（フッタの文字は各 1 文字）     |

「読めなかったファイル数と理由の分類」（埋め込みオブジェクト・テキストボックス等）は
**0 件**だったので、分類は生じていない。参考として Word と Excel を両方持つ 2 教科の
`.docx` 2 本も同じ方法で読め、合計 68 段落（うち空でない 56）だった。

- **決定**: **`python-docx` を足さない。標準ライブラリで足りる。** 読み取りコードは実装 Issue で
  `adapters`（`zipfile` / `xml.etree` を使う層）に置き、`domain` にはテキストを渡す
  （`AGENTS.md` の依存方向）。
- **撤去または昇格の条件**:
  - **昇格**: Word の読み取りを実装する Issue で、この走査を製品コード（`adapters`）へ移し、
    実資料をリポジトリに持ち込まずにテストできる形にする。プローブ自体はリポジトリに入れない。
  - **撤去**: 実装後、プローブは削除する。
  - **再検討（依存追加を提案してよい条件）**: 次の資料で、カタログ本文が
    **テキストボックス・埋め込みオブジェクト・画像内の文字**にしか無いことが実測された場合。
    今回の 4 教科ではいずれも **0 件**だったので、今は足さない。
    なお `python-docx` を足してもテキストボックス・埋め込みオブジェクト・画像内文字の解釈は
    解決しない（`python-docx` の守備範囲を超える）。その場合の提案は「依存追加」ではなく、
    **LLM にページ画像を渡す**等の別経路になる。

**画像・図表は取れないが、今は問題にならない。** 段落テキストが取れればカタログ本文は
LLM に渡せる。画像の中に文字が焼き込まれている場合は取れないが、今回の 4 教科では
カタログ本文は段落側にあった（テキストボックス 0・埋め込み 0）。

> **補足: `.doc`（旧バイナリ）は今回の対象に無かった。** `03*` の Word はすべて `.docx`
> だった（§5.4 の拡張子内訳）。`.doc` は zip ではないのでこの方法では読めない。
> 将来 `.doc` が来た場合は別の判断が要る（§0.1）。

## 6. 添削サンプル（添削済み答案の見本）

目視した 3 教科は、いずれも**赤ペンによる手書き**（またはそれを模した注釈）だった。
実際に使われていた表現は、Issue #95 決定 4 が MVP 対象とする
「ボックス・下線・テキスト」より**広い。**

観測されたもの:

| 種別                   | 観測内容                                                                 |
| ---------------------- | ------------------------------------------------------------------------ |
| テキスト               | 数行にわたる説明。**縦書きの答案では注釈も縦書き**                       |
| 下線                   | 直線のほか、**波線**・**破線**                                           |
| 囲み                   | 矩形、角丸の吹き出し                                                     |
| **矢印**               | 直線・曲線・ループ・双方向。**注釈と対象箇所を結ぶ主要な手段**           |
| **括弧類**             | `( )` `{ }` `[ ]` などを answer 上に重ねて、語のまとまりを示す           |
| 参照記号               | 小さな囲み記号（※1 等）を対象箇所と注釈ブロックの両方に置いて対応づける  |
| 記号                   | ○ / × / △ / チェック相当                                                 |
| **インラインの加減点** | 対象箇所の脇に `(+3)` `(-1)` のような**部分ごとの点の増減**              |
| 訂正                   | 誤った文字の脇に正しい文字を書く（置換）                                 |
| **手描きの図**         | ある教科では、注釈のほぼ全体が**手描きのグラフ**（軸・曲線・点・ラベル） |

**設計上の含意**: 決定 4 が「図形は将来」としたことで、**手描きの図が注釈の主体である教科は
MVP では再現できない。** これは想定される制約として明記すべきものであり、
[簡易設計書](./simplified-design-specification.md) §11 に記録した。

また、注釈と対象箇所の結びつけを**矢印**に頼れない以上、**参照記号（※1 …）による対応づけ**が
その代替になる。決定 4 の「ボックス・下線・テキスト」だけで実運用に近づけるには、
この参照記号の仕組みが要る。

## 7. 付属のデジタル添削手順書

配布物には、**現在この塾が実際に行っている添削手順**の手順書が同梱されている。
アプリが置き換えようとしている作業そのものなので、構造を記録しておく。

- 添削は **PDF 注釈ツール上の手作業**である（一般的な PDF リーダー、タブレット、
  OS 標準のプレビューアプリ、それぞれ向けの手順書がある）
- 手順書は「主にテキストボックスと、直線・長方形の描画を使う」と説明している
- 答案を**紙で受け取ってスキャンする**手順書が別にある（スキャンアプリの案内付き）。
  §4 で答案がすべてスキャン画像だったことと整合する

### 7.1 定型オブジェクト集

手順書には、**あらかじめ用意された添削オブジェクトを集めた PDF** が付属する。
講師はここからコピーして答案に貼る。**ファイルは横書き版と縦書き版の 2 本ある**（ファイル名による）。
**目視したのは横書き版 1 枚だけ**だが、**その 1 枚の中に横書き用と縦書き用の両方の
オブジェクトが並んでいた**（以下の列挙はこの 1 枚に基づく。縦書き版のファイルは開いていない）。

収録されているオブジェクトの種類（§6 で実際に使われていたものと対応する）:

- テキスト（**文字サイズ違いで 2 種類**用意されている）
- 参照用の囲み記号と、それを組み合わせた各種パターン
- **他ページへの参照文**（「続きの解説は N ページ参照」「下記に続く」「N ページ 問 N の続き」）
  — **注釈が 1 ページに収まらないことが前提になっている**
- 観点タグ（【文構造】【内容】【構成】【語数】のような分類ラベル）
- 加減点の表記（`(-1)` や「減点なし」を含む）
- 称賛スタンプ
- 下線（実線・破線）
- **白い矩形**（用途が「解答欄の罫線などを消せる」と明記されている。
  **描画ではなく下地を隠すためのオブジェクト**）
- 矢印（曲線・ループ・双方向など多数）
- 括弧類（多数）
- 講評欄・氏名欄・得点欄のプレースホルダ
- **ページを追加したときに、元のフッタのページ数表記の上に貼り替えるオブジェクト**

最後の項目と、白紙ページを追加するための PDF が同梱されていることから、
**添削の過程でページを増やす運用が正式に想定されている**と分かる（§4.5 の `m` の不一致と整合）。

**設計上の含意**: この定型オブジェクト集は、**塾自身による「必要な添削表現」の答え**である。
Annotation の種別を将来拡張するとき、推測ではなくこれを参照すること。
