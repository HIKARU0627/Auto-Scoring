# 配点と採点基準の抽出（Issue #103）

テストを登録しても、**設問ごとの配点と採点基準が無ければ採点は始まらない。**
このドキュメントは、それをどこから・どうやって取り、誰が確定するかを記録する。

関連: [`test-registration.md`](./test-registration.md) /
[`ai-grading-pipeline.md`](./ai-grading-pipeline.md) /
[`simplified-design-specification.md`](./simplified-design-specification.md) §6・§9

---

## 1. なぜ正規表現ではなく画像 + LLM なのか

これは好みではなく、実資料 11 教科の採点基準 PDF を計測した結果である
（内容は載せない。数値と構造のみ）。

|                             | 教科数 |
| --------------------------- | ------ |
| テキスト層あり              | 5      |
| **抽出 0 文字（画像のみ）** | **6**  |

**画像のみの 6 教科に、数式を扱う教科がまるごと含まれる。**
さらに、テキスト層のある教科でも構造の目印が揃っていない:

- 【解答】【解説】の見出しが**無い**教科がある（減点方式で書かれている）
- `問N` の番号が**無い**教科がある
- `N点` の出現数は 3〜39 と大きく開く

したがって:

- **ページ画像を主入力にする。** 「テキストを試して駄目なら画像」という分岐は作らない。
  その分岐は、テキスト経路がいちばん弱い 5 教科でテキストを選び、
  画像しか無い 6 教科でだけ画像を選ぶ、という逆の選択になる
- **決まった目印に依存するパーサを主機構にしない**（#95 の方針転換に一致）
- テキスト層は、**あれば補助として同じ 1 回の呼び出しに添える**だけ

将来の資料が同じ形とは限らない。ここに書けるのは**計測した 11 教科の範囲**である。

## 2. 経路

```
採点基準PDF
  → 全ページを PNG 化（pdfium, scale 2.0）＋ テキスト層があれば添える
  → 1 教科 = 1 回の呼び出し（画像を全ページ分まとめて渡す）
  → structured output で CriteriaExtractionOutput を強制
  → 崩れていれば SchemaViolation（502）。**何も保存しない**
  → CriteriaDraft（提案）として app-data/tests/<id>/criteria.json に保存
  → 人が画面で編集・確定
  → Question / Rubric 行になる
```

| 層                               | モジュール                                                           |
| -------------------------------- | -------------------------------------------------------------------- |
| スキーマ・ドラフト・集計・ポート | `backend/src/auto_scoring/domain/criteria_extraction.py`             |
| ページ描画と入力の組み立て       | `backend/src/auto_scoring/adapters/criteria_extraction/source.py`    |
| プロンプトと strict JSON Schema  | `backend/src/auto_scoring/adapters/criteria_extraction/_prompt.py`   |
| Vertex Gemini / OpenAI 互換      | `backend/src/auto_scoring/adapters/criteria_extraction/extractor.py` |
| provider の選択                  | `backend/src/auto_scoring/adapters/criteria_extraction/factory.py`   |
| 保存                             | `backend/src/auto_scoring/adapters/local/criteria_store.py`          |
| HTTP                             | `backend/src/auto_scoring/api/criteria_router.py`                    |
| 画面                             | `app/lib/features/test_registration/test_settings_page.dart`         |

### provider

**新しい設定変数は増やしていない。** 採点と同じ
`AUTO_SCORING_AI_GRADING_TRANSPORT` の優先順位を読み、
**画像入力を持つ transport（`gemini` / `openrouter` / `openai`）の先頭 1 つ**を使う。

- `codex_app_server` は画像入力が無いため対象外。連鎖に残すと毎回 1 回無駄に失敗する
- **fallback 連鎖は組まない。** 抽出は人が押して結果を見る 1 回きりの操作で、
  失敗は画面に出て押し直せる。無人で走る採点ジョブとは条件が違う
- 未設定なら 503 と、**設定値を含まない**理由文を返す

### ページ数の上限

1 回に読めるのは **30 ページ**まで。超えたら**明示的にエラー**にする。
実資料は最大 8 ページ（11 教科で計 40 ページ）なので余裕がある。
先頭だけ送って残りを黙って捨てることはしない。

## 3. 「不明」は 0 ではない

**配点は点数である。間違ったまま通ると、その設問の全答案が静かに誤って採点される。**
そのため、この機能のすべての points 型は `int | None` で、`None` は
**「読み取れなかった」**を意味する。0 でも 1 でもない。

- 画面には `配点: 不明` と出す。合計の横に**必ず不明件数を並べる**
  （不明を含む一覧の横に合計だけを出すと、それが満点だと読める）
- **不明が 1 件でも残っていると確定できない。** サーバ側 `ensure_confirmable` が 422 を返し、
  画面側もボタンを無効にして理由を出す
- 抽出が 0 件でも**落とさない**。「抽出は実行しましたが 0 件でした」と
  「まだ抽出していません」を**別の文言**で示す
- 読めなかったページ（`unreadable_pages`）と AI 自身の申し送り（`note`）も画面に出す

崩れた LLM 応答は `SchemaViolation` になり、**ドラフトは 1 件も保存されない**
（PR #100 で確立した規律）。部分的に読めた配点を画面に出すと、
本当に読めたものと見分けがつかなくなる。

## 4. 合計点と総得点の照合（#95 決定 5・案 A）

- 設問ごとの配点の合計は**アプリが算出**する
- 採点基準 PDF に総得点（満点）が書かれていれば、合計と**照合して差を示す**。
  差がある = 抽出漏れの手がかり
- **不明が残っている間は差を出さない。** その差は未入力で既に説明がついており、
  存在しない 2 つめの原因を探させることになる
- **四角囲みの `得点/満点` は総得点、フッタの `(k/m)` はページ番号。**
  後者を総得点として拾わないことをプロンプトで明示し、合成 fixture でテストに固定した

画面側は**編集中の値から毎回計算し直す**（`app/lib/core/criteria_totals.dart`）。
サーバの `totals` は保存済みの一覧に対する値なので、保存前の編集があると
**もう画面に無いリスト**の合計を出すことになる。
同じ画面の設問依存グラフが同じ理由で同じことをしている。

## 5. 画面（受入条件 7）

テスト設定画面（`/tests/:testId/settings`）の**中に節を足した。画面は 1 つのまま**。

```
テストプロファイル（設問・回答欄・添削記号領域の位置）   ← 座標だけ
配点と採点基準                                        ← 配点・基準・模範解答
設問依存関係グラフ
登録完了 ＋ 「まだ残っていること」
```

### 配点の入力口を 1 つに絞った

Issue #103 以前は、配点を `SCORE` 領域のテキストに書き、正規表現で読んでいた。
いまは**「配点と採点基準」節だけが配点の入力口**である。

- 領域編集ダイアログの種類から `配点`・`採点基準`・`模範解答` を**外した**。
  新しく作れない
- 自動解析が過去に作った `SCORE`/`RUBRIC`/`MODEL_ANSWER` 領域は**残り、
  ドラフトが無いときの後方互換 fallback として読まれる**
  （Issue #103 以前に登録されたテストのため）。ただし画面からは編集できない
- `app/test/test_settings_page_test.dart` が両方を固定している

**入力口が 2 つあること自体が事故の原因**である。どちらが効いているのか、
利用者にも実装にも分からなくなる。

### 抽出しなくても先に進める（#95 決定 8）

「設問を手で追加」は**抽出を一度も実行していなくても、失敗していても押せる**。
`PUT /tests/{id}/criteria` はドラフトが無ければ作る。
抽出が動かない教科でも、全項目を手で入れて確定できる。

## 6. Question / Rubric になるまで

`domain/test_registration.build_questions_and_rubrics` が**唯一の合流点**で、
領域とドラフトの両方を受け取る。

| 項目              | どこから                                                    |
| ----------------- | ----------------------------------------------------------- |
| 設問の存在        | `QUESTION` 領域のラベル **∪** ドラフトの設問番号            |
| `points`          | ドラフトにあればドラフト。無ければ `SCORE` 領域（後方互換） |
| `Rubric.criteria` | ドラフトにあればドラフト。無ければ `RUBRIC` 領域の全文 1 件 |
| `model_answer`    | ドラフトにあればドラフト。無ければ `MODEL_ANSWER` 領域      |
| `page` / 各 area  | 領域のみ（ドラフトは座標を持たない）                        |

`criteria=None` のときの挙動は Issue #103 以前と**同一**である。

### 確定の順序に依存しない

`/profile/confirm` と `/criteria/confirm` は**どちらも同じ関数を呼び、
確定済みの両方を読む**。だから、回答欄を先に確定しても配点を先に確定しても
同じ Question 行になる。両者は `api/test_artifact_lock.py` の
**同じロック**を取る（別々のロックだと、片方が読んだ後・書く前にもう片方が
コミットして、確定した配点が消える）。

**未確定のドラフトは読まない。** 誰も確認していない提案が
`Question.points` になってしまうと、不明の関門を素通りする。

### 座標が無い設問

ドラフトにしか無い設問は `page=1`・area なしになる。これは**エラーにしない**。
`adapters/submission_intake.py` がその設問を `no_answer_area_defined` として
**要確認に回す**ので、推測した座標で切り出すより正直である。

### 加点方式と減点方式

- 全部が減点の設問 → `ScoringMethod.SUBTRACTIVE`。採点プロンプトに方式が載る
- 加点と減点が混ざる設問 → 方式は `ADDITIVE` のまま、
  減点の行だけ文言に `減点: ` を付ける。**落とさない**
  （減点を加点として読むと点が逆になる）

## 7. 実資料での確認

11 教科の採点基準 PDF すべてに対して、Vertex AI Gemini でローカルに実行した
（2026-09-09）。**内容は載せない。件数のみ。**

```
subjects                  : 11
crashed                   : 0
schema violations         : 0
provider unavailable      : 0
questions extracted (sum) : 51
points unknown (sum)      : 0
subjects with a total     : 1
image-only subjects that produced questions: 6   (= 画像のみの 6 教科すべて)

per-subject: 1〜8 ページ / 1〜11 設問 / 7〜53 秒
```

**この数字の読み方を間違えないこと。**

- **「配点不明 0 件」は精度ではない。** モデルが 51 設問すべてに数値を返した、という
  ことでしかない。**その数値が正しいかは測っていない。** 実資料には正解ラベルが無く、
  Issue #35 で「現有データでは定量評価の受入条件を満たせない」と既に記録されている。
  確かめたのは「**落ちないこと**」と「**読めなかった箇所が分かること**」である。
  人の確認を必須にしてあるのは、まさにこれが測れないからである。
- **したがって「不明」の経路は、実資料では 1 度も通っていない。**
  固定しているのは合成 fixture のテストだけである。
- **総得点を明示していた教科は 11 中 1 教科**だった。§4 の照合は、この資料では
  大半の教科で効かない。

### この実行で見つかり、直したこと

実資料に当てるまで分からなかった不具合が 2 件あった。どちらも合成 fixture では
再現しない種類のものである。

1. **Vertex AI がスキーマを受け付けなかった（11 教科すべてで 400）。**
   `responseJsonSchema` は復号制約にコンパイルされ、数値の min/max・文字数上限・
   配列長で大きくなりすぎると `INVALID_ARGUMENT` になる。**値の制約をワイヤ上の
   スキーマから外した**（`_prompt._VALUE_CONSTRAINT_KEYWORDS`）。値の検証は
   もともとローカルの `parse_criteria_extraction` が行っており、そこは緩めていない。
2. **設問番号の重複で落ちた。** 節ごとに番号が振り直される文書で、モデルが `問1` を
   複数回そのまま報告した。落とさず・混ぜず、番号に接尾辞を付けて注記する
   （`_unique_number`）。

## 8. やっていないこと

**黙って落としたのではなく、意図的に範囲外にした。**

| 項目                                                   | なぜ                                                                                                                                       | どうする                     |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------- |
| **添削資料（Excel）の 誤答パターン → 減点 → 赤入れ案** | `.xls` と `.xlsx` が混在し、新規依存が 2 つ（`openpyxl` + `xlrd`）要る。効くのは**コメント生成**で、「採点が通る」の臨界経路に乗っていない | 別 Issue                     |
| **添削資料（Word）の非定型散文**                       | 構造が無く、同じ出力スキーマに落とす前段が別物                                                                                             | 別 Issue（#95 の未解決論点） |
| **抽出精度の定量評価**                                 | 正解ラベルが無い（#35 に記録済み）                                                                                                         | データが揃ってから           |
| **確定した配点の再編集**                               | 採点済みの答案を黙って再採点することになる                                                                                                 | 現状はテストを作り直す       |

### 採点はまだ始まらない

**配点を確定しても、それだけでは `ready` にならない。** 必要なのは 3 つ:

1. 取込（Issue #101）
2. **配点と採点基準（この Issue）**
3. **回答欄の検出**（#95 決定 2）— **未実装**

`complete-registration` はテストプロファイルの確定を必須にしており、
この Issue はその関門を**触っていない**。開けてしまうと、回答欄が無いまま
採点が走って全問が要確認に落ちる——「動いているように見えて動かない」状態になる。

いまの逃げ道は、テスト設定画面で**回答欄を手で引いて確定する**こと。
画面はこれを「まだ残っていること」として明示する
（`_buildRemainingWork`、`test_settings_page_test.dart` が固定）。

## 9. 実資料の扱い

**provider へ送ってよい（#95 決定 7・案 B）。公開してよいわけではない。**

- 送信内容と応答を**ログ・例外メッセージに残さない**。
  アダプタの例外は HTTP ステータスコードと例外型名だけを運ぶ
  （`test_criteria_extractor_adapters.py` が固定している）
- テストの fixture は**すべて合成**。実資料は 1 バイトもリポジトリに入れない
- OpenAI には `store: false`、OpenRouter には ZDR ルーティングを**毎回**付ける
