# PoC 5: 別々にスキャンされた同一様式のずれ（Issue #130）

GitHub Issue [#130](https://github.com/HIKARU0627/Auto-Scoring/issues/130)（親
[#3](https://github.com/HIKARU0627/Auto-Scoring/issues/3)）。回答欄を**検出する紙**と
**切り出す紙**は別々にスキャンされた別文書である。その系統誤差を、直す前に**測る**ための
技術プローブ。`AGENTS.md` «Verification» の 5 点（再現コマンド・期待・実際・決定・撤去/昇格
条件）で構成する。

## 結論（先に）

- **ずれは起きる。** 同一様式を別々にスキャンした紙の間で、印刷罫線の位置は
  ページ幅で **中央値 0.0074・最大 0.0154**（横方向）、ページ高で **中央値 0.0153・最大
  0.0337**（縦方向）動く。**「ずれない」ではない。**
- **ただし、これだけでは切り出しは列から外れない。** Issue #122 が実測した回答欄の幅
  0.048 に対し、横方向の最大 0.0154 は **列幅の 32%**、半幅 0.024 より小さい。**切り出しの
  中心は列の中に留まる。** 同じ紙でモデルの座標が最大 0.181 外していた（Issue #122）のと
  比べて**一桁小さい**。
- **したがって位置合わせは実装しない。** 理由は「小さいから」だけではない。位置合わせを
  駆動する罫線対応づけが、実資料の **60 軸中 30 軸（50%）で数値を出せなかった**——19 軸は
  そもそも当てはまらず、**10 軸は両立しない 2 通りに読めた**。当てはまらない紙に変換を
  当てれば、**ページ上の全部の枠がまとめて動く**。今の受け皿（空白切り出しの tripwire と
  採点画面の切り出し表示）が拾えるのは 1 枠の失敗であって、全枠の同時失敗ではない。
- **将来やるなら傾き補正から。** 横方向の最大 0.0154 のうち **0.0116 は回転由来**で、
  最大の単独寄与である。しかも回転は罫線の対応づけを必要とせず、**測れなかったページが
  1 枚も無い**（60 軸すべてで角度が出た）。→ [§ 決定](#決定)

## 何を測ったのか

「検出する紙」と「切り出す紙」が別文書であるとは、実際には次を意味する:

- 検出は 参照答案 PDF に対して行い、罫線もその画像から測る
  （`api/test_registration_router.py`、`adapters.image.ink.measure_page_ruling`）。
- 切り出しは**別の生徒の**答案 PDF に対して、確定した正規化座標をそのまま当てる
  （`adapters/submission_intake.py`）。**切り出し側で罫線に合わせ直してはいない。**

したがって測るべきは「**同一様式の紙を別々にスキャンした 2 枚の間で、印刷罫線がどれだけ
動くか**」である。実資料には同一様式の添削サンプルが複数ある教科があり、それらは
まさに「同じ印刷物を別々にスキャンした紙」なので、この差をそのまま測れる。

**傾き・平行移動・伸縮は分けて測る。** まとめて 1 個の「ずれ」にすると、どれを直せば
効くのかが数値から出てこない。

## 再現コマンド

```bash
# backend/ で実行する。

# 1. 計測器の校正（合成のみ・データ不要・どこでも走る）
uv run python poc/issue_130_scan_drift/report.py --self-test

# 2. 実資料に対する計測（パスは引数。リポジトリには埋め込まない）
uv run python poc/issue_130_scan_drift/report.py --data "<添削資料の置き場（リポジトリ外）>"

# 両方まとめて
uv run python poc/issue_130_scan_drift/report.py --self-test --data "<添削資料の置き場（リポジトリ外）>"
```

`--data` の下で、`--pattern`（既定 `04*.pdf`）に一致する PDF を 2 つ以上持つディレクトリが
1 つの「同一様式のまとまり」になる。**実資料はリポジトリ外**にあり、パスは引数でしか
渡らない（`AGENTS.md` «Security»）。出力は**数値と件数だけ**で、ページ画像も文字も、
ディレクトリ名すら出さない（`G01`, `G02`, … の安定ラベルに置き換える）。所要 8 秒。

## 期待した結果

Issue #130 起票時点の想定は「**数ミリのずれでも、切り出しが解答列から外れる**」だった。
A4 幅 210mm に対して回答欄の幅 0.048 は約 10mm なので、この想定は「**ずれが 0.024
（列の半幅、約 5mm）を超える紙がある**」という予測に当たる。

対照として、**ずれが起きないなら「起きないことを記録して閉じる」**でよい、が Issue の
明示的な指示だった。つまり期待値は両側に開いていた。

## 計測器の校正 — 先に定規を測る

**実測値を出す前に、この計測器自身の誤差を測った。** これが無いと「0.01 のずれ」が
紙の性質なのか測り方のノイズなのか区別できない。

既知の回転・伸縮・平行移動を合成罫線ページに掛け、復元誤差を見る。罫線の 2/3 を塗り潰し、
罫線でない長い線を 4 本足した「答案が書き込まれた紙」の形の場合も含める。

| 量       | 最大誤差（7 ケース）        |
| -------- | --------------------------- |
| 回転     | **0.020 度**                |
| 伸縮     | **0.00045**                 |
| 平行移動 | **0.00017**（ページ正規化） |

**実測値のいちばん小さい数字（0.0016）より 1 桁小さい。** 計測器としては足りている。

加えて、**別々の罫り方をしたページ同士は「測定不能」を返す**ことを確認している
（`--self-test` の最終行）。これが無いと「測れなかった件数」が意味を持たない
——何にでも当てはめてしまう計測器は、何も除外しない。

## 分母 — 自分で数えたもの

「同一様式が複数ある教科」が何教科・何ページあるかは、**渡された前提ではなく実ファイルから
数えた**。

| 数えたもの                               | 件数                   |
| ---------------------------------------- | ---------------------- |
| 同一様式のまとまり（ディレクトリ）       | **9**                  |
| その中の PDF 文書                        | **23**                 |
| 比較したページ対（同じページ番号どうし） | **30**                 |
| 軸ごとの当てはめ（対 × 2 軸）            | **60**                 |
| **数値が出た軸**                         | **30**（横 15・縦 15） |
| 少なくとも片方の軸が出たページ対         | 17                     |
| 数値が出たページ対が覆う異なるページ     | **7**                  |

**重複を 1 まとまり落としている。** ある教科の添削サンプルは、別の教科のものと
**バイト単位で同一のファイル**だった（資料に「課題は同じものになります」と書かれている
とおり）。両方数えれば同じ紙が 2 度分母に入り、独立した証拠のように見えてしまう。
SHA-256 が一致するまとまりは落としている。

数値が出なかった 30 軸の内訳:

| 出なかった理由                                      | 軸数   |
| --------------------------------------------------- | ------ |
| どの当てはめも罫線を十分に説明できない              | **19** |
| **両立しない 2 通りの当てはめが同じくらい説明する** | **10** |
| どちらかのページに印刷罫線が 4 本未満               | 1      |

**この 30 軸を「測れた」ことにしていない。** 特に 2 番目は重要で、同じ罫線の並びが
「左へ 0.04 動いた」とも「右へ 3% 伸びた」とも読める——**大きさではなく符号が違う**——
ページが実在した。片方を選んで報告すれば、数値は出るが嘘になる。

出なかった軸が偏っている理由も分かった。**横書き用の様式は横罫が 28〜37 本ある一方、
縦罫は 3〜7 本しかない**（逆に縦書き用は縦罫が 12〜23 本）。**各様式は、自分にとって
重要な軸の方に密な罫線を持っている**——縦書きの細い列（幅 0.048）を測るための縦罫は
足りている。

## 実際の結果

ページ正規化（x はページ幅、y はページ高。`NormalizedBBox` と同じ単位）。

| 量                      | n   | 中央値 | 90 パーセンタイル | 最大       | 最大 ÷ 0.048 |
| ----------------------- | --- | ------ | ----------------- | ---------- | ------------ |
| 回転（度）              | 17  | 0.27   | 0.52              | 0.94       | --           |
| ├ 回転由来のずれ, x     | 17  | 0.0033 | 0.0064            | 0.0116     | 0.24         |
| ├ 伸縮由来のずれ, x     | 15  | 0.0012 | 0.0027            | 0.0035     | 0.07         |
| ├ 平行移動由来のずれ, x | 15  | 0.0040 | 0.0074            | 0.0088     | 0.18         |
| ├ 説明できない残差, x   | 15  | 0.0030 | 0.0046            | 0.0048     | 0.10         |
| **└ 合計, x**           | 15  | 0.0074 | 0.0142            | **0.0154** | **0.32**     |
| ├ 回転由来のずれ, y     | 17  | 0.0017 | 0.0032            | 0.0058     | 0.12         |
| ├ 伸縮由来のずれ, y     | 15  | 0.0013 | 0.0021            | 0.0027     | 0.06         |
| ├ 平行移動由来のずれ, y | 15  | 0.0117 | 0.0186            | 0.0266     | 0.55         |
| ├ 説明できない残差, y   | 15  | 0.0027 | 0.0054            | 0.0056     | 0.12         |
| **└ 合計, y**           | 15  | 0.0153 | 0.0202            | **0.0337** | 0.70         |

「合計」は 3 つの最悪値の足し算ではなく、**回転・伸縮・平行移動を合成した変換をページの
四隅に当てた実際の移動量**。回転と平行移動は打ち消し合うこともあるので、足し算は紙の上に
存在しない数になる。

分けて測った結果、**原因の順位が軸ごとに違う**ことが分かった:

- **横方向（x）** — 最大を作っているのは**回転**（0.0116 / 0.0154）。平行移動は 0.0088 まで。
- **縦方向（y）** — 支配的なのは**平行移動**（中央値 0.0117、最大 0.0266）。紙送りの
  上端位置がスキャンごとに変わる。
- **伸縮はどちらの軸でも最小**（最大 0.0035）。**紙は伸びていない。** 正規化座標が
  ページ寸法と DPI を先に割り切っているので、残るのは紙そのものの伸縮だけであり、
  それは 0.4% 未満だった。

### 「たぶんずれる」を 2 回否定している

Issue #122 で司令塔の「一貫して右へ +0.035」が実測で否定された。本プローブでも同じことが
起きた。**自由に伸縮を探させると、実資料の 2 ページ対で 4〜5% の伸縮が出た。** 紙は
そんなに伸びない。原因は、様式のヘッダ罫が 0.013〜0.026 間隔の**梯子**になっていて、
梯子は 1 段ずれても罫線同士が合ってしまうこと——1 段ずれたヘッダと、ずれていない
ページ下端の罫を辻褄合わせすると 5% の伸縮になる。

**罫線が合った本数を最大化するだけでは、この間違いは検出できない。** 入れた歯止めは 2 つ:

1. **物理的な上限**（伸縮 1% 超は「2 回のスキャン」では起こり得ない）。
2. **一意性の検査** — 勝った当てはめと**大きく違う**当てはめが同じくらい罫線を説明するなら、
   その軸は測定不能として落とす。

一意性の閾値（勝者より何本少ないところまでを対抗馬とみなすか）を 0・1・2 と振ったときの
感度:

| 閾値                 | 測れた軸 | 合計 x 中央値 | 合計 x 最大 | 合計 y 中央値 | 合計 y 最大 |
| -------------------- | -------- | ------------- | ----------- | ------------- | ----------- |
| 勝者 − 0             | 16 / 18  | 0.0075        | **0.0453**  | 0.0159        | 0.0337      |
| **勝者 − 1（採用）** | 15 / 15  | 0.0074        | **0.0154**  | 0.0153        | 0.0337      |
| 勝者 − 2             | 14 / 8   | 0.0075        | 0.0154      | 0.0093        | 0.0211      |

**中央値はどれでも動かない（0.0074〜0.0075）。** 動くのは x の最大だけで、その 0.0453 は
**上で述べた「符号が違う 2 通りに読める」1 ページ対**である。閾値の好みではなく、
**そのページ対を目視で確認した上で**除いている。

## 決定

**位置合わせは実装しない。本 Issue はこの計測をもって閉じる。**

数値からの導出:

1. **ずれ単独では切り出しは外れない。** 横方向の最大 0.0154 は、回答欄の半幅
   0.024 より小さい。切り出し矩形の中心は列の中に留まり、列との重なりは最悪でも 68% 残る
   （中央値 0.0074 なら 85%）。Issue #130 本文の想定「数ミリのずれでも列から外れる」は
   **実測で成立しなかった**。
2. **主因は依然としてモデルの創作である。** Issue #122 の実測では最大 0.181。
   本プローブの最大 0.0154 は**その 1/12** で、優先順位は変わらない。
3. **位置合わせを入れる方が危険になりうる。** 位置合わせに要る罫線の対応づけは、
   実資料の **60 軸中 30 軸で数値にならなかった**（19 軸は当てはまらず、10 軸は
   両立しない 2 通りに読めた）。当てはまらない紙に変換を当てると
   **ページ上の全部の枠が同時に動く**。今ある受け皿——空白切り出しの tripwire
   （`domain.submission_intake.is_nearly_blank_crop`）と、採点画面での切り出し表示——は
   **1 枠の失敗を人に見せる**ためのもので、全枠が揃ってずれた画面は「そういう様式」に
   見えてしまう。**測れない紙に当てるくらいなら、当てない方がよい。**

**ずれが「無い」とは記録しない。** 0.0074（中央値）〜0.0154（最大）は、Issue #122 の
罫線スナップの許容幅 `SNAP_TOLERANCE = 0.015` と**同じ桁**である。将来スナップを
切り出し側にも持ち込むなら、**この 0.0154 を先に見ること**——検出した紙で罫線に乗せた枠が、
切り出す紙では同じ罫線から 0.0154 離れうる、つまり**許容幅の外に出うる**。

### 別 Issue に切り出すもの

| 何を                                                       | なぜ                                                                                                                                                                   |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 切り出し側の**傾き補正だけ**を入れるか検討する             | 横方向の最大 0.0154 のうち 0.0116 が回転由来。しかも角度は**罫線の対応づけを要さず、60 軸すべてで測れた**（誤差 0.020 度）。平行移動・伸縮と違って「測れない紙」が無い |
| スナップを切り出し側へ広げるなら `SNAP_TOLERANCE` を見直す | 実測のずれ 0.0154 が現在の 0.015 を超える                                                                                                                              |

**本 Issue では実装しない。** 起票は司令塔の判断に委ねる。

## 撤去または昇格の条件

| パス                                         | 扱い                                                                                                                                              |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `backend/poc/issue_130_scan_drift/drift.py`  | **保持。** 上の数値の再現に要る。製品コードからは参照しない。`--self-test` は実資料なしで走るので、計測器が壊れていないことはいつでも確かめられる |
| `backend/poc/issue_130_scan_drift/report.py` | **保持。** 同上                                                                                                                                   |
| 本ドキュメント                               | **保持。** 「ずれは 0.0154 まで起こる」という実測の証跡                                                                                           |

- **撤去してよいのは**、切り出し側の位置合わせを実装する Issue が立ち、そこで同じ計測を
  回帰テストとして持ち直したとき。そのとき本プローブの 5 点はその Issue の doc へ移す。
- **昇格の候補は `drift._skew_degrees` ただ 1 つ。** 傾きは罫線の対応づけを要さず、全ページで
  測れ、誤差 0.020 度。上表の「傾き補正だけを入れるか検討する」Issue が立ったときに、
  `adapters/image/` へ移して回帰テストを付ける。
- **`drift._fit_axis`（平行移動・伸縮の当てはめ）は昇格しない。** 実資料の半分で一意に
  決まらないものを製品の経路に入れてはいけない。昇格の条件は「**実資料で一意に決まらない
  軸が無くなること**」であり、本プローブの実測はその逆を示している。

## スコープ外

- **本プローブは製品コードの振る舞いを変えていない。** `backend/src/` 配下は 1 行も
  触っていない（`adapters.image.ink.measure_page_ruling` を**読み取り専用で再利用**した）。
- 同一様式が 3 枚以上ある教科では全対を数えているので、**ページ対どうしは独立ではない**
  （同じ紙が複数の対に現れる）。中央値・最大の解釈にはこの重複が乗る。異なるページ数
  （7）も併記しているのはそのため。
- 実資料は 1 塾・1 スキャン運用の標本である。**別の塾・別のスキャナでこの数値が保つ保証は
  無い。** 保つかどうかは、その資料が手に入ったときに同じコマンドを回して確かめる。
