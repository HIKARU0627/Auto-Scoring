# 業務ルール・対象範囲・評価データ決定書

## 0. このドキュメントの位置づけ

[`simplified-design-specification.md`](./simplified-design-specification.md)（簡易設計書）
で「要判断」「決定する必要がある」とされていた**業務ルール・対象範囲・データ保持**の項目を、
MVP 0.1 の実装着手前に確定する（GitHub Issue #8 / 親 Issue #3）。

- 簡易設計書が仕様の正本。本書は簡易設計書 §27（データ保持）・§31（最初の MVP）・
  §33（未決定事項）の業務側項目を具体化するもので、両者が食い違う場合は本書を優先し、
  簡易設計書側も同じ PR で更新する。
- 技術要素（OCR サービス、AI モデル、PDF エンジン等）の最終選定は
  [`technology-stack.md`](./technology-stack.md) と各 PoC Issue の担当であり、本書では
  **業務ルールとして固定できる範囲**と**PoC 後に確定する項目の判断条件**のみを定める。
- 本書の「確定」は Issue #8 時点でユーザー（プロジェクトオーナー）が確認したもの。変更が
  必要になった場合は Issue #8 またはその後継 Issue で更新し、履歴を残す。
- §3 の判断事項 A（OCR サービス）・B（AI モデル）・C（低 Confidence 基準値）・
  E（並列 AI 処理数）は、2026-09-08 にオーナーが
  [Issue #81](https://github.com/HIKARU0627/Auto-Scoring/issues/81) で確定した。
  確定後も残る制約（特に C の「閾値による自動確定は実装しない」）は §3.1 に残してある。

### 0.1 用語

| 用語                   | 意味                                                                                       |
| ---------------------- | ------------------------------------------------------------------------------------------ |
| criterion              | 採点マニュアルから抽出した個々の採点観点。結果は `pass` / `partial` / `fail` の 3 値       |
| テストプロファイル     | 簡易設計書 §5。テスト単位で保持する設問・回答欄・配点・Annotation 配置領域・模範解答       |

| クラウド送信ペイロード | OCR / AI の外部クラウド API へ 1 設問の処理のために送信するデータ一式                      |

## 2. 実装前に確定する項目（確定）

以下は Issue #8 時点で確定。実装はこの表に従い、コード内で別解釈をしない。

### (1) 対象 OS（§33-1）

- **決定**: MVP 0.1 は **Windows のみ**。macOS / Linux は将来対応。UI・PDF・OCR/AI の
  各境界は抽象化を維持し、OS 依存コードを 1 箇所に閉じ込める。
- **出典**: 簡易設計書 §3、`technology-stack.md` §7-1。

### (2) 外部 AI / OCR クラウド API への答案送信（§33-4）

- **決定**: **可**。ただしクラウド送信ペイロードは **1 設問の処理に必要な最小限**に絞り、
  **生徒識別情報（氏名・生徒 ID・出席番号・学校名・答案ファイル名）を一切含めない**。
- 送信してよい: 当該設問の答案画像の切り出し（回答欄領域のみ）、OCR テキスト、問題文、
  模範解答、当該設問の採点基準・配点、依存が確定している場合の前提結果（§4.3）。
- 送信してはならない: ページ全体の画像（他設問・ヘッダの氏名欄を含むため）、生徒識別情報、
  同一答案の無関係な設問、テストプロファイル全体。
- **出典**: 簡易設計書 §26、`technology-stack.md` §0.2 / §7-4。

### (3) 答案 PDF のファイル構造（§33-5）

- **決定**: 全テスト共通の固定座標は前提にしない。テスト単位のテストプロファイル
  （簡易設計書 §5）で構造差を吸収する。実ファイル構造の多様性は **PoC 4** で検証する。
- MVP で受け付ける答案 PDF: **1 生徒 = 1 PDF ファイル**（次項）。ページ数は複数可。
- **出典**: 簡易設計書 §4.2 / §5 / §30 PoC 4。

### (4) 1 PDF あたりの生徒数と識別方法（§33-6）

- **決定**: MVP は **1 PDF = 1 生徒**に固定する。
- **生徒の識別方法**: 答案取込画面（簡易設計書 §16.4）で、**人間が各 PDF に生徒を手動で
  割り当てる**。ファイル名からの自動抽出は MVP では行わない（実装しても確定は人間）。
- 割り当て結果は内部の `submissionId` に紐づけて保持する。氏名等の扱いは (13) に従う。
- **MVP 対象外**: 1 PDF に複数生徒が連続する形式、ファイル名規則による一括自動割当。
- **出典**: 簡易設計書 §16.4 / §33-6。

### (5) 必要な添削記号 / Annotation（§33-7、簡易設計書 §11）

- **決定**: MVP で扱う Annotation 種別は次に固定する。

  | 種別        | 用途                   | 位置決定方法（簡易設計書 §12）                    |
  | ----------- | ---------------------- | ------------------------------------------------- |
  | ○ / × / △   | 設問・criterion の合否 | テストプロファイルの Annotation 配置領域（固定）  |
  | 点数        | 設問ごとの得点表示     | テストプロファイルの「点数配置領域」（固定、(7)） |
  | コメント    | 設問単位の指摘         | テストプロファイルのコメント配置候補領域          |
  | 下線 / 囲み | 答案中の特定箇所の指摘 | OCR の Bounding Box。特定できなければコメント退避 |

- **MVP 対象外の記号**: チェック、取り消し線。必要性が確認できれば後続 Issue で追加する
  （Annotation 種別は拡張可能な設計にしておく）。
- AI は座標を直接返さない。AI が返すのは対象語・種別・コメントまで（簡易設計書 §12.1）。
- **未確認の前提**: 実際の塾の添削ルールで上記以外の記号が必須と判明した場合は Issue #8
  後継で見直す。実装は上記固定セットで進めてよい。

### (6) コメントの記入ルール（§33-8）

- **決定**:
  - コメントは**設問単位**。答案本文の特定文字に対する指摘も、Bounding Box が取れないときは
    設問コメント領域へ退避する（簡易設計書 §12.4）。
  - 本文はプレーンテキスト（装飾なし）。1 コメントの上限を **全角 120 文字**とする。
  - 文面・語調・定型句は、テストごとの採点マニュアル PDF から抽出した「添削コメント規則」
    （簡易設計書 §4.1）に従う。マニュアルに規則がない場合は AI 生成の候補をそのまま出さず、
    人間が確定する。
  - AI が生成するのは**候補**のみ。確定は人間（(17) と同一方針）。

### (7) 点数の記入位置（§33-9）

- **決定**: 設問ごとの得点は、テストプロファイルに設問単位で持つ **「点数配置領域」**
  （0〜1 正規化座標）へ配置する。AI・アプリともに座標を推測で決めない。
- テスト登録時に人間が点数配置領域を確認・修正する（簡易設計書 §6.1 の確認対象に含める）。
- 合計点の記載要否・位置は MVP では扱わない（設問ごとの得点のみ）。

### (8) 採点方式（§33-10）

- **決定**: **加点式・減点式の両方に対応**する。どちらを使うかは**設問ごと**に、テストの
  採点マニュアル PDF の記載に従う（マニュアルが正）。
- 内部表現は「criterion ごとの結果 + 設問の最終得点」で統一し、加点／減点はマニュアル解釈時に
  吸収する。UI・DB は方式によらず同一スキーマ。

### (9) 部分点の扱い（§33-11）

- **決定**: 部分点を**対象とする**。
  - criterion 単位で `pass` / `partial` / `fail` を持つ（簡易設計書 §9.2）。
  - `partial` のときの与点は、採点マニュアルの規定に従う。マニュアルに配分規定がなければ
    AI は `partial` と根拠のみ提示し、**点数は人間が確定**する（自動確定しない）。
  - 設問の最終得点は criterion 結果の合算。端数・上限の丸めルールもマニュアル準拠。

### (10) 対象問題種別（§33-12）

- **決定**: MVP 0.1 で採点対象とするのは次のとおり。

  | 種別                         | MVP 0.1 | 備考                                                |
  | ---------------------------- | ------- | --------------------------------------------------- |
  | 記述式・短答式（日本語）     | 対象    | 中心ユースケース                                    |
  | 記号選択（記号・番号の照合） | 対象    | 正解記号との単純照合。OCR 結果の記号一致で判定      |
  | 穴埋め（短い語句補充）       | 対象    | 模範解答との語句照合 + 許容表現（マニュアル）で判定 |
  | 数式                         | 対象外  | §5 (a)                                              |
  | 英作文                       | 対象外  | §5 (b)                                              |
  | 図・グラフの作図／読解       | 対象外  | §5 (c)                                              |

- 記号選択・穴埋ては「単純照合 + マニュアルの許容表現」で採点できる範囲に限る。判断が割れる
  ものは記述式と同じく人間確認へ回す。

### (11) 答案の保存期間・アプリ終了後の保持・一括削除（§33-16、§27）

- **決定**:
  - **元答案 PDF / 添削済み PDF**: ローカル（`app-data/`、簡易設計書 §23）に保持。
    **自動削除は行わない**。アプリ終了後も保持する。
  - **一括削除機能を必須で実装する**。単位はテスト単位・答案単位・全体。削除時は元 PDF・
    生成物・DB レコード・関連 AI ログを一括で消す。削除操作自体は監査ログに残す（§28）。
  - クラウド送信ペイロードはローカルに残さない（送信後キャッシュを保持しない）。
  - 評価用データ（PoC）の保持・削除は §6 で別途規定。

### (12) AI 処理履歴 / ログの保存期間（§33-17、§27）

- **決定**:
  - **AI 採点結果・Confidence・判定根拠**（Review 履歴、簡易設計書 §19）は答案本体と同じ
    ライフサイクルで保持し、一括削除の対象に含める。
  - **運用ログ**（AI/OCR の成功・失敗、PDF 解析失敗等、§28）は既定 **90 日**で自動削除する。
    設定で変更可能にするが、下限は 7 日、上限は 365 日。
  - いずれのログにも**生徒答案本文・生徒識別情報を無条件で書き込まない**（§28）。

### (13) 生徒識別情報の保存（§33-18、§27）

- **決定**:
  - 生徒の**氏名・生徒 ID 等の識別子は、ローカルの SQLite にのみ保存してよい**（(4) の手動
    割り当て結果）。保存は任意で、ユーザーが識別子を入力しなければ内部 `submissionId` のみで
    運用できる。
  - **クラウド送信ペイロードには識別情報を一切含めない**（(2)）。
  - バックアップ・エクスポート機能を作る場合も、識別子は既定で除外し、明示操作でのみ含める。

### (14) PDF 出力形式（§33-20）

- **決定**:
  - 出力は **PDF のみ**。元 PDF に確定 Annotation を重ねて **pypdfium2 + pypdf で新規
    PDF を生成**する（簡易設計書 §14、PoC 3 / Issue #12 で確定）。
  - 出力ファイル名: `<元ファイル名>_corrected.pdf`。同名が存在する場合は `_corrected_2` の
    ように連番。保存先は `app-data/exports/`（簡易設計書 §23）。
  - 画像・CSV 等の他形式出力は MVP 対象外。
  - **Issue #23 追記**: 上記を実装した。未確認設問が残る場合は出力を拒否し
    対象を返す。同一review versionへの再出力要求は決定表
    （`docs/pdf-export.md` §5）に従い、レビュー状態が前回の出力と一致すれば
    新規ファイルを生成せず既存の出力をそのまま返す（`_corrected_2` の連番は
    レビューが実際に進んだ場合にのみ発生する）。

### (15) 元 PDF への上書き（§33-21）

- **決定**: 元 PDF は**上書きしない**。編集中は「PDF + Annotation Overlay」、出力は常に新規
  ファイル（(14)）。元 PDF ファイルへの書き込み・置換・削除をアプリから行わない
  （簡易設計書 §13 / §14 / §35-4）。

### (16) キーボードショートカット（§33-22）

- **決定**: MVP は簡易設計書 §17 の候補をそのまま初期割り当てとして採用する。

  | キー                        | 動作          |
  | --------------------------- | ------------- |
  | Enter                       | 承認して次へ  |
  | E                           | 編集          |
  | X                           | AI 結果を却下 |
  | R                           | 再判定        |
  | ↑ / ↓                       | 設問移動      |
  | Ctrl + Z                    | Undo          |
  | Ctrl + Y / Ctrl + Shift + Z | Redo          |

- 割り当てはユーザー設定で変更可能にするが、既定値は上表で固定して実装を開始してよい。
  IME 変換中・テキスト入力フォーカス中はショートカットを無効化する。
- **Issue #22 追記**: `R`（再判定）と `Ctrl + Z`（Undo）を実装した
  （`app/lib/features/pdf_review/pdf_review_page.dart`
  `_shortcutBindings`/`docs/review-edit-history.md`）。`R` は簡易設計書 §17 に
  候補がなかったため本Issueで新規に決定した。`Ctrl + Y` / `Ctrl + Shift + Z`
  （Redo）は Issue #22 の対象外のまま（実施内容が Undo のみを求めている
  ため）— 後続Issueで扱う。

### (17) AI による自動コメント生成の許容範囲（§33-23）

- **決定**:
  - AI が生成するのは、点数・○×・コメント・判定根拠の**すべてにおいて「候補」**まで。
    **人間の承認なしに確定・PDF 出力しない**（簡易設計書 §2 / §35-1）。
  - コメント候補の内容は「当該設問の採点基準・模範解答・答案」に基づくものに限る。
    答案と無関係な一般的助言、生徒個人への評価（性格・態度への言及）は生成しない。
  - 低 Confidence（§3 (C) の閾値未満）の項目は候補を自動採用せず「要確認」で提示する。
  - AI 出力は構造化 JSON で受け取り、コメントは前述 (6) の文字数・規則の検証を通す。

### 3.1 確定後も残る制約と、判断待ち項目のブロック条件

A・B・C・E が確定しても、**確定したのは「どれを使うか」「どの値を既定にするか」であって、
自動確定や特定 SDK への依存を認めたわけではない**。項目ごとに、確定内容と、確定後も
守り続ける制約を示す。

- **A（OCR）確定済み: Google Document AI**。残る制約 — Document AI の SDK・レスポンス形式・
  Bounding Box 座標系への依存は `OCRProvider` 実装の内側に閉じ、座標変換／後処理へ
  漏らさない（別サービスへの差し替えと、クラウド不可時のローカル OCR フォールバックを
  維持するため）。**OCR 精度を前提にした「自動確定」フローは引き続き組まない**（C と同じ理由）。
  実 API キーが未提供のため live 疎通検証は #54 のまま。
- **B（AI モデル）確定済み: 優先度つきフォールバック**（Gemini API → Codex App Server →
  OpenRouter → OpenAI API）。残る制約 — フォールバックの層は `AIProvider` ポートの内側
  （複数アダプタを順に試す合成アダプタ）に置き、`GradingJobProcessor` から上に漏らさない。
  特定モデルのプロンプト最適化・モデル固有の JSON モードに依存したパースを
  `AIProvider` 実装の外へ持ち出さない。一致率を前提にした UI の初期表示（例: 既定で
  「承認」に寄せる）は引き続き作らない。**どの provider で採点したかを結果に残す**
  （`GradeResult.provider` / `model` / `prompt_version`）。設計は
  [`ai-grading-pipeline.md`](./ai-grading-pipeline.md)、実装は別 Issue。
- **C（Confidence 閾値）確定済み: 固定値を置かず、既定 0.80 のまま運用調整**。残る制約 —
  閾値をコードへハードコードして「要確認」判定を分岐させない。閾値は設定の単一箇所
  （`RecognitionSettings` / `GradingSettings`）から読む。既定値 0.80 は
  「未確定のプレースホルダ」ではなく「運用しながら調整する既定値」として扱う。
  **閾値に基づく自動確定（人間レビューのスキップ）は引き続き実装しない** — 今回の確定は
  閾値の運用方法についてであって、自動確定を認めるものではない。
- **D（PDF エンジン、PoC 3 で確定）**: 特定エンジンの API に直接依存した Annotation
  描画・座標 API を UI／サービス層へ散在させず、`PdfEngine` 抽象の内側に閉じる。
- **E（並列数）確定済み: 既定 4、設定値**。残る制約 — 並列度をコード内固定にしない
  （設定値 + 既定 4）。レート制限ハンドリング（バックオフ・キュー再投入）を
  「並列 1 前提」で省略しない。採用 provider（A・B）のレート制限は未実測であり、
  既定 4 は「レート制限に当たらない」保証ではない。**既定 4 での飽和動作も未検証**
  （既存の E2E テストは明示的に 2 を渡しており、同時実行可能なジョブが 4 つある
  シナリオを持たない。[`job-queue.md`](./job-queue.md)「並列度・retry設定」）。
- **Issue #25 追記（測定の位置づけ）**: 判断材料の一部を合成データで測定した
  （[`mvp-acceptance.md`](./mvp-acceptance.md) §5、再現は
  `backend/poc/issue_25_queue_throughput/report.py`）。キュー機構自体は並列度にほぼ線形に
  スケールし、上限を決めるのは採用 provider のレート制限である、という測定の読みは
  **E の確定後も変わらない**。エラー率は擬似 provider では常に 0.00 で、実測は Issue #35 を
  要する。E の確定作業（Issue #55）のうち並列数は本 Issue #81 で完了し、**残る
  「性能基準の答案件数」は #35 の実データ待ち**。

## 4. 追加要件 — 複数ページ答案の設問依存

複数ページ・複数設問を含む 1 答案で、設問間に依存がある場合のルール。簡易設計書 §29
（並列処理）を前提に、依存がある設問だけ順序を守る。

### 4.1 依存関係の分析（テスト登録時）

- テスト登録時（簡易設計書 §6）に、**設問ごとの処理を始める前に依存関係を分析する**。
- AI がテストプロファイル生成と同時に「設問 X は設問 Y の解答結果を前提とする」という
  **依存候補**を提案する。判断根拠（マニュアル・問題文の該当箇所）を添える。
- 依存の型は次に限定する。判定できないものは「依存あり（要人間確認）」に倒す。

  | 型           | 例                                                  |
  | ------------ | --------------------------------------------------- |
  | 解答連鎖     | (2) が (1) の答えを使って計算・論述する             |
  | 条件分岐     | (1) の答えにより (2) の採点基準（模範解答）が変わる |
  | 共通設定参照 | 大問の前提文・図を複数小問が共有する                |

### 4.2 確定 DAG の生成と再利用

- AI の依存候補を、**人間がテスト登録時に確認・修正して「確定 DAG」として固定する**
  （簡易設計書 §6.1 の人間確認対象に「設問依存」を追加する）。
- 確定 DAG は**同一テストの全答案へそのまま再利用する**。答案ごとに依存を推論し直さない。
- DAG は有向非巡回であること（循環を検出したら登録をブロックし人間に差し戻す）。
- テストプロファイルを修正して設問構成が変わった場合は、確定 DAG も再確認を必須にする。

### 4.3 依存設問へ渡してよい前提情報

依存元設問から依存先設問の採点へ引き継いでよいのは、次に**限定**する。

- 依存元設問の **確定した（人間承認済みの、または承認前でも高 Confidence の）OCR テキスト**
- 依存元設問の **criterion 結果と最終得点**
- 依存元設問の **模範解答**（テストプロファイル由来。答案内容ではない）
- 「条件分岐」型のとき、分岐の結果として選択された**依存先の採点基準・模範解答の枝**

渡してはならないもの:

- 依存元設問の答案画像そのもの（依存先のクラウド送信ペイロードに含めない。§2 (2)）
- 依存元設問の AI コメント文・自由文の判定根拠（採点に不要な伝播を避ける）
- 生徒識別情報（常に不可）
- 依存関係が確定 DAG に無い設問の情報

### 4.4 低 Confidence / 失敗時の停止・再開条件

- 依存先設問の処理開始時に、**依存元の前提結果が次のいずれかなら、依存先を実行しない**。
  - 依存元の OCR または採点の Confidence が §3 (C) の閾値未満
  - 依存元が「要確認」「エラー」状態（簡易設計書 §25）
  - 依存元がまだ「AI 処理済み」に達していない
- このとき依存先は **`blocked`（前提待ち）** 状態にし、理由（どの依存元か）を UI に表示する。
  依存の無い設問の並列処理は止めない。
- **再開条件**: 依存元が人間レビューで「確認済み」になった時点、または人間が明示的に
  「前提を承認して続行」を選んだ時点で、依存先を自動でキュー再投入する。
- 依存元が確定できないまま人間が依存先を手動採点した場合は、その旨を Review 履歴に記録する。

### 4.5 依存不明時の並列実行禁止

- **設問依存が不明なまま「依存なし」とみなして並列実行することを禁止する**。
- 確定 DAG が存在しないテスト、または DAG に含まれない設問が答案に現れた場合は、その答案の
  設問は**逐次処理**にフォールバックし、人間へ「依存関係が未確定」の警告を出す。
- 「依存なし」で並列できるのは、確定 DAG 上で当該設問が入次数・出次数ともに 0、または
  依存元がすべて「確認済み」の場合に限る。

## 6. 評価用データセット（4 PoC 共通）

実データ・個人情報は**リポジトリにコミットしない**。本節は「構成・件数・正解ラベル・利用許諾・
削除条件・保管場所・アクセス権」を、後から同じデータセットを再構築できる形で規定する。

### 6.1 構成

1 セットは以下をすべて含む。

| 区分               | 内容                                                                                  |
| ------------------ | ------------------------------------------------------------------------------------- |
| 生徒答案 PDF       | 手書き品質 3 区分（**綺麗 / 普通 / 汚い**）を含む。各区分に複数生徒分                 |
| 複数レイアウト     | **異なるレイアウトのテストを最低 4 形式**（1 枚物 / 冊子 / 2 段組 / 別紙解答など）    |
| 模範解答 PDF       | 各テストにつき 1 部                                                                   |
| 採点マニュアル PDF | 各テストにつき 1 部（配点・加点/減点条件・部分点・許容表現・コメント規則を含むもの）  |
| 人間の正解ラベル   | §6.3 の形式。設問ごとの確定スコア・criterion 結果・確定コメント・Annotation 位置      |
| メタデータ         | テスト ID、教科、設問数、想定難易度、レイアウト種別、手書き品質区分、匿名化の実施内容 |

### 6.2 件数（最小要件）

PoC の統計的な意味を確保するための下限。可能なら上回る。

| PoC   | 検証内容       | 最小件数                                                                                   |
| ----- | -------------- | ------------------------------------------------------------------------------------------ |
| PoC 1 | 手書き認識     | 手書き品質 3 区分 × 各 20 設問以上（計 60 設問以上）、2 レイアウト以上                     |
| PoC 2 | 採点一致率     | 2 教科 × 各 1 テスト × 各 30 答案以上（計 60 答案・のべ 300 設問以上）。人間採点ラベル付き |
| PoC 3 | PDF 座標       | 4 レイアウト × 各 10 ページ以上。既知の目標座標に ○×・コメントを描画し出力を照合           |
| PoC 4 | レイアウト変更 | 異なる 4 形式 × 各 5 答案以上。プロファイル生成 → 人間修正 → 各答案適用を通す              |

### 6.3 正解ラベル

- **作成者**: 現役の採点者 2 名が**独立に**採点する。不一致は 3 人目または合議で確定する。
- **形式**: 1 答案 = 1 JSON ファイル（個人情報を含まない `submissionId` で識別）。スキーマは
  簡易設計書 §9.2 の AI 出力構造に準拠し、`source: "human"` を付す。項目:
  - `questionId`、`score`、`maxScore`
  - `criteria[]`（`id`、`result` = pass/partial/fail）
  - `comment`（確定コメント）
  - `annotations[]`（種別と正規化座標。PoC 3 用）
  - `handwritingQuality`（clean / normal / messy）、`layoutType`
- **合意率**: 採点者間の一次一致率も記録し、PoC 2 の「人間同士の一致率」ベースラインとする。
- ラベル用スキーマ定義（データを含まない JSON Schema）と、匿名化手順書は**リポジトリに
  コミットしてよい**（`docs/` または `fixtures/schema/`）。

### 6.4 利用許諾

- 塾から、**PoC 評価目的での二次利用許諾を書面で取得**する。許諾書に次を明記する。
  - 利用目的: 本システムの精度評価（PoC 1〜4）に限定
  - 外部送信の可否: **OCR / AI のクラウド API へ、生徒識別情報を除いた設問単位データを
    送信することへの同意**（§2 (2) の運用と一致させる）
  - 保管期間・削除条件（§6.6）
  - 再配布の禁止
- 許諾が取れない答案は、氏名・生徒 ID・学校名・筆跡から個人特定につながる書き込みを
  マスキングした**匿名化版のみ**を使う。匿名化の実施内容をメタデータに記録する。

### 6.5 保管場所・アクセス権

- **保管場所**: リポジトリ外。組織が管理するアクセス制御付きストレージの専用領域に置く。
  本書には具体的な URL・共有リンクを記載せず、論理パス
  `"<組織管理ストレージ>/auto-scoring/eval-datasets/<dataset-id>/"` として参照する。
  実体の場所・認証情報はプロジェクトオーナーが別途管理する。
- **アクセス権**: プロジェクトオーナーと当該 PoC の担当者のみ。最小権限。共有リンクの発行禁止、
  ダウンロード後のローカルコピーは作業端末の暗号化ボリューム内に限定し、PoC 終了時に消す。
- **ローカル作業時**: 評価データは `app-data/` や作業ツリーの外の専用ディレクトリに置き、
  `.gitignore` 済みであることを毎回確認する（§7 のチェックリスト）。

### 6.6 削除条件

- 次のいずれか早い時点から **30 日以内**に、すべての複製（クラウド・作業端末）を消去する。
  - 対象 PoC 群（1〜4）がすべて完了し、結果が各 Issue に記録された時点
  - 利用許諾で定めた保管期限
- PoC を中止した場合は**中止決定から速やかに**消去する。
- 消去は「元データ・派生画像・ラベル・キャッシュ・ログ」を対象とする。消去実施日・対象・
  実施者を記録（消去記録自体に個人情報を含めない）。
- クラウド API 側に送信済みのデータについては、各サービスのデータ保持ポリシーを確認し、
  可能ならオプトアウト設定・ゼロデータ保持設定を有効にする。
