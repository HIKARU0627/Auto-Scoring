GitHub Issue [#21](https://github.com/HIKARU0627/Auto-Scoring/issues/21)（親

## 1. 実装したもの

- `PdfReviewPage`（`app/lib/features/pdf_review/pdf_review_page.dart`）:
  Material 3 の Navigation Rail（設問一覧）+ `pdfrx` PDF viewer + Inspector
  （AI認識文字・点数・根拠・採点基準・Recognition/Grading Confidence・
  設問コメント）+ action bar（修正/却下/承認して次へ、AIが採点できなかった
  設問では 点数を入力 も -- §2.13.1）。
- `backend/src/auto_scoring/api/review_router.py`: 既存の
  `RecognitionResult`/`GradeResult`/`Annotation`/`Question`/`Rubric`
  domain・repository（Issue #11 で実装済み）を読み取り専用でHTTPへ公開する
  最小限のエンドポイント（下記§3）。
- `app/lib/core/pdf_review_geometry.dart`: 0〜1正規化座標をpdfrxが報告する
  ページ実寸へ変換する純粋関数（PoC 3 の座標契約をそのまま利用）。
- `app/lib/core/confidence_level.dart`: Confidenceの高/中/低の表示用分類。

## 2. 決定事項・未決事項

### 2.1 バックエンドread APIをこのIssueで追加した

Issue #21 の本文は Flutter 側の画面実装のみを列挙しているが、Flutter は DB
ファイルへ直接アクセスしない設計（`docs/data-model-and-local-storage.md` §8
「Flutter が DB ファイルへ直接アクセスしない」）であり、実装済みの
`RecognitionResult`/`GradeResult`/`Annotation`/`Question`/`Rubric` を読む
REST エンドポイントは Issue #21 着手時点で存在しなかった（既存の
`recognitions_router.py` は文字認識のみ）。元PDFバイト列を取得する
エンドポイントも存在しなかった。これらが無いと本画面の受入条件
（AI認識文字・score・根拠・rubric・2種類のconfidence・annotationを同一設問に
対応付けて表示する）を実データで満たせないため、本Issueのlabel
`area: ai-grading` の範囲内として、読み取り専用のエンドポイントを追加した
（永続化・書き込み系エンドポイントは追加していない）。

### 2.2 pdfrxを新規依存として追加した

`pdfrx: ^2.4.7`。既存依存では PDF 表示ができないため、AGENTS.md
「新しい依存関係は既存コード・標準ライブラリ・既存依存で満たせない場合のみ
追加する」に従い追加した。`pdfrx` は pdfium を包み、PoC 3
（`docs/poc-3-pdf-coordinates.md`）が座標往復を検証したのと同じレンダリング
エンジンであるため、正規化座標の変換契約をそのまま使える。

### 2.3 Confidenceの高/中/低の閾値は表示専用（業務閾値とは別物）

低Confidenceの基準値は固定値を置かない運用に確定した（Issue #81。
`docs/business-rules-and-evaluation-data.md` §3 (C)、
`docs/data-model-and-local-storage.md` §9）。業務閾値は backend 側の設定値
（既定 0.80）で、運用しながら調整される -- つまり画面側が焼き込んでよい定数ではない。
本画面はテキスト/アイコンでの区別が受入条件のため、`ConfidenceLevel`
（`app/lib/core/confidence_level.dart`）に **表示分類専用**（0.9以上=高、0.7以上=中、
それ未満=低）の閾値を置いている。この閾値は何もゲーティングしない
（自動確定・ブロックの類は一切行わない）。業務閾値の運用値が動いても表示分類は
追随しないので、実運用の分布が見えた時点で分類の妥当性を見直すこと。

### 2.3.1 高Confidenceに「大丈夫」の顔をさせない（決定・Issue #156）

**印が付くのは「低」だけである。** 中と高は無彩色の数値と語だけで出す。

もとは高＝`check_circle` を `AppStatusTone.success`（緑）で描いていた。
実機再検証 #4 が、その緑チェックが何を意味していたかを実測した:

| 実測（AI採点12件）                                                      |        結果 |
| ----------------------------------------------------------------------- | ----------: |
| 採点信頼度 ≥ 0.95                                                       | **12 / 12** |
| うち誤った0点                                                           |       **5** |
| AI自身が `blank` と申告した3件（**3件とも切り出しの誤り**）の採点信頼度 |    **1.00** |

**確信度は正誤を分けていない。** それでも 0点 の隣に緑のチェックが並び、
同じ画面に「要確認」も出ていた。人に「見ろ」と言う旗と「見なくてよい」と言う印が
同居していたことになる。**正誤を区別しない数値に、承認の顔をさせない。**

**数値そのものは残す。** §8.2・§10 のとおり Confidence の役目は
「人がどれを先に見るか」の手がかりを出すことで、それは今も果たせる。
外したのは事実ではなく**太鼓判**である。簡易設計書 §25.2 が禁じているのは
「確信度から確認済みを導くこと」であり、緑のチェックは画面の上でそれを
先取りして人に勧めていた。

中と高が同じアイコン（`Icons.straighten`）なのも同じ理由で、高だけに別の形を
与えれば、色を外しても「高は良い印」が残ってしまう。区別は数値と「中」「高」の語が
付ける（Issue #21 の受入条件は満たしたまま）。

### 2.3.2 AIが「解答欄は空白」と申告した0点は、その申告を伴う（決定・Issue #156）

`GradeResult.answer_image_finding`（Issue #136）を `GradeResultResponse` に載せ、
`blank` のとき採点欄に本文として出す。

**0点は「採点できた」ではなく「点を与えられなかった」である。** 切り出しが誤って
いても正しくても同じ数字になり、Issue #136 が `not_the_answer` を止めたあとも
実測5件が残った（`blank` 3件・`answer` 2件）。`blank` 3件は**3件とも切り出しの
誤り**で、しかも採点信頼度 1.00 —— 数字の側から見分ける材料は一つも無く、
**AI自身のこの申告だけが残っていた。** Issue #136 はそれを保存するところまでで、
画面へ出す経路が無かった。

**旗ではなく本文にする。** アイコンも強調色も付けない。これは「確認せよ」という
指示ではなく「AIはこう言った」という事実であり、`blank` は本当の無記入
——つまり**正しい0点**——でもあり得るからである（#136 が `not_the_answer` と
別の値に分けた理由そのもの）。文面もAIの申告と、そこから確実に言える両義性までで
止め、**切り出しが誤っているとは言わない。** 人が見るべき現物は Issue #122 が
すでに同じ画面の先頭に出しているので、そこへ案内するだけでよい。

`answer` と申告なしには何も足さない。全設問に文が付けば、この Issue が畳んだ
「常時点いている旗」を別の形で作り直すだけになる（実測では12件中3件）。

### 2.3.3 この Issue が届かないもの（Issue #156）

**`answer` と申告された誤った0点2件は、上のどれでも止まらない。**
#136 の `not_the_answer` にも当たらず、`blank` でもないので §2.3.2 の本文も付かず、
確信度も 0.98〜1.00 で出る。

ここで効くのは Issue #122 の切り出し画像（AIが実際に見た画像が判断材料の先頭に
ある）と、§2.3.1 で緑のチェックが消えることだけである。**この2件を捕まえる新しい
旗は足していない。** 足せば全設問に立つ旗が1つ増え、いま畳んだ問題が1段深くなる。

### 2.4 annotationの表示位置は`anchor_text`から解決する（R3レビュー対応）

実際の`GradingJobProcessor`が永続化するannotationは、種類を問わず常に
`anchor_text`のみを持ち`rect`は設定しない（AIにPDF座標を直接推測させない
という簡易設計書 §12.1の方針どおり、座標決定はアプリ側の責務）。当初
このIssueでは`anchor_text`→座標の解決を実装しておらず、フィルタが
一切マッチしないため実データではoverlayが何も描画されない状態だった
（R3レビュー指摘）。

`app/lib/core/pdf_review_geometry.dart`の`resolveAnnotationRect`が、
簡易設計書 §12.1-12.4の手順をそのまま実装する。

1. `annotation.rect`が既に設定されていればそれをそのまま使う（APIの
   契約上あり得るが、現状どの書き込み経路も設定しない）。
2. なければ`anchor_text`を、その設問のOCR`RecognitionResult.boxes`と
   完全一致で突き合わせ、一致した語のBounding Boxを使う（§12.3）。
3. それでも解決できないものは`null`を返し、呼び出し側が設問のInspector内
   「設問コメント」欄へ退避表示する（§12.4）。**PDF上には何も描かない。**

**Issue #141 で手順3の前にあった`score_area`フォールバックを廃止した。**
`○`・`×`・`△`・`点数`は特定の語ではなく解答全体への印だから、という理由で
`fixedPositionAnnotationKinds`が`score_area`（Annotation配置領域、§12.2）へ
退避していた。しかしそれは「AIが解答全体を指した」場合の規約であって、
「AIが指した語をこちらが見つけられなかった」場合の規約ではない。
実機再検証ではAIの注釈14件が1件残らずこの経路を通り、Issue #120 以降
`score_area`は回答欄と同じ高さの帯として導出されるため、
**ページの高さの23%を横切る×**として描かれた。
位置が分からないものは、分からないと分かる形で出す（`docs/pdf-export.md`
§2.0.1）。明示`rect`のあるもの（人が置いた印）は従来どおり描画される。

**R5レビュー対応**: 上記2.のOCR Bounding Boxは、`adapters/submission_
intake.py`が答案areaごとに`crop_normalized_rect`でpageからcropした
answer画像に対して正規化された座標であり、page全体に対する正規化座標
ではない（`RecognitionJobProcessor`はこのcrop画像をそのままOCR provider
へ渡し、providerが返すbox座標を一切re-projectionせずに永続化する）。
`_findAnchorTextRect`が`box.x`/`box.y`をそのままpage正規化rectangleへ
コピーしていたため、答案areaがpage全体でない設問では、crop分のoffsetと
scaleが失われ、annotationが誤った位置（＝誤ったコンテンツの上）に配置
されていた（R5レビュー指摘）。

`resolveAnnotationRect`へ`questionAnswerArea`（`Question.answer_area`）を
追加の引数として渡し、`_cropRelativeToPage`が
`page.x = area.x + box.x * area.width`（y/width/heightも同様）で
box座標をpage正規化座標へ変換してから使う。`crop_normalized_rect`は
軸並行なcrop（offset・scaleのみ、回転なし）であるため、この一次変換で
厳密に一致する。`answer_area`が未確定の設問は
`_build_answer_image`がpage全体をそのままOCRへ渡す（`NEEDS_REVIEW`、
簡易設計書 §24）ため、この場合はidentity（offset 0, scale 1）の
crop領域として扱い、既存の（page全体を答案areaとする）挙動を保つ
（`_fullPageArea`）。

**R6レビュー対応（1/2）**: `_build_answer_image`は`answer_area`が`None`の
場合だけでなく、幅または高さが0以下の場合（`zero_area`）も同じpage全体
フォールバックを適用する（ドメインモデルは幅/高さ0の`NormalizedRect`を
そのまま許容するため、`Question.answer_area`にこの状態が実際に永続化され
得る）。当初`_effectiveAnswerArea`相当の判定が無く、`questionAnswerArea`
が非nullでさえあればそのままcrop変換に使っていたため、面積0の
`answer_area`ではannotationの幅/高さが`box.width/height * 0 = 0`に潰れ、
描画されないまま消えていた（R6レビュー指摘）。`_effectiveAnswerArea`が
`answerArea == null || width <= 0 || height <= 0`のいずれかで
`_fullPageArea`（identity）へフォールバックするようにし、backendの
`_build_answer_image`と同じ判定基準に揃えた。

**R6レビュー対応（2/2）**: 設問が再度採点されると（Issue #18の再submit）、
recognition履歴には設問ごとに複数のOCR結果（各Jobが自分専用の
`RecognitionResult`を作る）が古い順で積み重なる。`_findAnchorTextRect`は
`recognitions`を先頭（＝最も古い試行）から走査し最初に一致したboxを返して
いたため、`annotationsForDisplayedAttempt`が最新の試行のannotationを
表示し、Inspectorも最新のOCR結果を表示しているにもかかわらず、同じ
`anchor_text`が古い試行のOCR結果にもたまたま存在する場合、古い試行の
（別の位置にある）boxが使われてしまっていた（R6レビュー指摘）。

対応として2点変更した。

- `QuestionReviewState.recognitionsForDisplayedAttempt`（新規）: OCR半分の
  `RecognitionResult`は採点半分の`GradeResult`より先にcommitされるため
  （`_isAwaitingGrade`と同じ因果関係）、`annotationsForDisplayedAttempt`
  のような`created_at`の完全一致では紐づけられない。代わりに
  `created_at`が`displayGrade.created_at`以前のものだけに絞り込み、
  まだgrade化されていない（将来の）再submit試行のOCR結果を除外する。
- `_findAnchorTextRect`は`recognitions`を末尾（＝最も新しい試行）から
  走査するように変更した。上記で絞り込んだ一覧の中でも、複数の過去の
  試行が残っている（＝現在の試行だけに限定できていない）ケースを吸収し、
  「表示中の試行のOCR結果」を常に優先して一致させる。

呼び出し側（`_buildAnnotationOverlay`/`_fallbackAnnotationsFor`）は
`review.recognitions`ではなく`review.recognitionsForDisplayedAttempt`を
渡すよう変更した。

### 2.5 承認・修正・却下はこの画面のメモリ内でのみ保持する（Issue #22 で解消）

> **Issue #22 で更新**: 以下は Issue #21 時点の記録。承認・修正・却下・再判定・
> Undo は現在すべてサイドカーへ永続化される（`app/lib/core/app_dependencies.dart`
> の `editReview`/`rejectReview`/`regradeReview`/`approveReview`/`undoReview`、
> バックエンドは `backend/src/auto_scoring/adapters/review_actions.py` +
> `backend/src/auto_scoring/api/review_router.py`）。詳細は
> [`review-edit-history.md`](./review-edit-history.md)。`ReviewDecision` enum
> は削除済みで、`QuestionReviewState`はサーバーの`Review`履歴
> （`effectiveReview`）から確定状態を導出する。

Issue #21 の対象外どおり、`PdfReviewPage`のaction bar（修正/却下/承認して次へ）
は`ReviewDecision`をこの画面のState内でのみ保持し、バックエンドへは一切
送信・永続化しない。「修正」は同一セッション内のみ保持されるメモをInspector
内のテキストフィールドへ入力できるだけで、`Review`/`GradeResult`エンティティ
への書き込みは行わない。承認・修正の永続化・最終PDF生成は後続Issueで扱う。

### 2.6.1 答案をまたぐ移動（Issue #113）

**この画面は答案1件の中だけを見ていた。** 最後の設問で Enter を押すと
「最後の設問です」と出て止まり、次へ行く導線が無く、ホームへ戻るしかなかった。
40枚だとその往復だけで80回の操作になる。

いまは最後の設問を確定すると**次の答案の最初の設問へ `context.replace` で移る**。
AppBar に `12 / 40 件目` が出る。`S` は何も確定せずに次の答案へ移る（未了のまま
キューに残る）。

並び順を決めるのは `core/review_queue.dart` で、**答案キュー画面と同じ規則で
なければならない** — 一覧で見えている順と Enter で進む順がずれた瞬間、講師は
自分がどこにいるか分からなくなる。詳細は [review-queue.md](./review-queue.md)。

**キューが引けなくてもこの画面は成立する。** そのときは現在地が出ず、最後の設問で
止まる（Issue #113 より前の挙動に戻るだけ）。キューが引けないことを理由に、目の前の
答案のレビューまで止める意味は無い。

残りのfixtureでの目視確認は、Windowsデスクトップビルドでの手動確認に委ねる。

### 2.8 pollingはsubmission状態でなく設問ごとのAI結果有無で判断する（R3レビュー対応）

当初pollingの継続条件をsubmissionの`unprocessed`/`ai_processing`状態に
結び付けていたが、`submission_intake.py`が示すとおりsubmissionの状態遷移
（`UNPROCESSED→AI_PROCESSING→AI_PROCESSED`）は取込時に同期的に完了し、
設問ごとのjob（Issue #18のjob queue）が作られるより前に`ai_processed`へ
進んでしまう。つまり本番のタイミングでは、実際にjobがqueued/runningの間
ずっとsubmissionは既に`ai_processed`を報告しており、状態ベースの条件は
実質的に一度もpollingを継続させない（R3レビュー指摘）。

`_updatePolling()`は当初`QuestionReviewState.hasAnyAiResult`
（`latestOcrRecognition != null || latestAiGrade != null`）が`false`である
限りpollingを継続する方式に変更したが、これも不十分だった
（R4レビュー指摘、下記）。submissionの状態文字列は一切参照しない。
AppBarの手動更新ボタン（`review-refresh-button`）は変更なし。pollingは
引き続き`silent`フラグ付きで実行し、読み込み中スピナーやエラーバナーが
定期的にちらつくのを防ぐ。

**R4レビュー対応**: `GradingJobProcessor.process`はOCR認識（recognition半分）
を独立したtransactionで先にcommitしてから、採点半分でAI providerを呼び出す
（`jobs/grading_processor.py`）。そのため通常の採点jobが「OCR結果はcommit
済みだがAI providerの応答をまだ待っている」状態（job状態は`running`）でも
`latestOcrRecognition`は既に非nullになり、`hasAnyAiResult`ベースの条件は
gradeが1件も存在しないままpollingを停止させてしまい、手動更新するまで
画面が「未採点」のまま固まっていた。

`GET /submissions/{submission_id}/jobs`（Issue #18で実装済み、本Issueでは
新規に消費するだけ）から取得した設問ごとのJob一覧を使う。Jobsの取得は
submissionの取得と同様best-effort（`_refreshJobs`、失敗しても既知の一覧を
保持するだけで画面全体は壊さない）。`FAILED`はbackendの再試行ポリシーに
よって`QUEUED`へ自動的に戻り得るが、それは他の終端状態と同じく手動更新
ボタンに委ねる（P1 review）。

**R5レビュー対応**: `_isAwaitingGrade`は当初「gradeが1件でも存在すれば
即座にfalse（pollingを止めてよい）」だったが、これは設問が新しい確定済み
依存グラフversionの下で再submitされた場合（Issue #18）を考慮していな
かった。再submitは同じ設問に新しいJobを作るが、append-only履歴の
`latestAiGrade`は古い試行のgradeを引き続き返すため、`_latestJobFor`が
新しいJobをqueued/running/blockedとして報告していても、古いgradeの存在
だけでpollingが止まり、新しい試行が完了してもreviewerには古いscore・
annotationが残り続けていた（R5レビュー指摘）。

`_isAwaitingGrade(review, questionId)`は次の順で判定する。

1. その設問のJobが1件も無ければ、gradeが無い間だけ継続する（Jobが後から
   作られる可能性に備える、従来どおり）。
2. 最新Jobが終端状態（`_terminalJobStates`）でなければ無条件に継続する
   （新しい試行が走っている可能性があるため、たまたま古いgradeが
   キャッシュにあっても関係ない）。
3. 最新Jobが終端状態なら、`latestAiGrade`が無いか、その`created_at`が
   最新Jobの`created_at`以前（＝その試行より前に書かれたgrade）である間
   だけ継続する。gradeは常にそれを生成したJobの作成より後に書き込まれる
   ため、`grade.created_at`がJobの`created_at`より後であることが「この
   gradeはこのJobの結果である」ことの確認になる。

3.の判定により、新しいJobが実際にはterminalに達しているのにまだ古い
gradeしか観測できていない（次のfetchでまだ追いついていない）窓では
継続してもう一度fetchし、追いついた時点で自然に停止する。

pollingが導入する race condition に対処している。

- **世代トークンによる直列化**: `QuestionReviewState.fetchGeneration`を
  fetch開始のたびにインクリメントし、結果を適用する直前にまだ最新の世代か
  確認する。3秒間隔のpollingが前回のrefresh完了より早く発火した場合（遅い
  requestが複数並走した場合）でも、古いrequestが後から完了して新しい結果を
  上書きしないようにする。あわせて`_pollInFlight`フラグで前のpollが
  完了するまで次のtickを開始しない。
- **表示中fetchのloading状態を保護する**（R3レビュー指摘）: silentな
  pollは、その設問が既に（手動更新やタブ切替による）表示ありfetch中
  （`review.loading == true`）であれば何もせず即座に戻る。これが無いと、
  表示ありfetchの途中でsilent pollが割り込んで`fetchGeneration`を進め、
  そのsilent fetch自体が失敗した場合に表示ありfetch側の`loading`を誰も
  `false`へ戻さず、スピナーが永久に残ってしまう。
- **recognition/gradeのcommitタイミングの競合**（R5レビュー指摘）:
  `GradingJobProcessor.process`は採点半分のOCR訂正結果
  （`grading-recognition:`、stage=`grading`）をgrade・annotationと
  同一transactionでcommitするが、これはOCR半分の`RecognitionResult`
  （stage=`ocr`）の別のtransactionより後に発生する。`_ensureReviewLoaded`
  が`listRecognitions`を呼んだ直後・`listGrades`を呼ぶ前にこのcommitが
  割り込むと、取得した`recognitions`はまだ古いまま（`grading`段階の行が
  無い）なのに、`grades`は新しいgradeを含んでしまう。gradeが存在すれば
  pollingが停止し得るため、この不整合を放置すると「採点AIの認識結果」欄が
  手動更新まで欠落したままになる。fetch後に「最新のAI gradeと同じ
  `created_at`を持つrecognitionが取得済みrecognitions内にあるか」を
  確認し、無ければrecognitionsだけをもう一度取得し直す
  （`consistentRecognitions`）。annotationはgradeと同一transactionで
  commitされるため、この競合の対象にならない。

### 2.9 keyboardショートカットはnote編集中は無効化する

`note field`（修正コメント欄）がfocusを持っている間は、`CallbackShortcuts`の
bindingsを空map（`_shortcutBindings`）にする。`CallbackShortcuts`は
bindingsに一致するキーを、callbackの中身に関わらず無条件に「処理済み」として
消費してしまうため、callback内でfocus判定をしても手遅れ（キー入力そのものが
note fieldへ届かなくなる）。bindingsの登録自体をfocus状態に応じて外す方式を
採用した。

### 2.10 InspectorはOCRと採点AIの認識結果を別々に表示する（R3レビュー対応）

`RecognitionResult`には、OCR自体の認識結果（Issue #19の文字認識job、
id接頭辞`recognition:`）と、採点AIが採点時に独自に読み直し訂正した認識結果
（`GradingJobProcessor`、id接頭辞`grading-recognition:`）の2種類があり、
どちらも`source=ai`のため`source`だけでは区別できない
（`docs/ai-grading-pipeline.md`「AI graderが訂正した認識結果を保持する」）。
当初Inspectorは`source`のみでグルーピングしていたため、この2段階が
同一の「AI認識文字」欄へ意図せず統合されていた（R3レビュー指摘）。

`RecognitionResponse`（`recognitions_router.py`）へ`stage`
（`"ocr" | "grading" | "human"`）フィールドを追加し、id接頭辞と
`source == human`から機械的に導出する（`_recognition_stage`）。
Inspectorは`latestOcrRecognition`（`stage == 'ocr'`）と
`latestGradingRecognition`（`stage == 'grading'`）を別々のセクション
（「OCR文字認識信頼度」欄と「採点AI文字認識信頼度」欄）として表示する。
pollingの継続判定（2.8）も`latestOcrRecognition`の有無のみを見る
（採点AIの訂正結果はグレーディングjob完了後にしか現れないため）。

### 2.11 設問番号の並び順は数字/英字混在でも推移的な自然順にする（R3レビュー対応）

設問番号（`Question.number`）は`"1"`のような単純な数字だけでなく、
`"1a"`のような枝番も許容される。当初の比較関数は
`int.tryParse`で両辺を数値化できたときだけ数値比較し、片方でも失敗したら
文字列比較にfall backしていたが、これは推移律を満たさない
（例: `"2" < "10"`、`"10" < "1a"`、`"1a" < "2"`が同時に成立してしまい、
安定した全順序にならない）。

`_compareQuestionNumbers`は`_tokenizeForNaturalSort`で文字列を数字の連続と
非数字の連続に分割し、トークンを先頭から順に比較する一貫した規則に
書き換えた: 同じ位置のトークンが両方数字ならその数値で、両方非数字なら
辞書式で比較し、型が異なる場合は常に「数字トークン側を小さい」とみなす
（共通の型付けルールを型ペアごとに変えないことで推移律を保証する）。
共通接頭部が一致してどちらかのトークン列が尽きた場合は、短い方を先とする。

### 2.12 annotationは表示中のgrading試行だけに限定する（R4レビュー対応）

設問は複数回グレーディングされ得る（Issue #18: 新しい確定済み依存グラフ
version下での再submitは新しいJobを作り、`GradingJobProcessor.process`は
そのたびに新しい`GradeResult`と新しいannotation群を追加する。append-only
履歴のため古い試行の行は削除されない）。当初はannotation一覧を無条件に
全件overlay/フォールバック表示していたため、Jobが再発行されると、
Inspector/overlayが現在の`displayGrade`（最新のgrade）を示しているにも
関わらず、過去の試行の（矛盾し得る）markがそのまま重ねて表示され続けて
いた（R4レビュー指摘）。

`Annotation`はどの`GradeResult`から生まれたかを指すidを持たない
（`GradingJobProcessor.process`が同じtransaction・同じclock読み取り
`now`から両方を作るだけで、互いのidを記録し合わない）。スキーマ変更を
避け、`QuestionReviewState.annotationsForDisplayedAttempt`が
`annotation.createdAt == displayGrade.createdAt`（両方とも同じ`now`から
書き込まれる）で一致するものだけに絞り込む。`displayGrade`が存在しない
（まだ一度もグレーディングが完了していない）場合は空リストを返す。
overlay（`_buildAnnotationOverlay`）・フォールバック一覧
（`_fallbackAnnotationsFor`）の両方がこのフィルタ済み一覧だけを参照する。

この方式は、人がgradeを確定した後（`displayGrade`が`latestHumanGrade`に
切り替わった後）は、どのAI annotationの`created_at`も人のgradeの
`created_at`と一致し得ないため、AIの古いmarkが人の確定後の点数の隣に
残り続けるケースも合わせて解消する（「human overrides AI」の既存方針と
一貫した挙動）。

### 2.13 設問の状態と答案の状態を、置き場所と語彙で分ける（Issue #84）

この画面は同じ「問1」について**粒度の違う状態**を同時に出していた。設問見出しの
直下にあったバッジは `_submissionStateVisual`、つまり**答案全体**の state を描いて
いたが、`問1` という見出しのすぐ下にあるので、読む側はそれを「その設問の状態」と
して読む。一方 DAGパネルと左レールは設問ごとの状態を出していた。

結果、同じ画面が同じ設問について逆のことを言った。

| 画面の状況     | DAGパネルの問1 | 右パネルのバッジ |
| -------------- | -------------- | ---------------- |
| `blocked` 相当 | 承認済み       | ⚠ 要確認         |
| `failed` 相当  | レビュー待ち   | ✓ AI処理済み     |

**どちらの表示も単体では正しい。** データの誤りではなくスコープの不一致であり、
答案の状態を設問見出しの直下に置いたこと自体が原因である。提供元の異なる5体の
AIエージェント（Google / OpenAI / Anthropic / xAI / Anysphere）が互いの評価を
見ずに独立に、全員 high で指摘した唯一の項目である（Issue #71 の集約結果。
`docs/ui-ux-multi-agent-evaluation.md` §4.1 -- 本PR時点では未マージ）。

決めたことは3つ。

**(1) 設問の状態を導く場所を1つにした。** `app/lib/core/question_status.dart` の
`QuestionStatus` が語（ラベル）・形（アイコン）・強調度（トーン）を1組で持ち、
`deriveQuestionStatus` だけが `Job` と `Review` からそれを決める。DAGパネル・
左レール・右パネルの3箇所は `_questionStatus` を通して同じ入力を同じ関数に渡すので、
**食い違いようがない**。「3箇所の描画を揃える」のではなく導出を1本にする、という
違いが重要で、揃えるだけならまた離れる。

`QuestionStatus` は Issue #64 で `DagNodeStatus` として `core/dependency_dag.dart`
に置いたものである。DAG専用の名前のまま他の2箇所から使うと、また「これはDAGの語彙
だから」と別の語彙が生えるので、名前と置き場所ごと動かした。ヘッダ要約の
`DagNodeProgress` はパネル固有なので `dependency_dag.dart` に残っている。

`前提待ち` が名指す前提の設問番号（「問1 待ち」）も `QuestionStatus.labelWaitingFor`
に置いた。DAGノードだけが持っていた表現だが、レールと右パネルが同じ状態を別の語で
呼ぶ理由が無い。

**(2) 答案の状態は AppBar へ移した。** 消したのではない。AppBar は**答案の名前が
出ている唯一の場所**なので、そこに置けば位置で対象が分かる。加えてラベルにも
`答案: ` を付けて、位置と語の両方で名指す。設問見出しの直下にあったときは、どちらも
無かった。

答案の語彙も1箇所に出した（`app/lib/core/submission_status.dart`）。この画面と
答案取込画面が別々の対応表を持っていて、同じ `ai_processed` を一方は「処理済み」、
他方は「AI処理済み」と呼んでいた。同じ食い違いの小さい版なので、同じPRで潰した。
語は設問側の `AI処理中` に合わせてある。

**(3) 左レールが読む先を、`_reviews` から `_questionStatus` に変えた。**
`_reviews` はこの画面が**いま開いている設問**しか持たないので、それ以外はすべて
`hourglass_empty` に落ちていた。要確認・前提待ち・レビュー待ちが同じ絵になり、DAGが
真上で描き分けている差が消える。狭幅ではラベルも落としていたので、同一アイコンが
5個縦に並ぶだけになっていた。

新しいAPIは要らなかった。`_jobs`（`listJobs`）は元から答案全体をカバーしており、
DAGパネルは既にそこから未訪問の設問を描いている。レールは同じものを読むだけである。
狭幅でも `NavigationRailLabelType.all` を維持して設問番号を残す。16px の節約より、
レールが何で索かれているかの方が重い。

**レールに載せないもの**: 「この画面がその設問をまだ取得していない」「取得に失敗した」
は、設問の状態ではなく Inspector の内容についての事実である（Inspector 側が
スピナーと再試行バナーを出す）。レールにこれを描かせていたことが、真上のパネルとは
別の問いに答え始めた入口だった。レールは設問の状態だけを出す。

状態の語はレールでは幅が足りないので、tooltip と semantics label に載せている
（`問2 要確認`）。アイコンの形だけで意味を当てさせない（Issue #25）。

### 2.13.1 AIが採点できなかった設問（Issue #118）

**症状**: AI 採点が permanent 失敗した設問で、インスペクタは
「まだAI結果がありません」とだけ出し、action bar の 承認 も 修正 も
サーバ側で 409 になる。**その設問はそこで詰み、答案1枚が止まる。**
実機検証で発生した。

**画面側の決定**:

- **何が起きたかを言う。** AI が終了して grade を出さなかった設問
  （`_aiProducedNoGrade`: Job が terminal で、AI の `GradeResult` が無い）
  では、インスペクタの先頭に `AppErrorBanner`（`retryable: false`）で
  「AIはこの設問を採点できませんでした」と、`Job.last_error` を出す。
  `last_error` は provider 名・例外クラス名・HTTP status だけで組み立てられて
  いる（Issue #97 レビュー4回目）ので、答案本文が混ざりえない。
- **そこから進める道を2つ並べる。** 「点数を入力 (G)」と「再判定 (R)」。
  一過性の provider 障害ならもう一度で済むので、**再判定を人力採点に
  置き換えない**。
- **「点数を入力」は該当設問にだけ出す。** どこでも出すと、AI の判断を直す
  「修正」と役割が重なった2つのボタンになる。
- **Job が queued/running/blocked のあいだは出さない。** これから grade が
  出るかもしれない設問で人力採点を勧めるのは、パイプラインと競争させることに
  なる。Job が1つも無い設問（未処理）も対象外 -- そこは「採点を開始」の仕事。
- **停止した Job は、その後に記録された人の決定に負ける**
  （`deriveQuestionStatus`、[review-edit-history.md](./review-edit-history.md) §3.1）。
  そうしないと、答案自体は確認済みなのに §2.13 の3箇所が「失敗」と言い続ける。

### 2.13.2 切り出しが解答でなかったとき、何を直すかを言う（Issue #136）

§2.13.1 のバナーは「AIはこの設問を採点できませんでした。『再判定』でもう一度AIに
任せるか、『点数を入力』で自分で採点できます」と言う。**1 つの失敗については、
この 2 つはどちらも直し方ではない。**

採点 AI 自身が「渡された画像はこの設問の解答ではない」と報告した設問
（`crop_not_the_answer`、[ai-grading-pipeline.md](./ai-grading-pipeline.md)）では:

- **再判定は同じ切り出しを同じモデルへ送り直すだけ**で、同じ答えが返る。
- **点数を手で入れても根拠が無い。** 切り出しが答案でないなら、その設問について
  人が見たものも答案ではない。

直すべきなのは**回答欄の位置**である（Issue #105 が答案の上で編集できるようにした）。
そこでこの設問だけ文面を差し替える:

> AIは、この設問に渡された画像がこの設問の解答ではないと判断しました。
> テスト設定の「回答欄」で、この設問の枠の位置を直してください。
> 位置を直さないまま点数だけ入れても、次の答案でも同じことが起きます。

**「点数を入力」は残す。** 見たうえで自分で採点すると決めた人を止める理由は無い。
変えたのは**最初に見えるもの**だけである。

**答案キューはこの設問を「人が自分で採点する設問」として数える**
（[review-queue.md](./review-queue.md) §6.1）。一覧は直し方を名乗らないので
矛盾はしないが、切り出しの誤りはテスト単位の問題になりやすい——そこは実測してから
決める、と向こうに書いてある。

**判別は `Job.last_error` に入る理由語で行う**（`core/grading_failure_reason.dart`）。
サイドカー側の `domain.submission_intake.NOT_THE_ANSWER_CROP_REASON` と同じ文字列で、
`core/submission_review_reason.dart` が `review_reason` に対してしているのと同じ
「知らない語は何も言わない」規則で読む——知らない `last_error` は §2.13.1 の
一般の文面に戻る。応答スキーマに切り出しの状態を足して API クライアントを
再生成するより、**画面が既に受け取っている文字列**を読むほうが小さい。

### 2.14 縦の配分は「判断材料 > 進捗」で決める（Issue #85）

Issue #71 の多視点UI評価で、5体中4体が独立に同じことを指摘した。**1280x720
でも右パネルは「4 / 5 点」で画面下端に達し、採点根拠・コメント・基準ごとの
判定は画面内に無い。それでも「承認して次へ (Enter)」は常に見えている。**

コードで原因を特定した。3つとも「縦の配分」を誰が決めているかの問題である。

| 症状                                     | 原因                                                                                                                                  |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 狭幅で「元に戻す」が「戻す」と頭欠けする | アクションバーが `reverse: true` の横スクロールだった。`reverse` は初期位置を**末尾**に置くので、先頭の 元に戻す が左端の外に出ていた |
| 標準幅で判断材料が下端で切れる           | 進捗パネルが**画面全幅のバンドとして最上段**に固定 `AppLayout.dagPanelHeight`(272px)＋ヘッダを占め、その高さをInspectorも失っていた   |
| 標準幅でノードが左3/5に寄り右が空白      | 3層のDAG canvasの固有幅は約480px。それを1280pxのバンドに**左寄せ**していた                                                            |

直し方も1つの原則から出している。**この画面の縦は、判断材料が先に取り、
進捗は余りを取る。**

- 進捗パネルはPDFビューア側のペインに移した（`_buildReviewBody`）。標準幅では
  Inspectorがビューポート全高を保ち、進捗パネルの高さを負担しない。狭幅では
  Inspectorがビューアの下に積まれる＝同じペインなので、従来どおり分け合う。
- バンドの高さは固定値ではなく、**そのペインの高さの
  `AppLayout.dagPanelMaxHeightFraction`(30%) 以内**にした（内容がそれより
  低ければ内容ぶんだけ）。1ノード行にも満たない高さしか割けないときは開かず、
  ヘッダの件数表示が「まだ動いているのか」に答える。トグルは無効化し、理由を
  tooltipに出す（消さない。消えるボタンは不具合に見える）。
- 幅が余るぶんは層間ギャップに回し（`DagMetrics.spreadAcross`、上限は元の幅の
  `AppLayout.dagColumnGapSpreadLimit` 倍）、残りは中央に寄せる。ギャップは
  このパネルが見せたい「上流が終わって下流が動き出す」矢印そのものが描かれる
  場所なので、そこを広げるのが一番効く。ノード自体は広げない（設問番号と
  状態ラベルは116pxで既に読める）。
- アクションバーは横スクロールをやめて `Wrap` にした。折り返せば全ボタンが
  常に完全に読める。**誤承認からの唯一の復帰手段である「元に戻す」が
  半分だけ読める状態は、この画面では許容できない。**
- Inspectorは440px幅（従来360px）。設問見出しと §2.13 の設問状態チップを
  同じ行に、採点基準を1行1基準に、修正コメント欄をスクロール領域の外へ
  固定した。チップは設問の状態のままで、読む場所も 問N の隣のままである
  （縦に積むか横に並べるかを変えただけ）。
- Issue #80 が足した「AI採点を開始」の通知は、**高さ配分の外**に置いてある。
  ボタンを持つ行動喚起であり、縮められる側になってはいけない。進捗パネルの
  高さ上限は、その通知を引いた**残り**から計算する。
- 狭幅でInspectorが取る高さには一時**下限**を置いていたが、修正コメント欄を
  スクロール領域へ戻した（§2.15）ので不要になり、素の `Expanded(flex: 2)` に
  戻した。下限が要ったのは、高さの決まった子を下端に固定していたからである。

#### 実測（#84 適用後、1280x720）

| 測ったもの                                | 値              |
| ----------------------------------------- | --------------- |
| Inspector のスクロールビューポート        | 508px           |
| 判断材料の高さ（受入テストの内容）        | 508px           |
| `maxScrollExtent`                         | 0px（＝収まる） |
| 採点基準の最終行の下端 / ビューポート下端 | 548 / 564       |

Issue #80 が「AI採点を開始」の通知を足したあとも**この表は変わらない**。
進捗パネルと同じくビューア側のペインに入るので、Inspector の高さを削らない。
それがこの節の変更で買ったものである。

受入テストの内容は**デモデータより長い**（`scripts/seed-demo-app-data.py` は
総評コメントを書かず、採点基準の文言も短い）。つまりデモデータでの余白は
これより広い。それでも 1280x720 の余白は薄く、根拠が数行伸びればゲートは
発動する。**それは想定どおりの動作**である（§2.15）。受入テストは
`maxScrollExtent == 0` を直接assertするので、将来ここが崩れたときは
「何pxはみ出したか」まで分かる。

### 2.15 判断材料を末尾まで表示するまで承認を出さない（Issue #85）

Issue #85 の受入条件は「判断材料が画面外にある状態のまま承認できてよいかを
決め、決めた内容と理由を残す（未読を示す／スクロールを促す／到達するまで
承認を出さない、のいずれか）」である。**3つ目を選んだ。**

理由は、残り2つが問題を解いていないからである。`claude` の指摘（Issue #71
評価、原文の要旨）はこうだった。

> 承認ボタンだけが常時見えているため、スクロールせずEnterを押すのが最短
> ルートになる。何十件も流す作業では実際にそうなり、human-in-the-loop の
> 前提が崩れる。

問題は「気づかない」ことではなく「**気づかないほうが速い**」ことである。
未読を示すのも、スクロールを促すのも、Enterを押す速さを1ミリも変えない。
数十件を流す作業でどちらが選ばれるかは決まっている。このアプリの前提が
「AIが採点し、人が見てから確定する」である以上、**見ていないものを確定
できない**ようにするしか、画面の側からその前提を守る方法がない。

実装（`_PdfReviewPageState`）:

- 判断材料の各行が画面に入った範囲を記録する（`_materialSeenRanges`）。
  **全部が一度に画面に収まっている場合は、最初のレイアウト直後にその場で
  条件を満たす。** 標準幅の通常ケースで
  ゲートは一切発動しない。ここは
  「見ていないまま確定させない」ためのものであって、毎回スクロールさせる
  ためのものではない。何十件も流す作業で全部見えているのに毎回操作を
  要求するなら、それは使い勝手の後退でしかない。
  - この「収まっているときは発動しない」性質は受入テストで固定している
    （`収まっているときはゲートが最初から解けていて、スクロールを求めない`）。
    `maxScrollExtent == 0` を前提として明示し、誘導行も「続きを表示」も
    出ないこと、**スクロール操作を一切挟まずに最初のEnterで承認が
    サイドカーへ届くこと**まで確認する。
  - **測り直す契機は3つあり、3つとも要る**（レビュー3回目 P2）。下記
    「末尾が見えているかは、どの契機で測り直すか」を参照。
  - 初期表示だけを見るテストでは足りない（レビュー1回目）。**状態が変わる
    経路**を通す必要がある（後述）。
- 記録するのは真偽値でも寸法でもなく、**行ごとに「その行のどこが画面に入ったか」**
  （`_materialSeenRanges`）。行は OCR認識・採点AIの認識・人による修正・AIの採点・
  人による確定・採点基準・設問コメントで、それぞれのブロックの両端に高さ0の
  マーカーを置き、ビューポートと重なった区間を**その行の高さに対する割合**として
  和集合で持つ。既読は「表示中の全行が `[0, 1]` を覆った」。

  読み返しのために上へ戻しても消えず、あとから材料が変わった場合
  （pollingがgradeを運んできた、Undoで行が戻った）は**その行が新しい行になる**
  ので、その行だけが未読に戻る。

  idで行を名指せるのは**履歴がappend-onlyだから**である。`Recognition` /
  `GradeResult` / `Annotation` は書いたら二度と編集されず、人の修正も再判定も
  Undoも**別の行**として増える（[review-edit-history.md](./review-edit-history.md)）。

  **両端では足りない**（レビュー5回目 P1）。上端と下端を別々に見ると、
  ビューポートより高いブロックを上端だけ見て末尾へ飛ばしたとき、**あいだが
  空白のまま両端が揃って既読になる**。1280x720（ビューポート592px）で高さ
  2525px の根拠本文を `jumpTo` すると実際にそうなった。スクロールバーを掴んで
  落としても同じである。**ビューポートより高いブロックは根拠本文そのもの、
  つまりこのゲートがいちばん読ませたいもの**なので、ここが抜けるのは致命的だった。
  覆った範囲の和集合なら、通っていない範囲は残る。

  ピクセルではなく**割合**で持つのは、折り返しで行の高さが変わっても
  「どれだけ見たか」が保たれるからである。ピクセル区間だと、幅を変えただけで
  未読に戻る（1〜3回目の誤爆がそのまま帰ってくる）。

- 未読のあいだは 承認して次へ が無効（`_canApprove`）。無効な理由はボタンの
  tooltipと、パネルの下端に浮かぶ誘導行（アイコン＋文＋「続きを表示」ボタン、
  色だけに依存しない）で示す。
- **「続きを表示」は1画面ぶんずつ、未読のある方向へ送る。** 末尾へ飛ぶと、
  あいだの行は一度も表示されないまま通り過ぎる ——「続きを表示」と書いておいて
  表示しないことになる。少し重ねて送るので、行が2画面の隙間に落ちることもない。

  **方向は下とは限らない**（レビュー5回目 P2）。末尾で止まっているあいだに
  画面外の**上**の行が差し替わると、ゲートは閉じるのに移動先が現在位置と同じに
  なり、**何度押しても無反応**だった。案内の文言と矢印も逆を向いていた。
  押しても何も起きないボタンは壊れているのと同じなので、未読の位置を見て
  行き先と文言を決める（`_unreadIsAbove`）。受入テストは**画面が差し出す復帰
  操作そのもの**（「続きを表示」）で戻れることを確認する。手でドラッグして
  確かめると、この壊れ方は見逃す。

- **修正コメント欄はスクロールする側に置く。** 1行から3行へ伸びる可変高なので、
  下端に固定すると3行入力したときに桁あふれし、判断材料の領域が高さ0になって
  「続きを表示」にすら届かなくなる（レビュー4回目 P2-2。700x400で実際に6px
  あふれた）。**ゲートを満たす手段が画面から消える**のが一番まずい。留める理由も
  無い: ゲートは行ごとの判定なので、メモ欄がどこにあっても判定は1pxも変わらない。
- **Enter は「無反応」にしない。** 未読のあいだの Enter は承認せず、次の1画面を
  表示したうえで理由をSnackBarで告げる（`_approveAndNext` 冒頭）。押しても何も
  起きない画面は、理由が伝わらないという意味では画面外の判断材料と同じ問題で
  ある。加えて ↑/↓ はこの画面では設問移動に割り当たっているので、**キーボード
  だけの利用者が残りを表示する経路はここしか無い**（「続きを表示」ボタン側でも
  Enter を `ActivateIntent` に再束縛してあるので、Tabで到達すれば押せる）。
- **既に確定済みの設問では素通しする。** その場合の 承認して次へ は確定では
  なく単なる移動なので、止める理由がない。
- **却下・再判定・修正・元に戻すはゲートしない。** 却下と再判定は「AIの結果を
  採らない」方向の操作で、見えていない材料を正しいと確定してしまう事故が
  起きない。元に戻すは復帰手段であり、いかなる理由でも塞がない。
- **点数を入力（Issue #118）もゲートしない。** このゲートが防いでいるのは
  「**AIの判断**を、その根拠を見ずに正しいと確定してしまうこと」である。
  点数を入力が出るのは AI が判断を出さなかった設問だけで、そこには確定して
  しまう AI の判断が無い。人は答案画像そのものを見て自分で採点しており、
  スクロール外に隠れている「見落としたはずの根拠」も存在しない。

#### 末尾が見えているかは、どの契機で測り直すか（レビュー3回目 P2）

既読の記録を材料の同一性に移したことで、判定は2つに分かれた。

| 問い                       | 何で答えるか                | レイアウト依存 |
| -------------------------- | --------------------------- | -------------- |
| 材料が変わったか           | 行のid（`_materialRowIds`） | しない         |
| いま末尾が画面に出ているか | スクロールのメトリクス      | **する**       |

分けたのは正しかったが、**後者はレイアウトが変わるたびに測り直さないと
古いままになる**。分けたからこそ、片方だけ更新されない状態が作れてしまった。

契機を列挙して塞ぐ。

| #   | 契機                                     | 経路                                     |
| --- | ---------------------------------------- | ---------------------------------------- |
| 1   | 指がスクロールした                       | `ScrollNotification`                     |
| 2   | この画面が build された                  | build 中に仕込む post-frame コールバック |
| 3   | **build を伴わずレイアウトだけ変わった** | `ScrollMetricsNotification`              |

2 には、最初のレイアウト・設問の切り替え・データの到着が入る。内容が収まって
しまうふつうのケースはスクロール通知を1度も出さないので、通知だけに頼ると
「下端外に何も無い画面で承認が出せない」という最悪の形で固まる。

3 が抜けていた。**進捗パネルを畳むのは、そのパネル自身の `setState`** である。
この画面は build されず、指も触れていないので 1 も 2 も鳴らないまま、
Inspector のビューポートだけが広がる。`maxScrollExtent` が 79.4 から 0 に
なっても未読のままになり、**ポーリングが止まっている設問では直らなかった**
（ポーリング中の画面は3秒ごとの再描画が 2 を鳴らすので、たまたま自己修復して
いた。テストも `_isAwaitingGrade` が真のままでポーリングが走っており、それが
欠落を隠していた）。

2 と 3 が重なって鳴るのは無害である。`_recordMaterialSeen` は本当に変わった
ときしか `setState` しないので、余分な測り直しはそこで止まる。

受入テストは `build を伴わないレイアウト変更でも、末尾判定は測り直される`。
**ポーリングが止まる状態**（完了済みジョブと、それより新しい採点結果）を
わざわざ作ってから進捗パネルを畳む。ポーリングが走っていると欠落を検出でき
ないので、そこがこのテストの要である。

#### スクロール量から「人が見たか」を推定するのをやめた（レビュー1〜4回目 P2）

ここは**5回**間違えた。最初の3回はパネル全体について1つのスカラを見ており、
4回目は行ごとにしたものの、まだ「点」しか見ていなかった。

| 記録していたもの                               | 誤爆した経路                                                                | 向き                   |
| ---------------------------------------------- | --------------------------------------------------------------------------- | ---------------------- |
| `maxScrollExtent`                              | 窓を縮める／修正コメントを3行打つ。ビューポートが縮むだけで extent が伸びる | 見たのに未読           |
| 判断材料の高さ（`maxScrollExtent + viewport`） | 700x720 で読み終えてから 1280x720 へ広げる。折り返しが増えて高さが伸びる    | 見たのに未読           |
| 行の組 ＋ `extentAfter == 0`                   | 末尾で止まっているところへ、pollingが**画面より上**の行を差し替える         | **見ていないのに既読** |
| 行ごとの上端と下端                             | ビューポートより高い根拠本文を、上端を見たあと末尾へ飛ばす                  | **見ていないのに既読** |

2つ目は1つ目の修正として入れたもので、**窓の高さへの依存を捨てて幅への依存を
拾っただけ**だった。テキストが折り返す以上、高さは幅の関数である。

3つ目は、記録を材料側（行の組）へ移した正しい修正の**残り半分**だった。行の組は
レイアウトから独立していたが、その組が既読かどうかを決める証拠が
`extentAfter == 0` ——**差し替え前の材料について得た測定値**——のままだった。
**証拠は、それが証明する材料そのものに紐づいていなければならない。**

4つ目は、行ごとにしたあとも**まだ「点」しか見ていなかった**ためである。両端は
「通過した2点」であって「通った範囲」ではない。

### 5つ目は誤爆ではなく、直したはずの症状が別の形で残っていたもの（PR #110）

覆った範囲の和集合にしたあと、**マージ処理そのものに欠陥が残っていた**。
「新しい区間はもう置いた」を `double.nan` の番兵で表していたため、飛び飛びに読んで
から途中へ戻ると `(NaN, x)` が区間リストに入る。

**症状は表示ではなく再描画だった。** NaN は自分自身とも等しくないので、
「区間は変わったか」の判定が毎フレーム「変わった」と答え、`setState` が止まらない。
5ラウンドのレビューはすべてウィジェット越しだったので、**画面の内容ではなく
再描画の回数**として出るこの欠陥には届かなかった。

そこで、承認できるかどうかを決める算術を `core/material_read_ranges.dart` へ
切り出した。**行ごとの区間の和集合と、その比較は、ウィジェットを立てずに検証できる。**

固定している性質は3つ:

1. **収束すること** —— 出力をもう一度マージしても変わらない。
   これが「再描画が止まる」の言い換えである。同じ入力から2回計算して比べるのでは、
   決定的な関数なら何をしても通ってしまう（PR #110 のレビュー指摘）
2. **上端と下端の両方**が揃って初めて既読 —— 下端だけで既読にすると、
   行の上半分を見ずに承認できる
3. **イプシロンは丸めの許容** —— 0 にすると、丸め幅の隙間が閉じず既読にならない

`maxScrollExtent` も `extentAfter` も「いまどこにいるか」しか答えられず、
「何を通過したか」を答えられない。だから**行ごとに、その行のどこを覆ったか**を
記録する形にした。スクロールの実測値は「**いま**その行のどこが画面に出ているか」
という一瞬の判定にだけ使い、記録には残さない。

- レイアウトが変わっても行のidは変わらないので、1〜2回目の誤爆は構造的に
  起きない
- 画面外に現れた新しい行は覆われていないので、3回目の誤爆も構造的に起きない
- 飛ばした範囲は覆われないので、4回目の誤爆も構造的に起きない

同じ形の問題は同じ日に何件も出ている（#73 のスクリーンショット鮮度判定、
#83 のガードのdocstring、#85 のこれ）。**測る対象に、測る行為自体が
混ざっている**形である。

#### 「レイアウトを変えても既読は消えない」を1本で確認する

誤爆は毎回「試していなかった軸」から出た（幅を広げる／高さを狭める／
コメントを打つ／広げて折り返しが変わる）。軸を1本ずつ足すやり方は、次の軸に
いつまでも先回りできない。そこで受入テストは**性質そのもの**を確認する形に
した。

`レイアウトを変えるだけでは既読は消えない` は、折り返しが実際に変わる長さの
根拠を持つ設問を狭幅で末尾まで表示してから、ウィンドウの幅・高さを4通りに
変え、メモ欄に3行打ち、先頭までスクロールを戻し、**そのすべてで承認が有効な
ままであること**を確認する。どの操作で崩れたかが `reason` に出る。

対になるのが次の3本である。これが無いと「絶対に閉じないゲート」が上のテストを
全部通ってしまう。

- `材料そのものが増えたときは未読に戻る` — あとから新しい認識結果の行が届く
- `画面の上の方が別の行に差し替わったら、末尾にいても未読に戻る` — 末尾で
  止まっているところへ、**前より長い**行が上で差し替わる。長いのが要点で、
  行の下端だけが画面に入ってくる状況を作っている。あわせて、案内が上を向くこと
  と、**「続きを表示」で戻れること**も確認する（常に下へ送る実装に戻すと、
  このテストだけが落ちる）
- `末尾へ飛ばしても、通っていない範囲が残っていれば既読にならない` —
  ビューポートより高い根拠本文を `jumpTo` で末尾へ飛ばす。両端だけを見る実装に
  戻すと、このテストだけが落ちる

#### 誘導行はレイアウトの外に浮かせる（レビュー1回目 P2）

誘導行は `Stack` でパネルの下端に**浮かせて**いる。レイアウトに参加させると、
どこに置いても**自分の存在を未読の根拠にしてしまう**。

- アクションバーの上に置くと、「まだ続きがある」と言うための行が、その続きを
  表示するためのビューポートを自分で削る。
- 判断材料スクロール領域の先頭に置くと、今度は内容の高さを自分で押し上げる。
  実際にこれで踏んだ: **700x720 で発動した誘導行が、1280x720 へ広げても
  消えなくなった。** 材料そのものは収まる幅なのに、誘導行の約60pxが下端外に
  残り、「収まらないから誘導行が出る／誘導行が出ているから収まらない」で
  固定される。

`Stack` なら内容の高さもビューポートも変えない。**測っているのは判断材料の
高さであって、判断材料＋ゲートUIの高さではない。** 下端に置くのは、指している
向きがそちらだからであり、覆うのはこれからスクロールして通る場所だけである
（末尾に着いた時点でゲートは開き、誘導行は消える）。

出すのは、パネルに実際に下端外の内容があることを確認してから
（`_materialOverflows`）。

#### 残る限界

既読の判定は行のidに依存する。**同じidのまま中身だけが差し替わった場合は
検知できない。** 現在のバックエンドはこれらの行を書き換えないので
（append-only）そういう更新は起こらないが、将来どれかの行が可変になったら
この前提は崩れる。そのときは内容ハッシュへ移す必要がある。

覆った範囲は**その行の高さに対する割合**で持つので、行の高さが変わる折り返しの
前後で、覆い方はわずかに伸び縮みする。全部覆っていれば `[0, 1]` のままで影響は
無いが、途中まで読んで幅を変えた場合、覆った割合は厳密には同じ範囲を指さない。
`_materialCoverEpsilon`（行の高さの0.1%、2525pxの根拠本文で3px弱）ぶんの
取りこぼしも許している。

画面が保証できるのは「**表示したこと**」までで、「読んだこと」ではない。
未読のあいだの Enter は残りを表示するので、Enterを2回押せば承認には到達する。
それでも、判断材料が一度も画面に出ないまま確定される経路は無くなる。
そこから先（本当に読んだか）は画面の側からは保証できない。

## 2.9. 「AIが見た画像」を判断材料の先頭に置く（Issue #122）

添削レビュー画面の 判断材料 の先頭に、**採点 AI に実際に送られた切り出し画像**を
出す（`features/pdf_review/answer_crop_view.dart`）。

**なぜ登録画面ではなく採点画面か。** 回答欄を人が直せる重ね合わせ編集は Issue #105
が既に作ったが、それはテストを準備する画面にあり、**点数が間違っていると分かる頃には
誰も見ていない**。Issue #122 が実測した代償はこうだった——検出枠が余白に落ち、
採点 AI には白紙が渡り、「空白なので 0 点」が**確信度 0.95〜1.00**で返る。画面には
`0点` と `確信度 95%` しか出ず、正しい 0 点と区別が付かない。**疑う手がかりが無い。**

Issue #85 が 5 ラウンドかけて「判断材料と承認を同じ画面に置く」を作った。
**AI が実際に見た画像は判断材料である**——だから、そこから導かれた文字や点数より
**上**に置く。

置き方で決めたこと:

- **空の分岐より上に置く。** 切り出しが余白なら取込が採点**前**に止めるので
  AI 結果が無い。その「まだAI結果がありません」だけを出すと、いちばん見せたい
  ケースで何も見せないことになる。
- **ほぼ余白のときは、そう書く。** ただし**理由は断定しない**。「回答欄の位置が
  ずれているか、答案が無記入です」と両方を書く。切り出しから 2 つは区別できず、
  区別できるふりをするほうが害になる。判定はサイドカーが実測した旗
  （`crop_nearly_blank`）で、ウィジェットは測り直さない。
- **高さを固定で制限する。** 縦書きの細長い列が、点数と承認ボタンを画面外へ
  押し出さないようにする（Issue #85 の「同じ画面で判断して承認する」を壊さない）。
- **`pdf_review_page.dart` には置かない。** 既に約 3,000 行あり Issue #126 で
  分割対象。差分は `_buildAnswerCrop` の呼び出しだけに留めた。
- **遅れて届いた応答は捨てる。** 設問を移動している間に前の設問の画像が届くと、
  別の設問の点数の下に別の設問の画像が出る——このウィジェットが防ごうとしている
  混同そのものになる。

## 3. 追加したAPI（読み取り専用）

| メソッド | パス                                                                | 用途                                                                |
| -------- | ------------------------------------------------------------------- | ------------------------------------------------------------------- |
| GET      | `/tests/{test_id}/questions`                                        | 設問一覧（各設問領域＋rubric）                                      |
| GET      | `/submissions/{submission_id}/source-pdf`                           | 元答案PDFバイト列（`application/pdf`）                              |

`backend/openapi/openapi.json` と `app/packages/auto_scoring_api/` へ反映済み。
