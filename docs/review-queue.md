# 答案キューと、答案をまたぐ連続レビュー

GitHub Issue #113。UI 調査（2026-09-09）で見つけた「承認の手数が枚数 × 設問数に
比例する」問題への対処である。

## 1. 何が問題だったか

**添削レビュー画面は答案 1 件の中しか見ておらず、答案をまたぐ導線が無かった。**

- 最後の設問で Enter を押すと「最後の設問です」と出て止まる
- 添削レビューへ入る経路はホームの「レビューを続ける」1 つだけで、**常に 1 件しか
  指さない**
- **答案の一覧画面が存在しない**

40 枚 × 5 設問の実測見積もり:

| 操作                                  | 回数           |
| ------------------------------------- | -------------- |
| 設問の承認                            | 200            |
| 最後の設問で行き止まり → ホームへ戻る | 40             |
| ホームで「レビューを続ける」          | 40             |
| **合計**                              | **280 回以上** |

**基本思想は「採点の自動化」であり、人の手数が枚数に比例する設計はそれだけで
失格である**（簡易設計書 §2）。ホームへの往復 80 回はここで消える。

**残る 200 回は、この Issue では減らしていない。** 減らすには「判断材料を全部
見せたうえで 1 回で確定する」形が要り、それは §25.2「確信度から完了を導かない」を
守った設計を別に立てる話である。

## 2. 並び順は 1 か所にしかない

`app/lib/core/review_queue.dart` の `ReviewQueue`。これを読むのは 2 画面ある。

- **答案キュー画面** — どの順で並べるか
- **添削レビュー画面** — Enter で次にどれへ進むか

**2 か所で別々に並べると、一覧で見えている順と実際に進む順がずれる。ずれた瞬間、
講師は自分がどこにいるか分からなくなる。** だから並び順は `core` の、ウィジェットを
持たない値に置いてある（`home_dashboard.dart` が優先順位を画面の外に出しているのと
同じ理由）。

並び規則は `HomeTestProgress._pickResumable` と**同じ**にしてある:
要確認が先、同じ状態内では取込の古い順（`HomeWorkBucket` の宣言順）。
**ホームの「レビューを続ける」が開く 1 件と、キューの先頭は一致していなければ
ならない。** 違う答案が開いたら、講師はどちらも信用できなくなる。

## 3. 済んだ答案を隠さない

一覧には全件を出す。「済みを隠す」絞り込みは作らない。

> Reddit のモデレーター 106 名への調査で、**94 名が「既定では全件見えるべき」に
> 強く同意**した。絞り込まれたバッチは全体のパターンを見えなくする。
> 並べ替え・絞り込みよりも、**キューの行に直接埋め込まれた視覚的な手がかりを
> 74.5% が選んだ。**
> — Bajpai & Chandrasekharan, "Towards a Better Modqueue"
> ([arXiv:2409.16840v2](https://arxiv.org/html/2409.16840), 2025-10)

だから行の中に、通し番号・状態・確定数・手作業の要否を並べてある。

**ただし巡回（`nextAfter`）は済んだ答案を飛ばす。** 一覧に出すことと、もう一度
開かせることは別である。40 枚を流している最中に確認済みの答案を開かされる意味は
無い。

末尾まで見て未了が残っていなければ**前に戻って探す**。「後回し」で送った答案は
キューの手前に残るので、これが無いと自分で飛ばした答案を二度と拾えない。

## 4. 行に何を出すか

| 出すもの                               | なぜ                                                                                                                                          |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| 通し番号 `12 / 40`                     | あと何枚かが見えないのは、終わりの見えない作業をさせること                                                                                    |
| 状態                                   | `core/submission_status.dart` の `SubmissionStatusVisual` を使う。**この画面が 3 つ目の対応表を作ってはならない**（Issue #84 の小さい方の版） |
| `3 / 5 問 確定`                        | §5                                                                                                                                            |
| 「AIが採点できなかった設問があります」 | §6                                                                                                                                            |
| 取込が立てた旗の要約                   | §7                                                                                                                                            |
| PDF出力ボタン                          | §4.1（Issue #137）                                                                                                                            |

### 4.1 出力は行から起動する（Issue #137）

**決定**: 全設問が確定した答案の行に「PDF出力」を置き、`showExportDialog` を
直接呼ぶ。添削レビュー画面の出力ボタンは残す。

このアプリの成果物は採点済み PDF である。#113 が入るまで出力ボタンは添削レビュー
画面にしか無く、全問承認した答案はホームの「レビューを続ける」からも消えていた
ので、**完了操作を行うと成果物に到達できなくなっていた**（#137、経緯は
[review-edit-history.md](./review-edit-history.md) §6.1）。#113 でこの一覧から
開き直せるようになったが、出力するには一覧 → レビュー画面と 2 枚めくる必要が
ある。ここはその近道である。

行ごとに置くのは、出力が**答案 1 件の操作**だからである。ヘッダに 1 つ置くと
「どれを出すのか」を別に選ばせることになり、一覧の意味が薄れる。

**出す条件は `isDone` ではなく `isFullyConfirmed`（全設問が確定しているか）。**
状態は設問粒度の事実の写しであって、事実そのものではない。取りこぼすのは
**全設問を確定したのに `reviewed` へ動かなかった答案**で、これは実在する:
#112 より前は `ai_processed` が `_REVIEWABLE_SUBMISSION_STATES` から外れており、
普通に取り込めた答案ほど全問承認しても状態が動かなかった。遡って直す
マイグレーションは無いので、それ以前に採点し終えた答案はいまも `ai_processed` の
まま全設問確定で残っている。サイドカーはこれを出力するので、画面が状態を見て
隠せば「出力できるのに出せない答案」ができる。**§6 で
`manual_grading_questions` が踏んだのと同じ形の誤りである** — 粗いほうの記録から
細かい事実を推測しない。

数え方はサイドカーの出力ゲートと**同一の述語**である。`review-progress` の
`confirmed_questions` は `domain.review_workflow.count_confirmed_questions`、
出力が拒む条件は `domain.pdf_export.unconfirmed_question_ids` で、どちらも
`is_confirmed(effective_latest_review(...))` を設問ごとに評価している。判定の
やり直しではなく、**同じ数を読んでいる**。

進捗が引けなかったとき（`0 / 0`）は出さない。押した先で必ず 409 になるボタンを
出さないためで、そのときも出力は添削レビュー画面から起動できる。**分からない
ときは出さない。**

ダイアログ本体は `core/widgets/export_dialog.dart`。`features/pdf_review/` から
移したのは、出力を起動する画面が 2 つになり、`features` どうしの import を作らずに
済ませるためである（依存方向は
[technology-stack.md](./technology-stack.md) §5）。

## 5. なぜ設問粒度の進捗が要るか

答案の `state` が動くのは**全設問が確定したとき**だけである（Issue #112）。
したがって 3/5 まで確定した答案は `ai_processed` のままで、**手つかずの答案と
`state` では区別がつかない**。中断して戻ってきた講師に「どこまでやったか」が
読めない。

#112 は答案の粒度でこの穴を塞いだ。**同じ穴が設問の粒度で残っていた。**

塞ぐには口が要る。`GET /tests/{test_id}/review-progress` が答案ごとに
`total_questions` / `confirmed_questions` / `manual_grading_questions` を返す。
**返すのは数だけである。**

既存の口では引けない。レビュー履歴は `(submission, question)` 単位なので、
40 枚 × 5 設問の一覧を描くのに 200 リクエストかかる。ホーム画面が Job について
既に断っているのと同じ形である（[home-dashboard.md](./home-dashboard.md) §4/§5）。

**進捗が引けなくても一覧は成立する。** 数が出ないのは、一覧が出ないより軽い。

## 6. 「人が自分で採点する設問」の数え方

`manual_grading_questions` は **「ジョブが失敗した」ではない**。

    終端のジョブがある (succeeded / failed / cancelled)
    かつ AI 採点が無い
    かつ まだ確定していない

設問が人の手に渡る道は失敗だけではない。

- ほぼ余白の切り出しを AI へ送らない（Issue #122）
- OCR の無い端末（Issue #114）

どちらもジョブは `SUCCEEDED` で終わり、`GradeResult` を残さない。**講師にとっては
同じこと**で、その設問は自分で採点するしかない（Issue #118 の「点数を入力」）。

**これは添削レビュー画面の `_canGradeManually` の双子である。** 終端の集合は
`domain.models.TERMINAL_JOB_STATES` と `_PdfReviewPageState._terminalJobStates` に
分かれて置いてあり、両方にその旨を書いてある。**一覧が「0」と言っているのに
開いた先が「点数を入力」を出す、は起きてはならない**（Issue #84）。

数える理由は、**金曜の午後の終わりに「残り 3 枚」を見たとき、その中身が読み分け
られるようにする**ためである。3 枚が「AI の提案を見るだけ」なのか「1 問ずつ自分で
採点する」なのかで、残り時間の見積もりがまるで違う。

> **Issue #118 が入る前は、この数は「詰んだ」を意味していた。** AI が失敗した設問に
> 人が点数を入れる経路が無く、その答案は本当に終わらなかった。いまは終わらせられる。
> 意味が変わったので、名前も画面の文言もそこに合わせてある。

### 6.1 「解答ではない画像」の設問も、この数に入る（Issue #136）

採点 AI 自身が「渡された画像はこの設問の解答ではない」と報告した設問は、ジョブが
`PERMANENT` で終わり `GradeResult` を残さない（[ai-grading-pipeline.md](./ai-grading-pipeline.md)）。
上の3条件にそのまま当てはまる。**当てはめてよい**と判断した。

- この答案は人の手が要る。数えないと**一覧が「0」と言い、開いた先に仕事がある**——
  Issue #84 の形そのものになる。
- 行に出るのは「AIが採点できなかった設問があります」で、この設問について本当のこと
  しか言っていない。一覧は**直し方を名乗っていない**ので、開いた先と矛盾しない。
- 「点数を入力」も残してあるので、「自分で採点する設問」という読み方も嘘にならない。

**ただし、開いた先が勧める最初の一手は違う。** ここでは「点数を入力」ではなく
**「回答欄の位置を直す」**である（[pdf-review-overlay.md](./pdf-review-overlay.md) §2.13.2）。

**未決事項**: 切り出しの誤りは、答案 1 枚ではなく**テスト 1 つの問題**になりやすい
——同じ枠が全答案でずれるので、40 枚すべてにこの旗が立ちうる。そのとき講師が
40 枚を 1 問ずつ手で採点し始めるのは、正しい直し方（回答欄を 1 回直す）より
はるかに高くつく。**実データでこの形が何件出るかを見てから**、キューにこの種類を
区別する手掛かりを足すかを決める。実測前に列を増やすと、頻度が 0 だったときに
消せない画面が残る。

### 6.2 起票されていない答案は数に出ない

ほぼ余白が 1 問でもあると答案全体が `needs_review` になり、**自動起票が止まる**
（[job-queue.md](./job-queue.md)「自動起票は `ai_processed` の答案だけに限る」）。
その状態ではジョブ自体が無いので、この数は 0 である。

**画面側の `_canGradeManually` も同じ条件なので、両者は一致している**（「点数を
入力」も出ない）。講師の次の一手は「AI採点を開始」か回答欄の修正であり、
そこは添削レビュー画面が答える。**キューだけでは「起票されていない」ことは
分からない。**

## 7. 取込が立てた旗は、生のまま出さない

`Submission.review_reason` はワイヤ形式である。

```text
answer_area_undefined:q-1;crop_nearly_blank:q-2,q-3
```

`core/submission_review_reason.dart` の `describeReviewReason` が
「回答欄が確定できない設問が 1 問、切り出しがほぼ余白の設問が 2 問あります」に
変える。**どの設問かは書かない** — 40 枚を仕分ける画面に要るのは「何が何問か」
までで、設問を名指しするのは開いた先の仕事である。

**知らない理由には何も言わない。** 新しいサイドカーがこのビルドの知らない旗を
立てているとき、当てずっぽうのラベルを付けると実際とは違うことを講師に読ませる
ことになる。`questionsFlaggedAs` が未知を空集合として扱うのと同じ方針で、全部が
未知なら行そのものを出さない。

## 8. 入口

**ホームのテストカードの「確認済み N / M」を押す。** ボタンは増やしていない。

#68 でホームの情報量を絞ったのは正しい判断だったが、**あのときは答案キューが
存在しなかった**。いまは「40 枚のうちどれを見たか分からない」ほうが問題である。

既存の「レビューを続ける」は残してある。あれは「次の 1 件を今すぐ開く」で、
キューは「全体を見る」であり、役割が違う。

### 8.1 テスト一覧からも入る（Issue #151）

**入口がホームのテストカードだけだったのが、実機で行き止まりになった。**
ホームはテストを絞って載せるので、11 教科を登録するとカードに出ない教科が生まれ、
**その教科の答案には到達手段が無かった**。ホームの絞り込みそのものは
`docs/home-dashboard.md` §2.3 で直したが、それとは別に**全テストを出す画面から
キューへ入れる必要がある** — ホームがどう絞ろうと、テスト一覧が登録画面にしか
行けないのは独立した欠落だからである。

`ready` のテストはタイルのタップで答案キューへ、テスト設定は末尾のボタンから。
`draft` のテストはタップでテスト設定のまま — 答案を取り込めない（簡易設計書
§6.1）ので、キューは必ず空にしかならず、行き止まりが 1 つ増えるだけになる。

### 8.2 どの入口から入っても、同じように戻る（Issue #160）

**入口は 3 つある。** ホームのテストカード「確認済み N / M」、テスト一覧のタイル、
そして添削レビューで全問を確定したときのスナックバー「答案キューへ」（§9）。

3 つとも `context.push` で入る。**`go` は使わない。** go_router の `go` は現在地を
指すだけの API ではなく、積んであるスタックを丸ごと捨てて組み直す。ルート表は
`app_router.dart` に 7 本フラットに並んでいて `go` の行き先には親ルートが無いので、
着いた画面には戻る先が 1 つも残らない — アプリバーの戻る矢印が出ず、Escape も
Alt+Left も効かない。

実機再検証 #5 では、スナックバーだけが `go` だった。**同じ画面が、入口によって
行き止まりになったりならなかったりしていた**（3 つ目から入った講師は、アプリを
再起動するまでホームへ戻れなかった）。入口ごとに戻り方が変わる画面は、来た道を
利用者に覚えさせることになる。

**スタックを捨ててよいのはコンポジションルート（`lib/main.dart`）だけである。**
サイドカーが落ちたときに講師が積んだ画面を全部落とすのは、まさに「捨てる」のが
正しい操作で、そこには理由が書いてある（Issue #24）。

これは #88「ホーム以外に戻る導線が無い」の全部ではない。**戻るスタックが空のまま
着いた画面**（起動直後のディープリンク、`AUTO_SCORING_INITIAL_ROUTE`）には依然として
出口が無く、それは全画面共通の `AppBar` の入れ替えで解く話なので #88 に残してある。

## 9. 答案をまたぐ連続レビュー

最後の設問を確定したら、**次の答案の最初の設問へ `context.replace` で移る**。

`push` ではない。40 枚ぶんを戻るスタックに積んでも意味が無く、戻る先は「入って
きた場所」（キュー、またはホーム）のままであるべきだからである。答案ごとに
`State` が作り直されることは `app_router.dart` の `ValueKey` が保証している。

AppBar に `12 / 40 件目` を出す。**キューが引けていないときは書かない** —
「1 / 1」と出すと残り 1 枚だと読まれる。分からないことを、分かっているように
見せない。

次が無いときは**理由を言い分ける**。キューが引けていないのか、本当に全部終わった
のかは、講師にとって全く違う話である。後者にはキューへ戻る導線を添える（この
「答案キューへ」も `push` で入る。理由は §8.2）。

**キューが引けなくてもこの画面は成立する。** そのときは現在地が出ず、最後の設問で
止まる（この Issue より前の挙動に戻るだけ）。キューが引けないことを理由に、目の前の
答案のレビューまで止める意味は無い。

## 10. 後回し（`S`）

何も確定せず、答案の状態も書き換えず、次の答案へ移る。未了のままキューに残り、
また回ってくる。**「無視する」ではなく「順番を変える」**なので、画面のラベルも
「後回し」にしてある。押したことは画面に出す — 黙って次へ飛ぶと「消えた」と
読まれる。

決定は
[business-rules-and-evaluation-data.md](./business-rules-and-evaluation-data.md)
§2 (16)。

**当初の理由は Issue #118 が解消した。** 書いた時点では「AI 採点が失敗した設問が
あると、その答案は確定できない」ことが `S` を要る理由だった。「点数を入力」が
入ったいま、その答案は人が引き取れる。

**それでも残す。** 40 枚を続けてさばく最中に手が止まる理由は、AI の失敗だけでは
ない。採点基準を確認したい、後の答案と見比べたい、単に判断を保留したい — どれも
「いま決めない」であって、**決めないまま次へ行けることが要る**。むしろ #118 が
入ったことで、後回しにした答案が最後に必ず片付けられるようになった。
