# AI一次添削支援アプリ 簡易設計書

## 1. 概要

### 1.1 目的

塾から提供される以下の資料を利用し、答案添削作業を効率化する。

必須:

- 生徒答案（PDF）
- 採点基準（PDF）

任意（あれば精度が上がる）:

- 添削資料（Word / Excel）
- 添削サンプル（PDF）

**PDFだけが来る前提を置かない。** 実際の配布物にはWord / Excelが含まれる。
詳細は §4、実資料で確認できた構造は
[`grading-material-structure.md`](./grading-material-structure.md)。

AIが一次添削を行い、人間はAIの結果を確認・修正・承認することを基本とする。

完全自動採点ではなく、**Human-in-the-loop型の添削支援システム**として設計する。

効率的に採点を行うために並列で採点を行えるようにする。

---

## 2. システムの基本方針

### 2.1 AIの役割

AIは以下を担当する。

- 採点資料（採点基準・添削資料）の役割判定と構造抽出（§4.3）
- 生徒答案の読み取り
- 採点基準に基づく判定
- 点数候補の生成
- ○・×等の添削記号候補の生成
- コメント候補の生成
- 判定根拠の生成
- 判定信頼度の算出

AIの判定を最終結果とはしない。

### 2.2 人間の役割

人間は以下を担当する。

- AIによる文字認識結果の確認
- AI採点結果の確認
- 添削位置の確認
- 点数・コメントの修正
- AI結果の承認または却下
- 判読困難な答案の手動添削

# 4. 入力データ

> **本章はIssue #95で全面的に書き換えた。** 旧版は「模範解答PDF」と「採点マニュアルPDF」を
> 必須入力としていたが、実際の採点者が持っている資料と対応していなかった。
> 実資料で確認できた構造は
> [`grading-material-structure.md`](./grading-material-structure.md) に記録している。

## 4.1 必須入力

1つのテストについて、必須は次の2つだけとする。

### 採点基準PDF

**このテストの採点に必要な情報が入った資料。** 実資料では、1本のPDFに

- 問題（設問文）
- 模範解答
- 解説
- 配点・採点基準

がまとめて入っていた（[実資料の構造](./grading-material-structure.md) §3.3）。
**ただしこの4点が常に揃っていることを前提にしない。** 取り出せた項目だけを使い、
取り出せなかった項目は「取れなかった」として人に確認させる（§4.4）。

### 生徒答案PDF

実際に添削する対象。

---

## 4.2 任意入力

### 添削資料（任意だが強く推奨）

誤答パターンと、それに対する赤入れ（コメント）の文例。**Word / Excel で配布される。**

- **無くても登録・採点できる。** ただしコメント候補の質が落ちる
- **無い場合は画面で警告し、精度が落ちることを明示する**（決定3）
- 形式は Word / Excel のどちらもありうる。実資料では教科によって、同じ役割の情報が
  表（Excel）だったり地の文（Word）だったりした

### 添削サンプル（任意）

添削済み答案の見本。採点形式やコメントの入れ方の参考として登録できる。

### 模範解答PDF（廃止）

**必須入力から外した**（決定1）。理由は次の2つ。

1. **採点基準PDFが模範解答を既に含んでいる。** 別に要求する理由がない
2. **「回答欄に模範解答が書かれた形式のPDF」を採点者が持っているとは限らない。**
   旧版はこれをテストプロファイルの自動解析の入力にしていたが、その前提が成り立たない

模範解答が別ファイルで手元にある場合は、参考資料として §4.2 の枠で追加してよい。
**アプリはそれを前提にしない。**

---

## 4.3 形式非依存の取り込み — 設計方針

> **この方針はIssue #95でオーナーが指示したものである。**
>
> > 今回のケースがこれからの採点資料と合致するとは限らないため、いろいろなケースに
> > 対応できるようにしてください。分類にAIやLLMを使用しても構いません

**形式ごとのparserを書かない。文書をLLMに理解させ、人が確認する。**

### 4.3.1 なぜparserを書かないか

実資料を調べた結果、**形式を仮定した実装はどこかで必ず外れる**ことが分かった
（[実資料の構造](./grading-material-structure.md)）。

- 採点基準PDFの機械可読性が3通りに割れる。**「抽出文字数 > 0」はOCR要否の判定に使えない**
  （縦書きの文書は、文字は取れるのに読み順が壊れる）
- 添削資料のExcelは、7本に対して**列スキーマが4種類**あり、**見出し行が1行目ですらない**
- 同じ役割の情報が、教科によって表だったり地の文だったりする
- ファイル名の規則が揃っておらず、名前から役割を判定できない

**これは1つの塾の1期分のサンプルでしかない。** 次の塾の資料が同じ形である保証はない。
形式ごとにparserを足していく方針は、資料が増えるたびに破綻する。

### 4.3.2 取り込みの4段階

```text
1. 機械的な下ごしらえ（形式非依存）
   PDF   → pdfiumでテキスト抽出 + 全ページを画像化
   Word  → テキストと表を素直に取り出す（構造は仮定しない）
   Excel → 全シートのセルを素直に取り出す（見出し行を仮定しない）
        ↓
2. 役割の判定（LLM）
   「この文書は答案か、採点基準か、参考資料か、添削サンプルか」を
   ファイル名ではなく中身から判定する
        ↓
3. 構造の抽出（LLM）
   設問・配点・採点の観点・よくある誤り・コメント例を、
   表でも地の文でも同じ出力スキーマに落とす
        ↓
4. 人による確認（必須の関門）
   抽出結果は提案であって確定ではない。
   取れなかった項目は「取れなかった」と表示する。推測で埋めない
```

段階1でテキストが得られなかった場合、および得られても読み順が壊れている疑いがある場合は、
**ページ画像を多モーダルモデルに渡す。** §8.3 も参照。

### 4.3.3 この方針の代償

**代償があることを承知のうえで採る方針である。** 隠さず記録しておく。

| 代償                                      | 内容                                                                       | どう扱うか                                                      |
| ----------------------------------------- | -------------------------------------------------------------------------- | --------------------------------------------------------------- |
| 採点資料そのものを外部APIへ送ることになる | 塾の著作物であり、講師名・塾名を含む                                       | 決定7で許可済み。ただし**公開は禁止**（§26、業務ルール §2 (2)） |
| コストと待ち時間                          | ファイル1本ごとにLLM呼び出しが発生する。テスト登録が重くなる               | 登録は1テストにつき1回。答案ごとの採点とは頻度が違う            |
| **再現性が無い**                          | **同じ入力から同じ結果が出るとは限らない。抽出結果をテストで固定できない** | **だから人の確認が必須である**（§4.3.2 段階4）。§4.4 も参照     |

**3番目が最も重い。** 抽出の正しさをテストで担保できない以上、
**人の確認を省略可能な最適化として扱ってはならない。** 確認は仕様の一部である。

---

## 4.4 抽出に失敗したときの退避

**全項目を人が手入力できる画面を必ず用意する**（決定8）。

- LLMが役割判定・構造抽出のどちらに失敗しても、**登録作業が止まらないこと**
- 取れなかった項目は空欄として提示し、**推測値を埋めない**
- 一部だけ取れた場合は、取れた項目を初期値として提示し、取れなかった項目だけ人が埋める
- 「AIが抽出した値」と「人が入力・修正した値」を区別して保持する（§35-5）

詳細は §16.2・§24。

## 4.5 PDF構造

テストごとにPDFレイアウトが異なることを前提とする。

そのため、

> 全テスト共通の固定座標

は使用しない。

代わりに、テスト単位で「テストプロファイル」を生成する。

### 4.5.1 実資料で確認できた、設計が耐えるべきケース

以下は**仕様ではなく、実在が確認できた例**である
（[実資料の構造](./grading-material-structure.md)）。設計がこれらに耐えるか確認する材料として使う。

| ケース                                                                           | 根拠                                       |
| -------------------------------------------------------------------------------- | ------------------------------------------ |
| **設問とページの対応が多対多**（1設問が2ページに跨る／1ページに複数設問）        | 目視した3教科で3通りが同時に存在           |
| **縦書きの答案**（列が右から左）                                                 | 目視した3教科中1教科                       |
| 回答欄の形状が4通り（横書きマス目／縦書きマス目／小問1文字枠／罫線なし自由領域） | 同上                                       |
| **答案PDFが課題全体の一部**（フッタの総ページ数とPDFのページ数が一致しない）     | 目視した3教科中1教科で不一致               |
| **答案にQRコードが0〜2個**（個数が答案により違う）                               | 目視した3教科で0個・1個・2個がそれぞれ存在 |
| 採点基準PDFが完全な画像で抽出0文字                                               | 異なる10文書中6                            |

**「1ページ＝1設問」を既定値にしてはならない。** 旧版の設問依存DAG（§4章 業務ルール）は
複数ページ答案を前提にしており、この点は引き続き有効である。

# 5. テストプロファイル

## 5.1 概要

新しいテストを登録した際に、PDFの構造を解析し、そのテスト専用の情報を保存する。

例：

```text
テスト
 ├─ Page 1
 │   ├─ 問1
 │   ├─ 問2
 │   └─ 問3
 │
 └─ Page 2
     ├─ 問4
     └─ 問5
```

## 5.2 保存する情報

設問ごとに以下を保持する。

- 問題番号
- **ページ番号（複数可）** — 1設問が複数ページにまたがる（§4.5.1）
- 問題文領域
- 回答欄領域
- **書字方向**（横書き / 縦書き） — 縦書きの答案が実在する（§4.5.1）
- ○×等を配置する候補領域
- コメント配置候補領域
- 配点
- 採点ルール
- 模範解答（採点基準PDFから取れた場合。**無くてもよい**）

各項目は **「AIが抽出した値」か「人が入力・確定した値」かを区別して保持する**（§4.3.3・§35-5）。
**取れなかった項目は空のまま保持する。推測値で埋めない**（§4.4）。

座標については可能な限り0〜1の正規化座標で保持する。

> PoC 4（Issue #15）でこのスキーマの往復（生成→人間確認→再適用）を検証した。
> ドメインモデルは `RegionKind`（問題文領域／回答欄領域／○×等の候補領域／配点／
> 採点ルール／模範解答）ごとに `Region` を持ち、`Profile.status` が
> `DRAFT`（未確認）→`CONFIRMED`（確認済み）の一方向で遷移する。詳細は
> [`poc-4-multi-layout-profiles.md`](./poc-4-multi-layout-profiles.md)。

例：

```json
{
  "questionId": "q3",
  "page": 2,
  "answerArea": {
    "x": 0.15,
    "y": 0.42,
    "width": 0.7,
    "height": 0.18
  }
}
```

# 6. テスト登録フロー

**テスト登録と答案取込は1つの操作で行う**（決定9。§6.3）。

```text
採点基準PDF（必須）
+ 生徒答案PDF（必須。1枚でも複数枚でもよい）
+ 添削資料 Word/Excel（任意・強く推奨）
+ 添削サンプルPDF（任意）

  ※ ディレクトリごと渡してもよい（決定9。§6.3.2）
        ↓
形式非依存の下ごしらえ（§4.3.2 段階1）
        ↓
役割の判定・構造の抽出（LLM。§4.3.2 段階2-3）
   ├─ 採点基準から：設問・配点・採点の観点・模範解答
   └─ 答案から　　：回答欄・書字方向・設問とページの対応（§6.2）
        ↓
テストプロファイル生成（draft）
        ↓
人間による確認 ←→ 取れなかった項目は人が手入力（§4.4）
        ↓
必要なら領域・配点・採点基準を修正
        ↓
テスト登録完了（confirmed）
```

## 6.1 重要方針

AIによる推定を無条件で採用しない。

初回のみ人間が、

- 設問の対応
- 回答欄
- 配点
- 採点基準

を確認する。

**この確認は省略可能な最適化ではない。** §4.3.3 のとおり、LLMによる抽出は
**同じ入力から同じ結果が出ることを保証できず、テストで固定できない。**
人の確認が、正しさを担保する唯一の手段である。

## 6.2 回答欄は答案そのものから解析する

**決定2。** 回答欄の位置は、模範解答からではなく、**生徒答案のページ画像から**求める。

- 答案のページ画像を多モーダルモデルに渡し、**回答領域の候補**を出させる
- 併せて**書字方向**（横書き / 縦書き）と、**設問とページの対応**を推定させる
- 人が確認・修正して確定する

### なぜ答案からか

**教科ごとに様式が大きく変わり、共通の様式を仮定した自動解析が成立しないため。**
実資料では、回答欄の形状が4通り、設問とページの対応が3通り観測された（§4.5.1）。
そして旧版が入力に使おうとしていた「回答欄に模範解答が書かれたPDF」は、**そもそも存在しない**。

### 制約

- **1テストにつき、少なくとも1枚の答案が登録時に必要になる。** 答案が1枚も無い状態では
  回答欄を確定できない。→ **決定9により、登録と答案取込を同時に行うことで解消した**（§6.3）
- 答案ごとにスキャンのずれがあるため、確定した回答欄は**テスト単位のプロファイル**として持ち、
  答案ごとの位置合わせは §7 の前処理で吸収する

## 6.3 テスト登録と答案取込を同時に行う（決定9）

**「テストを登録してから答案を取り込む」という2段構えをやめる。**
1つの画面で、採点基準PDFと答案を**同時に**受け取る。

### なぜか

§6.2 のとおり、**回答欄は答案から解析する**（決定2）。
答案が無ければ回答欄が決まらず、テスト登録が完了しない。
一方、旧版のフローは「テスト登録 → 答案取込」の順で、**必要な順序と逆転していた。**

利用者から見ても、「テスト登録」と「答案取込」が何を指すのか分かりにくいという指摘が
Issue #95 の発端だった。**1回の操作にまとめることで、この分かりにくさも減らす。**

### 6.3.1 受け取るもの

| 種別                     | 必須 | 備考                                      |
| ------------------------ | ---- | ----------------------------------------- |
| 採点基準PDF              | 必須 | §4.1                                      |
| 生徒答案PDF              | 必須 | 1枚でも複数枚でもよい。回答欄の解析に使う |
| 添削資料（Word / Excel） | 任意 | 強く推奨。無ければ警告（§4.2）            |
| 添削サンプルPDF          | 任意 | §4.2                                      |

**答案は後から追加できる。** 登録時に渡した答案でプロファイルを確定し、
以降の答案は確定済みプロファイルを再利用する。

### 6.3.2 ディレクトリごとの取り込み（オプション）

**フォルダを渡すと、中の各ファイルの役割を判定して振り分ける。**

- 役割の判定は **§4.3.2 段階2 と同じ**。すなわち **LLMが中身から判定する**
- **ファイル名に依存しない。** 実資料の教科フォルダには連番と役割名を含む命名規則があるが、
  **その規則が揃っていないうえ、命名規則の違う塾でも動く必要がある**
  （[実資料の構造](./grading-material-structure.md) §2）
- 振り分け結果は**人が確認して確定する**。判定できなかったファイルは
  「判定できなかった」として提示し、人が役割を選ぶ。**推測で割り当てない**
- サブディレクトリの扱い、対象外拡張子の扱いは未決（§33.2）

**この機能はオプションである。** 個別にファイルを選ぶ経路は常に使えること。

# 7. 答案解析

## 7.1 前処理

答案PDFをページ単位で画像化する。

必要に応じて以下を行う。

- 傾き補正
- 回転補正
- 拡大縮小補正
- ノイズ低減
- コントラスト調整
- テストプロファイルとの位置合わせ

画像処理にはOpenCVを使用する。

> 取込・保存・前処理の実装はIssue #17で行った。PDFの検証（拡張子・MIME・magic bytes・
> size上限・page数・暗号化・破損）、同一PDFの再取込方針、回答欄切り出しは
> 「テストプロファイルとの位置合わせ」ではなく`Question.answer_area`
> （Issue #11で導入済みの設問ごとの正規化座標）を直接使う実装とした。
> デスキュー等の前処理はプレビュー画像にのみ適用し、切り出し座標には影響しない。
> 詳細・未決事項は[`answer-intake-and-preprocessing.md`](./answer-intake-and-preprocessing.md)。

# 8. 手書き文字認識とOCRの位置づけ

> **本章はIssue #95 決定10（数式・英作文・図グラフも採点対象にする）を受けて
> 位置づけを変更した。** 変更の理由は §8.1.2 に書く。

## 8.1 基本方針

### 8.1.1 採点の入力は答案のページ画像である

**OCRは採点の前提ではない。** 採点AIには**答案のページ画像を渡す**。
OCR結果は、得られていれば**補助情報として添える**。

```text
答案画像 ─┬────────────────→ 採点AI（多モーダル）
          │                     入力: 画像 ＋（あれば）OCR結果
          │                     出力: 採点結果 ＋ **採点AI自身の読み取り説明**
          │
          └─ OCR ────────────→ 認識文字     ─→ 採点AIの読み取りとの**照合**（§8.1.3）
                               Bounding Box ─→ 文字に紐づくAnnotationの位置決定（§12.3）
                               Confidence   ─→ Recognition Confidence（§10）
```

**OCRと採点AIは、別々のモデルが別々に答案を読む2本の独立した経路である。**
この点が §8.1.3 の前提になる。

### 8.1.2 なぜ位置づけを変えたか

**決定10により、数式・英作文・図グラフが採点対象になった。**
このうち**数式と図は、テキストに落とした時点で情報が失われる。**
手書きのグラフを文字列として表現する方法は無く、数式も、レイアウト（分数の上下、
添字、根号の範囲）が意味を持つため、1次元の文字列にすると採点に必要な情報が落ちる。

したがって **「OCRでテキストにしてから採点する」という前提は、決定10と両立しない。**

一方、このアプリは既に**答案のページ画像を多モーダルモデルに渡す**方針を採っている
（決定2の回答欄解析、§4.3 の資料理解）。**画像のまま採点基準と突き合わせるなら、
数式も図も同じ経路で扱える。**

**採点の入力を画像に一本化する理由**は、決定10への対応に加えてもう1つある。
テキスト経路（記述式）と画像経路（数式・図）を分けると、**経路ごとにプロンプトも
失敗の仕方も異なる2系統を保守する**ことになる。これは §4.3 で
「形式ごとのparserを書かない」と決めたのと同じ問題である。**同じ理由で経路も分けない。**

### 8.1.3 それでもOCRを残す理由

**OCRは採点の前提ではなくなるが、廃止はしない。** 2つの役割が残る。
**ただし1つ目は、採点の入力を画像にしたことで意味が変わっている。**

#### 役割1: 独立した比較材料（「採点AIが何を読んだか」ではない）

> **注意（Issue #95 レビューでの指摘）**: 旧版はこの役割を
> 「AIが生徒の字をどう読んだかの提示」と書いていた。**これは誤りである。**

**画像を主入力にすると、OCRと採点AIは別々のモデルが別々に答案を読む。**
したがって次が成り立つ。

- **OCRが正しく読んでいても、採点AIが同じ文字を正しく読んだ保証はない。**
- **OCR結果とそのConfidenceをいくら確認しても、採点AIの読み違いは検出できない。**

**OCR結果は「採点AIが何を読んだか」ではなく、「独立した比較材料」である。**

#### 読み取りを人が検証するために必要なもの

**3つ揃って初めて検証になる。文字答案でも同じである。**

| #   | 手段                         | 役割                                                                                                                                                   |
| --- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | **採点AI自身の読み取り説明** | **採点の根拠になった読み取りはこちらである。** 採点AIに「何をどう読んだか」を出力させる（§9.2）                                                        |
| 2   | **OCR結果との照合**          | 1と食い違えば、少なくとも一方が誤っている。**価値は「食い違いの検出」にあり、一致は弱い根拠にすぎない**（2つのモデルが同じ誤りをする可能性は消えない） |
| 3   | **元画像の確認**             | 最終的な裏取り。**1と2が一致していても省略できない**                                                                                                   |

**3は文字答案でも省略できない。** 旧版は「人が元画像を見る」を非テキスト答案だけの
要件として書いていたが、それは誤りだった。**画像を主入力にした以上、文字答案でも
採点AIの読み違いはOCRでは検出できない。**

UIは、**採点AIの読み取り説明とOCR結果を並べ、食い違いを目立たせる**こと。
**両者を1つの「認識結果」として混ぜて表示してはならない**（どちらの読みなのかが
分からなくなり、照合そのものが成り立たない）。

#### 役割2: 文字に紐づくAnnotationの位置決定

§12.3 は、特定の語に下線・囲みを引くためにOCRのBounding Boxを使う。
§35-3「AIにPDF座標を直接決めさせない」を守る以上、**座標の出どころが要る**。
OCRを消すと、この原則を破るしかなくなる。**この役割は画像主入力でも変わらない。**

### 8.1.4 OCRで表現できない答案の扱い

**数式・図・グラフには、OCRによる読み取り結果もBounding Boxも期待できない。**
ここを取り繕わない。

- **Recognition Confidence を出さない。** OCRが読めていないものに信頼度の数値を与えない。
  UIでは「読み取り結果なし」として提示する（§10）
- **§8.1.3 の3つの手段のうち、2（OCR結果との照合）が使えない。**
  残るのは 1（採点AI自身の読み取り説明）と 3（元画像の確認）だけになる
- **文字に紐づくAnnotationは置けない。** §12.4 のとおり設問単位のコメント領域へ退避する

**なお §8.1.3 のとおり、元画像の確認は文字答案でも必須である。**
非テキスト答案で特別なのは「照合相手が無くなる」ことであって、
「ここだけ人が見る」ということではない。

### 8.1.5 判断A（OCRサービス）への影響

判断A（Google Document AI、Issue #81 で確定）は**維持する**が、**重要度が下がる。**

- **OCRは採点の critical path から外れる。** OCRが失敗しても採点は実行できる（§24）
- したがって「OCRサービスが使えないと採点できない」というブロック条件は**解消する**
- ただし **OCRが無いと、読み取りの検算と、文字に紐づくAnnotationができない**。
  機能が落ちるのであって、動かなくなるのではない
- **未検証**: 非テキスト領域（図・数式）を判定してOCR呼び出しを省けばコストが下がるが、
  **その判定を確実に行えるかは検証していない**。現時点で省略前提の設計にしない（§33.2）

### 8.1.6 Vision AIへの入力

採点AIには次を同時に入力する（§9.1）。

- **元答案画像（必須）**
- OCR結果（得られていれば）
- 採点基準・配点
- 模範解答（採点基準PDFから取れた場合）

# 9. AI採点

## 9.1 入力

設問ごとに以下をAIへ入力する。

- 問題文
- **生徒答案画像（必須。採点の主入力）**（§8.1.1）
- OCR結果（**得られていれば**。無くても採点は実行する）
- 採点基準（採点の観点と、加点式 / 減点式の別を含む）
- 配点
- 模範解答（採点基準PDFから取れた場合。**必須ではない**）
- 添削資料から抽出した誤答パターン・コメント例（登録されている場合）

**採点方式は設問ごとに異なりうる。** 実資料では、観点ごとに積み上げる加点式と、
配点から引く減点式（「配点を超えて減点しない」等の下限規則を伴う）が教科間で混在していた
（[実資料の構造](./grading-material-structure.md) §3.5）。
業務ルール §2 (8) のとおり両方に対応する。

---

## 9.2 出力

AIから自由文だけを返させず、構造化データとして取得する。

**`recognition` は採点AI自身の読み取り**（§8.1.3 の手段1）であり、
**OCRの読み取り結果とは別物である。** 両者は別フィールドとして保持し、
**同じ「認識結果」として混ぜない**。`source` でどちらの読みかを区別する。

例：

```json
{
  "questionId": "q3",

  "recognition": {
    "text": "光合成によって酸素が発生する",
    "confidence": 0.91,
    "source": "grading_ai"
  },

  "grading": {
    "score": 4,
    "maxScore": 5,
    "confidence": 0.88
  },

  "criteria": [
    {
      "id": "criterion-1",
      "result": "pass",
      "confidence": 0.97
    },
    {
      "id": "criterion-2",
      "result": "partial",
      "confidence": 0.76
    }
  ],

  "comment": "理由の説明が不足しています。",

  "annotations": []
}
```

# 10. 採点Confidence

以下のConfidenceは分離する。

### Recognition Confidence

**OCRが自身の読み取りに与える信頼度である。それ以上のものではない。**

- **採点AIの読み取り精度を保証しない。** OCRと採点AIは別々のモデルであり、
  この値が高くても**採点AIが読み違えている可能性は残る**（§8.1.3）
- したがって **この値を根拠に採点結果を自動確定してはならない**
- **OCRで読み取れない答案（数式・図・グラフ）には、この値を出さない**（§8.1.4）。
  「読み取り結果なし」として提示する。**読めていないものに数値を与えない**

### Grading Confidence

読み取った答案に対して採点が正しい可能性。

例えば、

```text
文字認識：98%
採点判断：63%
```

という状態を許容する。

# 11. 添削Annotation

## 11.1 MVPで対応する種別（決定4）

**ボックス・下線・テキストに対応する。図形は将来対応とする。**

| 種別             | 用途                            |
| ---------------- | ------------------------------- |
| ボックス（囲み） | 対象箇所を囲む / 注釈を枠で囲む |
| 下線             | 対象箇所の指摘                  |
| テキスト         | コメント・点数・○×△等の記号     |

**テキストは書字方向を持つ。** 縦書きの答案には縦書きの注釈を置く（§4.5.1・§12）。
左横書きだけを想定した実装は、縦書きの教科で破綻する。

## 11.2 将来対応（MVP対象外）

**図形。** 特に**矢印**である。

## 11.3 実運用との差 — 既知の制約

**決定4の範囲は、実際の添削で使われている表現の一部でしかない。**
実資料の添削サンプルと、塾が配布している「定型オブジェクト集」で確認できたものは次のとおり
（[実資料の構造](./grading-material-structure.md) §6・§7.1）。

| 実際に使われているもの                                           | MVPでの扱い                                               |
| ---------------------------------------------------------------- | --------------------------------------------------------- |
| テキスト（縦書き含む）                                           | **対応**                                                  |
| 下線（直線・波線・破線）                                         | **対応**（線種の作り分けは未決）                          |
| 囲み（矩形・角丸の吹き出し）                                     | **対応**                                                  |
| ○ / × / △ / チェック相当                                         | **対応**（テキストとして描画）                            |
| **矢印**（直線・曲線・ループ・双方向）                           | **対象外。** 注釈と対象箇所を結ぶ主要な手段だった         |
| **括弧類**（`( )` `{ }` `[ ]` を答案に重ねて語のまとまりを示す） | **対象外**                                                |
| **手描きの図**（グラフ等）                                       | **対象外**                                                |
| インラインの加減点（`(+3)` `(-1)`）                              | **未決**（§11.4）                                         |
| 白い矩形（下地の罫線を隠す）                                     | **対象外**                                                |
| 他ページへの参照文                                               | **対象外**（注釈が1ページに収まらない場合に使われている） |

**特に重い制約**: ある教科では、添削の主体が**手描きのグラフ**だった。
**その教科はMVPの表現力では再現できない。** これは「まだ作っていない」ではなく
「MVPの範囲では代替できない」として認識すること。

### 矢印の代わりに何を使うか

矢印が使えない以上、**注釈と対象箇所の対応づけには参照記号を使う。**
実資料でも、小さな囲み記号（※1 等）を対象箇所と注釈ブロックの両方に置いて
対応づける方法が併用されていた。

**MVPはこの参照記号方式を前提に設計する。** ボックス・下線・テキストだけで
実運用に近づけるには、この仕組みが要る。

## 11.4 未決

- インラインの加減点表示（対象箇所ごとの `(+3)` `(-1)`）を扱うか。
  決定5は**設問ごと**の点数を扱うと定めており、部分ごとの加減点表示は含んでいない
- 下線の線種（直線・波線・破線）を作り分けるか

## 11.5 将来の拡張時に参照するもの

Annotation種別を拡張するときは、**推測で決めない。**
塾が配布している「定型オブジェクト集」（横書き版・縦書き版の2種）が、
**塾自身による「必要な添削表現」の答え**である
（[実資料の構造](./grading-material-structure.md) §7.1）。

## 14.1 点数の記載（決定5）

**添削済みPDFには、設問ごとの点数と合計点の両方を記載する。**

| 誰が         | 何を                           |
| ------------ | ------------------------------ |
| AIが提案する | **設問ごとの点数と、その根拠** |
| 人が確定する | **設問ごとの点数**             |
| PDFに載る    | **設問ごとの点数 ＋ 合計点**   |

合計点は、確定した設問ごとの点数から**アプリが算出する**。
AIに合計を計算させない。

## 14.2 答案上の得点欄を読み取るときの注意

実資料の答案には、**採点者が点数を書き込むための欄が最初から印字されている。**
これを読み取って再利用する場合、次を取り違えると誤った値を拾う
（[実資料の構造](./grading-material-structure.md) §4.4）。

**下表は実資料で観測された例であって、識別規則ではない**（識別方法はこの節の末尾）。

| 版面上の表記                 | 実体（観測された内容）                                          |
| ---------------------------- | --------------------------------------------------------------- |
| 斜線入りの四角の `得点/満点` | **設問ごとの得点欄。** 分母はその設問の配点であって満点ではない |
| 「総得点」ラベル付きの欄     | **テスト全体の合計。** **確認できたのは1教科のみ**              |
| 囲みの無い `得点/満点`       | **設問ごとの得点。** 縦書きの教科では囲みが無かった             |
| フッタの `（k／m）ページ`    | **ページ番号。** 得点ではない                                   |

**「四角で囲まれているか」で合計点を判定してはならない。**
囲みの有無は「得点かページ番号か」の手がかりにはなるが、
**設問得点と総得点は区別できない。**

**識別規則を版面の特徴に固定しない。** 上表は**実資料で観測された例**であって、
**次の資料が同じ形である保証はない**（§4.5.1 と同じ扱い）。
たとえば「総得点」というラベル表記は、**1教科でしか確認できていない**
（[実資料の構造](./grading-material-structure.md) §8）。
**この文字列の一致を必須の識別条件として実装してはならない。**

したがって得点欄の識別は、次のように行う。

1. **文書全体（版面と、あれば採点基準PDFの配点）から候補を提示する。**
   特定のラベル文字列や座標に依存しない（§4.3 の「形式ごとのparserを書かない」と同じ方針）
2. **どれが設問得点でどれが総得点かは、人が確認して確定する**
3. **判別できなければ推測しない。** 「判別できなかった」と提示して人が入力する（§4.4・§35-2）

なお、答案PDFが課題全体の一部だけを抜き出したものである場合、
**その PDF に総得点欄が含まれていないことがある**（§4.5.1）。
その場合、答案からはテストの満点も合計も分からない。配点は採点基準PDF側を正とする。

## 14.3 出力に含める欄

実資料の答案には、点数欄のほかに次の欄が印字されていた。

- **講評欄** — 添削者による全体コメント
- **添削者名の欄**

**MVPでこれらを埋めるかは未決**（§33）。決定5は設問ごとの点数と合計までしか定めていない。

## 16.4 答案取込画面

**2枚目以降の答案を追加する画面である**（決定9）。
最初の答案はテスト登録画面（§16.2）で同時に受け取るため、

> Issue #17でFlutter側の画面（`app/lib/features/answer_intake/`）とAPI
> （`POST /tests/{test_id}/submissions`ほか）を実装した。取込方式は
> business-rules-and-evaluation-data.md §2 (4) の確定（1PDF = 1生徒、生徒識別は
> 人間が手動割当）に従う。詳細は
> [`answer-intake-and-preprocessing.md`](./answer-intake-and-preprocessing.md) §9・§11。

### 取り込み方法

取り込み方法を選択できるようにする

- 1PDF = 1生徒か
- 1PDFに複数生徒が含まれるか
- PDFファイル名に生徒識別情報が含まれるか
- 一括投入方法

### QRコードは使わない（決定6）

実資料の答案にはQRコードが印字されているが、**アプリはこれを読まない。**
様式・回・生徒の識別に使わない。

**理由**（次に検討する人が同じ道を通らないよう残す）:

1. **必ずあるとは限らない。** 目視した3教科で、QRが0個の答案・1個の答案・2個の答案が
   それぞれ存在した（[実資料の構造](./grading-material-structure.md) §4.1）
2. **中身が何かを確認していない。** 何の識別子が入っているか不明であり、
   塾の内部管理用である可能性が高い。意味を推測して使うことはできない
3. **他塾の資料にあるとは考えられない。** これは1つの塾の様式である
4. 生徒の識別は**人間による手動割当**で確定する方針が既にある（業務ルール §2 (4)）。
   QRで置き換える必要がない

再検討するなら、まず1と2（何個あるか・何が入っているか）をオーナーに確認すること。

# 24. エラー処理

以下を正常系とは別に扱う。

### 資料の役割判定・構造抽出失敗（§4.3.2 段階2-3）

**人が全項目を手入力できる画面へ退避する**（決定8、§4.4）。
一部だけ取れた場合は、取れた項目を初期値として提示し、残りを人が埋める。
**推測値で埋めない。** 登録作業が止まらないことを優先する。

### PDF解析失敗

人間に通知する。**Word / Excel の読み取り失敗も同様に扱う。**

### 回答欄検出失敗

手動領域指定へ切り替える。

### OCR失敗

**採点は止めない。** OCRは採点の前提ではない（§8.1.1）。
答案画像で採点を実行し、**読み取り結果は「なし」として提示**する。
文字に紐づくAnnotationは設問単位のコメント領域へ退避する（§12.4）。

**OCRとの照合が使えないため、検証手段は「採点AI自身の読み取り説明」と「元画像の確認」の
2つだけになる**（§8.1.3・§8.1.4）。なお元画像の確認は、OCRが成功している場合でも省略できない。

### AI API失敗

再実行可能にする。

### AI低Confidence

自動確定せず要確認状態にする。

### Annotation位置特定失敗

設問コメント領域へ退避する。

### PDF出力失敗

元PDFを破壊しない。

# 26. セキュリティ・個人情報

## 26.1 provider への送信（決定7）

**採点基準・添削資料・添削サンプル・生徒答案は、採用providerへ送ってよい。**
形式非依存の取り込み方針（§4.3）が成立するための前提である。

> **Issue #95 でこの制約は緩和された。** それ以前は「実データを外部APIに送らない」を
> 厳守していた。

**ただし「providerへ送ってよい」は「公開してよい」ではない。**
この区別を取り違えないこと。

|                                                                                 | 可否     |
| ------------------------------------------------------------------------------- | -------- |
| 採用providerへ送信する                                                          | **可**   |
| commit / PR / Issue / docs / CIログ / スクリーンショット / テストfixture に出す | **禁止** |

公開物のスクリーンショットには**合成フィクスチャだけ**を使う。
実データを読み込んだ画面を撮って貼ると公開される。詳細は業務ルール §2 (2)・§6.7。

## 26.2 付随して守ること

- **送信内容と応答をログに残さない。** エージェント・アプリのログ、記録データセット、
  例外メッセージのいずれにも残さない
- **何を送るかを利用者に示す。** 塾の資料と生徒の答案を扱う以上、黙って送らない
- **providerごとにデータの扱いが違う。** フォールバック連鎖に組む前に、各providerの
  データ保持・学習利用の設定を確認して記録する（業務ルール §2 (2)）
- 元答案をクラウドストレージへ自動アップロードしない
- ローカル保存を基本とする
- 不要な外部通信を行わない

# 35. 設計上の最重要原則

本システムでは以下を守る。

1. AIの結果を無条件で確定しない
2. 読めない文字を無理に推測しない
3. AIにPDF座標を直接決めさせない
4. 元PDFを破壊しない
5. AI結果と人間の最終結果を分離して保持する
6. OCR・AIサービスを交換可能にする
7. テスト形式が変わることを前提とする。**手元の実資料は1つの塾の1期分でしかない**
8. 人間の確認作業自体を高速化する
9. 生徒データの外部送信可否を最優先で確認する
10. 実際の答案を用いたPoCで精度を確認してから本格開発する
11. **形式ごとのparserを書かない。文書をLLMに理解させ、人が確認する**（§4.3）
12. **抽出できなかったものは「取れなかった」と表示する。推測で埋めない**（§4.4）
13. **仕様を書く前に実物を見る。** 実資料を見ずに入力仕様を決めた結果、
    存在しない入力（模範解答PDF）を必須にした画面を作り込んだ（Issue #95）
